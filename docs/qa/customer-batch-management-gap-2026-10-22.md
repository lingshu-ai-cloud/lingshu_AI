# 客服按标签批量管理的能力盘点与完善方案

> 本文保留 43892e74 的历史排查结论。修复后的实现、验证结果和保留边界见[隔离验收报告](./customer-service-isolated-acceptance-2026-10-22.md)。

代码基线：43892e74。日期：2026-10-22。补充此前的[客服管线排查](./customer-service-pipeline-audit-2026-10-22.md)。

结论：已有业务标签、客户列表筛选、条件分群、逐客草稿、批次审批和派发基础，但尚未形成统一的“按业务维度选客并批量管理”能力。适合扩展现有分群与跟进流程，不需要新建一套群发系统。

## 对两个目标场景的判断

| 场景 | 已有基础 | 当前仍缺什么 |
| --- | --- | --- |
| 老客批量唤醒 | 沉默阶段、分群、逐客草稿、窗口/模板、批次审批和调度 | 明确老客口径、独立沉默维度、已成交客唤醒预设、跨渠道业务标签读取、可复核的条件预览、按唤醒目的生成草稿 |
| 新客批量筛选 | lead/inquiry、标签、BANT、意向分、新老关系证据 | 区分“新建档/新询盘/首次采购”，支持限定时间与证据、多个业务维度交叉、生成筛选解释和人工跟进任务，而非默认进入发送 |

现有代码可以支撑“在已有运行中明确选客，再走逐客跟进”，还不能把任意自然语言分群描述直接当作可靠的筛选契约。

“老客”需要区分已有往来客户与已验证成交客户。“沉默客户”可能从未成交；已有往来也不证明购买过。现有关系评估刻意保留 `purchaseConclusion: not_verified`，必须保持这个边界。若任务要求复购唤醒，需要订单事实或明确的成交证据，不能拿已有聊天历史代替。

## 本次确认的关键缺口

### 业务标签没有稳定到达所有下游

Messenger 的 classifyContextTags 会将标签、证据、BANT 等写入本地客户记录，但 `readAuthorizedMessengerCustomers` 当前只投影通过账号与凭据证据校验的入站消息及基础身份，去掉 tags/contextTagEvidence/stage/intentScore/bant 等字段。列表、分群若只拿这份投影，就无法用这些标签。

这项裁剪是为了排除没有当前账号证据的旧聚合资料，不能简单恢复透传原对象。应从已准入消息重新计算或读取绑定相同租户、账号、会话指纹、分析版本的分类结果；不匹配则明确返回 classification_pending/stale。

### 通用跟进默认规则不等于老客唤醒规则

`DEFAULT_FOLLOWUP_SEGMENT_CRITERIA` 使用 `match:any`，阶段包括 inquiry/quoted/silent30/silent60，排除 won，另设 minIntentScore=60。

实际语义是“命中这些阶段或意向分达标”，并且始终排除 won。因此低分 inquiry 可以进入，而已成交客户不会进入默认批次。这个配置可以服务其原有跟进目的，但不能当作高意向新客或已成交老客的统一默认模板。

### 标签组合表达力有限

目前 tags 数组内部采用 OR。即使顶层 match=all，`tags:[询价中,预算已提供]` 仍代表有任一标签，而非同时具备两者。没有独立 tagsAll/tagsAny/tagsNone，也没有“预算未确认”等缺失条件及嵌套条件组。

### 新增条件可能被静默忽略

分群 normalization 只保留既有字段，没有严格拒绝未知键。例如 inactiveDaysMin、country、waitingFor 当前均不在服务端标准中。只传这些条件，会退化为没有生效的筛选条件，测试客户全部匹配。

界面有国家、语言筛选，但服务端分群没有相同字段。Agent 不能把界面支持的筛选维度自动推定为 API 支持的维度。需要明确的字段目录与校验错误。

### 沉默时长与销售阶段混用

quoted/won 会被沉默阶段维护保留，前端“沉默客户”视图则只按 silent30/silent60 筛选。因此已成交或已报价但长期无互动的人，不会仅因长期沉默出现在该视图。

后端 activeWithinDays 表示“最近若干天活跃”，无法反向表达“超过若干天无买家回复”。lastActiveAt 也不是总能代表最后买家回复：原始会话实现会随消息更新，Messenger 授权投影则只保留已准入买家消息。应统一定义并分开提供 lastBuyerAt、lastSellerAt、lastContactAttemptAt。

### 上下文有数据但不能作为分群条件

BANT 完整度、SPIN 阶段、progressionGoal、是否等我回复、是否等客户、知识/报价待人工核验、最近跟进结果等信息分布在画像、会话、异常和跟进明细。当前 criteria 没有这些稳定筛选字段。

模型可以阅读它们形成建议，不代表已实现服务端可复现分群。尤其“买家说想要样品”与“已寄样待反馈”需要不同证据，不能只靠索取样品标签推导已寄样进度。

### 批量动作种类没有统一目录

已有主链集中在分群、生成草稿、审批、发送。标签修改的普通客户 PATCH、逐客标签分析或单客处理，不等于有一套可审计、可恢复的批量归类/指派/待办操作。

数字员工应能选择“只筛选”“复核标签”“创建待办”“分配负责人”“生成草稿”“申请发送审批”，不能把所有批量任务都解释成向客户发送消息。当前提示词里的“整理唤醒批次”也不等于已暴露这些完整结构化操作。

## 建议的业务分类维度

以下为拟补齐的逻辑模型，不是声称现有 API 已支持。

| 维度 | 建议字段及含义 | 事实来源 |
| --- | --- | --- |
| 客户关系 | new_inquiry/existing_contact/unknown，明确评估窗口 | 复用真实关系评估、入站消息和确认记录 |
| 成交情况 | purchase_verified、paidOrderCount、lastPaidOrderAt | 订单台账；无法关联时为 unknown |
| 销售阶段 | 初询、需求澄清、待报价、已报价、待确认、已成交 | 已有 CRM 状态及报价等业务对象，保留版本 |
| 业务需求标签 | 采购类型、补货、定制、样品、预算、交期 | 买家消息证据及人工确认，带分析版本和撤销状态 |
| 活跃与互动 | lastBuyerAt、lastSellerAt、buyerSilentDays、unansweredBuyerSince | 有时间和发送者身份的真实会话 |
| 待办进度 | waiting_for_seller/customer/quote_review/knowledge_review 等 | 当前回复顺序、未结报价/知识任务及负责人 |
| 资质与风险 | BANT 等级/完整度、真实性、意向分、黑名单 | 现有资质引擎及明确风险记录 |
| 产品与地区 | productIds、country、language、timeZone | 已确认客户信息和当前业务绑定，未知值明确保留 |
| 触达限制 | 最近发送时间、次数、人工接管、退订、窗口/模板 | 发送账本、接管记录、渠道许可及平台消息 |

所有可筛字段都需要类型、允许操作符、数据来源、更新时间、新鲜度和 unknown 语义。业务事实与模型推断要可区分。关键事实未知时，进入“待补充/待确认”客群，不悄悄把 unknown 解释成 false 或 zero。

## 应补成的执行链

1. **发现能力**：Agent 先读可用字段、操作符、动作、渠道范围与版本，不能编造条件。
2. **解释任务**：把“筛选近期询价且预算明确的新客”解析成有类型的条件组与动作意图；未知阈值不擅自变成确定业务规则。
3. **只读预览**：返回命中、排除、资料未知和不可联系的客户数量，以及每客理由、消息证据、能力限制；预览不创建草稿、不发消息。
4. **冻结执行范围**：复用 customer_segments/members，固定 criteriaHash、成员证据、数据版本和动作目的，修复此前已确认的部分写入恢复缺口。
5. **执行指定动作**：筛选导出结果、复核标签、创建跟进任务或生成逐客草稿；对本次没有要求的外部动作不自动延伸。
6. **审批与派发**：沿用现有 followup_batches/items、批准版本、窗口/模板、限频、接管和发送账本。发送前重查退订、人工接管、已回复和证据漂移。
7. **逐客追踪与汇总**：分别报告成功、排除、待确认、失败、未确认外部结果；重试只处理明确可重试项，查询原发送回执不重新发信。

保存的客群规则与执行快照应分开：规则可以重复评估，执行批次只用当时冻结的成员。新增客户不能自动加入已批准批次；新证据导致成员或文案变化，需要新的范围/版本并按既有规则重新审批。

## 优先提供的场景模板

| 模板 | 必须明确的条件 | 默认动作 | 不能冒充的事实 |
| --- | --- | --- | --- |
| 已往来客户唤醒 | existing_contact、买家沉默阈值、产品范围、未退订、触达冷却 | 预览并生成逐客唤醒草稿 | 已往来不代表已购买 |
| 已成交客户复购 | 可验证订单、最后购买/补货周期、产品与关系证据 | 预览、复核后生成复购草稿 | 不能把报价金额当成交金额 |
| 新询盘筛选 | 指定时间窗口内的新询盘证据、所需标签/资质、排除重复 | 分层结果及销售待办 | 新建档不代表新询盘或首次采购 |
| 高意向待跟进 | 明确 BANT/意向门槛与标签组合、没有未处理回复 | 生成待办或建议草稿 | 询价不自动等于高意向 |
| 已报价未回复 | 有已确认报价、报价后无买家回复、到期阈值 | 跟进提醒及草稿 | 询价中不代表已报价 |
| 样品与知识异常 | 已寄样或已受理任务证据、待处理对象与负责人 | 指派待办、批量复核 | 索取样品不代表寄样完成 |

阈值、行动额度和审批策略由现有企业配置或用户任务确定；模板只提供结构与可解释条件，不把样例阈值当作默认授权。

## 最小实现顺序

**第一批解决“筛得准”。** 增加共享分群 schema 和字段能力目录；拒绝未知条件；支持 tagsAll/tagsAny/tagsNone 与明确 AND/OR 条件组；把关系、成交、活跃维度独立出来；补只读预览及逐客证据；修复分类结果到授权读取的受控投影。继续使用现有资质和标签引擎。

**第二批解决“管得住”。** 以现有客群快照和任务运行作为范围，补动作目录和批量操作记录。先支持筛选、待办、草稿这几种已有基础的动作，再补标签复核与负责人指派。批量写标签需要区分人工标签与模型标签，防止下一次分析把人工决定覆盖。

**第三批解决“唤醒闭环”。** 增加唤醒/初筛等动作目的，将目的传给现有逐客生成器；保留事实校验、模板、授权、审批、限频、原回执和局部重试。批量任务结束输出候选、可联系、需人工、发送、送达、回复等不同数量，不能用命中人数代表发送人数。

不建议先做一个“一键群发”按钮。当前更值得优先补齐的是服务端条件语义、证据投影和范围预览，否则按钮会放大已经确认的误选和状态不明问题。
