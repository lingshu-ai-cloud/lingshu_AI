# ADR：数字员工业务资源准备与回执观察

- 日期：2026-10-23
- 状态：已接受

## 问题

主路由原本同时负责采集、内容生产、发布、客户归因、分层和跟进业务的资源准备及完成证明。正常运行协调、审批预检和人工纠偏都依赖相同的观察结果；继续在路由内扩展容易把租户汇总误当作当前任务证明，或另建执行路径。

## 决策

`createTaskBusinessObservation` 统一观察原有业务证据。按已认证租户查询后，再使用运行/任务范围、不可变托管项目血缘、显式参考及逐账号/逐项回执规则判断完成。租户库存或仪表盘总数只是快照背景，不能替代本任务证据。正常协调、审批与纠偏共用同一实例。

跟进观察继续通过既有端口核对最新有效批次、恢复历史 sending 状态并运行发送预检；观察器不被定义为纯只读函数，也不实现新的发送或结果不明重提逻辑。跟进草稿、实际发送计数和平台回执维持原有含义。

`createTaskBusinessPreparation` 统一采集配置、内容生产、客户分层和跟进草稿的准备编排。原调度器、生产执行、分层/草稿、浏览器和冻结资料能力由主路由以明确类型端口注入；不从领域模块加载整个 HTTP 路由。私有直接准备函数不作为另一个公开入口导出。

执行适配器在每次调用时从既有上下文读取，保留隔离联调作用域，不把某次模拟适配器永久缓存为生产默认值。浏览器模式先保存采集配置与任务引用，再进入原浏览器执行回调；首轮采集、重试和未知结果策略均交由原服务判定，不因拆分额外发送请求。

内容生产和跟进草稿在需要时读取同一运行冻结的企业事实，不能用后续配置替换正在执行的输入。内容项目、知识缺口、客户分群和草稿引用仍先写入原任务，并通过原事件/审计记录反馈。草稿生成不意味着已发送，等待状态不意味着业务已成功。

## 验证与后续

- 三个迁移函数的逻辑正文与起点归一化比较一致。
- 独立行为测试使用显式假端口，覆盖范围证明、回执、浏览器顺序、采集不重提、冻结资料及草稿不发送；原领域和工作流集成继续验证实际 DAG 与恢复链。
- TypeScript、架构 ratchet、迁移清单只读完整性、租户隔离、支持会话只读及生产构建分别检查；均不代替真实供应商或登录后浏览器验收。
- 主路由仍持有执行推进、周计划、批准和配置等职责；后续继续迁移完整边界，不放宽历史预算，不以通过 ratchet 作为结构完成。
