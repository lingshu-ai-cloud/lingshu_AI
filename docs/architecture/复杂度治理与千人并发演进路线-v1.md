# 灵枢系统复杂度治理与千人并发演进路线 v1

> 状态：执行基线稿（当前实现校准版）
> 日期：2026-09-13
> 适用范围：当前 `lingshu-AI` 仓库、198 白标标准版、灵枢内部交付版
> 核心决策：保留 React + Express 的技术主干，先建设有强边界的领域化模块单体；数据、任务、授权和 AI 调用形成可信内核后，再决定是否拆服务。
> 产品范围更新：产品阶段、交互和商业边界以 `docs/product/PRD-198白标数字员工标准版-v2.md` 为准；本期不建设购买、支付或客户自助套餐流程，工作区由灵枢内部标准化开通。
> 状态口径：**已实现**＝代码链路已落地且有对应自动化测试；**部分实现**＝局部纵切可运行但未过该里程碑退出门禁；**目标态**＝本文要求的最终架构；**未验证**＝缺生产同等迁移、故障或容量证据。

## 1. 结论

当前问题不是功能不够，也不是必须立刻换前端或 API 框架，而是产品复杂度已经超过了现有代码和运行时边界：页面、HTTP Controller、领域规则、文件处理、第三方调用和后台任务互相穿透，很多安全与租户约束依赖调用方自觉维持。

治理采用“先封风险、再建边界、随后迁移底座”的顺序：

1. 先阻断未鉴权入口、跨租户和重复外部动作等 P0 风险。
2. 以契约、Repository、应用服务和能力策略为缝，把巨型文件按业务纵切。
3. PostgreSQL 成为唯一业务事实源，对象存储成为唯一媒体源。
4. API 无状态化，所有长任务进入持久队列和独立 Worker。
5. 198 标准版和内部交付版共享同一套领域能力，但由服务端 capability policy 暴露不同产品表面。
6. 最后用 1,200 个并发已登录会话持续 30 分钟的混合负载、故障演练和恢复演练证明系统能力，覆盖 1,000 位以上用户同时使用目标；在这些门禁通过前，不以“可横向扩容”对外承诺。

不采用一次性重写，也不立即微服务化。两者都会在业务规则仍快速变化时放大迁移风险。

### 2.0 技术栈基线

| 层 | 当前 | 结论 |

### 2.2 依赖边界

- `server` 生产代码直接引用多个 `src/lib` 模块，后端依赖前端目录。
- 知识、企业资料、WhatsApp 与风格记忆之间存在运行时循环依赖。
- Studio 内容生产服务反向依赖 HTTP route 中导出的 TTS/媒体能力。
- `shared/contracts/starter198.ts` 已承担 starter 的 Agent、命令、工作区和报价输入合同；其他 legacy 状态、权限和错误结构仍没有全系统统一来源。

### 2.3 数据与租户

- 服务端使用 PocketBase 超级用户能力访问数据；数据层接口没有强制携带 `TenantContext`。
- `tenantId` 与 `tenant_id` 并存，租户过滤主要由每个路由手写。
- PocketBase 通用 Store 已区分合法空结果与服务故障；普通开发和全部生产默认 fail closed，本地 JSON 只在隔离 demo/test 显式 `ENABLE_LOCAL_DEV_FALLBACK=true` 时参与。Studio 等遗留域仍有本地文件事实源，尚待 E3 迁移。
- 渠道和插件的遗留 JSON 配置是全局的，不具备租户归属。

### 2.4 任务与并发

- HTTP、scheduler、publisher、crawler、followup 和数字员工 runtime 在同一 Node 进程启动。
- legacy 多个任务领取锁仍是 `Map`、`Set` 或进程内状态；starter 的 run mutation、发布证据和产品档位切换，以及平台投放任务，已增加数据库 lease，但多记录提交与其余任务尚未统一，直接增加 API 副本仍有重复执行或部分提交风险。
- 长任务、SSE 连接和事件分发仍与单进程生命周期绑定。
- 普通 JSON body 默认已降至 2 MB；鉴权后的 legacy base64/语音兼容入口分别硬限 32/24 MB，并提供流式素材入口。服务增加连接超时、优雅 drain、每进程有界限流和依赖/能力 `/ready`，但边缘分布式限流与媒体全面直传仍未完成。

### 2.5 产品与授权

- starter 专用层已有服务端 profile/capability 与角色命令矩阵；legacy 全系统仍没有统一的服务端能力矩阵。
- `SUBSCRIPTION_ENFORCED` 可关闭，现有门禁只判断订阅是否有效，不区分标准版和内部能力。
- starter legacy boundary 已把客户侧旧业务入口 fail-closed；其他产品面仍必须逐路由证明“页面隐藏不等于权限”，不能把 starter 局部守卫外推为全系统安全边界。
- 支持访问、遗留渠道/插件接口、可恢复密码属于独立 P0 安全问题，必须早于扩容处理。

Starter 纵切中的最新边界已经比上述 legacy 基线更严格：workspace 任务／用量只接受固定 schema 的公开展示字段，四类生产现场按字段白名单生成公开 ID，并清理联系方式、secret、prompt 和 provider payload；`production_site.read` 关闭时，服务端不查询现场存储、不返回现场记录，也不允许下载发布／报价产物。starter 探测豁免只认 `/auth/me` 经管理员校验产生的 `platformAdmin: true`，不能根据订阅计划、邮箱或 browser-read token 推导。browser-read 凭据仍只能用于获准的只读访问，不能绕过 starter legacy boundary。

### 2.6 依赖供应链与产品文件导入

- `pnpm run audit:production` 当前报告 0 项生产依赖漏洞。
- SheetJS 使用官方发布的 vendored `xlsx@0.20.3`；安装前和质量门禁校验来源、包名、版本、LICENSE 与 SHA-256 `8dc73fc3b00203e72d176e85b50938627c7b086e607c682e8d3c22c02bb99fe8`，避免 registry 漂移或本地包被静默替换。
- 产品 CSV/XLS/XLSX 解析校验扩展名与文件签名；XLSX 在解析前检查中央目录，拒绝加密、分卷、ZIP64、越界及超限压缩包。当前上限为 10 MiB 文件、2,048 个 archive entries、64 MiB 总展开量、32 MiB 单项、20 张表、每表 20,000 行／256 列／750,000 个范围单元格、每工作簿 1,000,000 个范围单元格与 8 MiB 文本，并关闭公式、样式、VBA 和依赖解析。
- 完整开发依赖审计仍报告 Electron 33 与其 `extract-zip` 链两项 high；审计建议 Electron 44，跨越 11 个主版本。该迁移必须独立完成桌面运行时、权限、打包、签名、安装／更新／回滚和关键旅程回归，不能运行 `audit fix --force` 后直接发布。生产依赖 audit 0 不能外推成“全部依赖漏洞已清零”。

## 3. 目标架构

```text
浏览器 / 白标域名
        │
        ▼
CDN + Caddy/API Gateway
        │  鉴权、限流、请求体上限、request_id
        ▼
无状态 Express API（可水平扩容）
        │
        ├── identity / tenancy / entitlement
        ├── 灵小枢 orchestration / digital-employee workflow
        │     ├── 灵小图 content role
        │     ├── 灵小量 traffic / publishing role
        │     └── 灵小售 sales / quotation role
        ├── studio content production
        ├── inspiration / crawl
        ├── publishing
        ├── customer engagement
        ├── enterprise knowledge
        └── integrations
        │
        ├── PostgreSQL：业务事实、RLS、事务、outbox、审计、事件重放
        ├── Redis：BullMQ、短期缓存、限流、事件广播
        └── S3/R2/COS：租户媒体对象与预签名上传

事务 outbox ──► BullMQ
                  ├── AI worker pool
                  ├── crawl worker pool
                  ├── media/render worker pool
                  ├── publish worker pool
                  └── follow-up worker pool
                            │
                            ▼
                      第三方模型与平台

PostgreSQL workflow_event ──► SSE gateway ──► 浏览器按 cursor 断线续传

可选 assisted_session：
用户在场控制通道 ──► session broker ──► 单租户／单账号隔离浏览器 Worker
                                   └── 会话级加密临时凭据（硬 TTL 后销毁）
```

四 Agent 是同一工作流聚合内的固定职责，不是四套任意互调的聊天机器人。客户的意图、补充、审批、纠偏和结果查询只进入灵小枢；服务端先持久化派工包，再把有 schema、事实版本、权限快照、成本预算、截止时间和幂等键的任务交给灵小图／灵小量／灵小售。198 只使用版本化标准图，内部交付才能配置高级节点、provider、恢复和接管策略。

### 3.1 模块内固定依赖方向

```text
http adapter ───────────────► application service ─────► domain
                                      ▲
infrastructure adapter ────────────────┘
      （实现 application 定义的 port）

composition root ──► 只负责实例化并装配上述 adapter / service
```

- `http` 只解析、鉴权、调用应用服务和序列化响应。
- `application` 编排用例、事务、幂等和授权，拥有 Repository／队列／provider port，不依赖 Express 或具体基础设施。
- `domain` 包含状态机、规则与纯函数，不依赖数据库、文件或第三方 SDK。
- `infrastructure` 实现 application port；它可以依赖 port 契约，但 application 不得导入具体 infrastructure adapter。
- 禁止任何 domain/application 层导入 `routes`。
- 前后端共享内容只进入 `packages/contracts` 或迁移期的 `shared/contracts`。

### 3.2 产品能力模型

授权不是把平台人员与客户角色相乘，而是先区分互斥的 actor 路径，再在各自路径内全部满足约束：

```text
客户路径 = tenant membership + org_role + product_profile + feature_entitlement + resource_limit

内部路径 = platform_role
        + target-tenant scoped support_grant（scope / reason / expires_at）
        + 目标租户已有 feature_entitlement / resource_limit
        + 客户对高风险动作的有效审批
```

- `platform_role`：`internal_admin | delivery_operator | support_engineer`；仅内部 actor 持有，客户永远为 `null`
- `org_role`：`owner | admin | operator | customer_service | reviewer | viewer`；仅由目标租户 membership 产生，内部人员不会因 support grant 成为租户成员
- `product_profile`：`starter_198 | advanced_customer`；本期由内部标准开通写入，仅表达能力边界，不代表购买或订阅；`internal_delivery` 是平台工作模式，不是客户能力集
- `feature_entitlement`：具体可执行能力，如 `workflow.standard.run`、`publishing.package.generate`、`publishing.assisted_session`、`quotation.calculate`、`studio.ai_video`、`workflow.graph.edit`
- `resource_limit`：席位、账号、产品、生成、渲染、消息、并发任务和存储限制
- `support_grant`：客户批准的作用域、原因、创建人、到期、撤销和审计

两条路径最终都由服务端 fail-closed。`internal_delivery` 永不继承 `advanced_customer`，support grant 也不能扩大目标租户已有 entitlement、资源上限或替代客户审批。

前端 capability manifest 只用于决定展示；每个服务端入口仍独立执行授权。

历史角色迁移采用同一 canonical 映射：租户唯一主 `super_admin → owner`，重复 `super_admin` 进入人工确认后最多映射 `admin`；`admin → admin`、`social_operator → operator`、`customer_service → customer_service`；缺失／非法角色拒绝访问并进入迁移清单，绝不默认提升为 Owner。完整定义以产品 PRD §13.1 为准。

`starter_198` 基础 GA 默认包含发布包生成和确定性报价计算；隔离登录态辅助发布是独立 entitlement，必须逐平台通过安全／法务评审并按次取得用户在场授权，不阻塞发布包基础 GA；官方 API 发布和付费投流是后续 entitlement。报价语言可以由 AI 组织，但金额、阶梯、币种、税运费、MOQ、Incoterm、毛利线和有效期只由版本化规则引擎计算；外部发送与规则外商业承诺始终要求客户审批。

### 3.3 领域边界与写入所有权

目标不是把巨型文件机械切小，而是让一个业务事实只有一个写入所有者：

| 领域模块 | 唯一负责 | 对外合同 | 禁止事项 |
|---|---|---|---|
| identity／tenancy | 身份、membership、租户上下文 | actor、tenant context、role claims | 业务模块自行猜角色或接受客户端 tenantId |
| provisioning／brand | 内部标准开通请求、Owner 邀请、租户品牌快照 | provisioning request、canonical origin、brand snapshot | 把不完整开通暴露给客户，或从未验证 Host 生成身份链接 |
| capability／budget | 固定产品能力、entitlement、资源限额、用量和预算 | capability decision、reservation／settlement | 从产品名、支付状态或 UI 判断权限 |
| orchestration／灵小枢 | Goal、Plan、Run、Task、Decision、handoff | command、`AgentTaskEnvelope`、run event | 直接改内容、发布、报价领域表 |
| content／灵小图 | 内容、素材引用、质检、版本 | content artifact／quality result | 自行发布或直接请求用户决策 |
| traffic／灵小量 | 发布包、辅助会话、发布证据、渠道指标 | publication request／receipt／metric | 无用户批准发布、把包生成算已发布、198 自动花广告费 |
| sales／灵小售 | Inquiry、计价规则、计算、报价、业务结果 | inquiry／quote／outcome event | 让模型计算金额、无审批发送或承诺 |
| evidence／memory | 证据索引、记忆候选、采用／撤销 | `EvidenceEnvelopeV1`、memory event | 把模型推断写成事实或覆盖源记录 |
| platform delivery | 高级配置、诊断、支持授权、接管审计 | support grant、operator command | 成为租户常驻万能管理员或代客户审批 |

建议目录骨架为 `server/modules/<context>/{domain,application,ports,adapters,http}`；组合根负责装配，模块间只通过 application command/query、版本化事件和 `shared/contracts` 通信，禁止跨模块直写 Repository。前端按 `src/features/lingshu-workbench`、facts、publishing、quotation、usage-cost 与 internal-console 纵切，客户壳和内部生产现场不再共享巨型状态容器。

## 4. 分里程碑实施方案

> 工期仅是以 4–6 名工程人员并行的初步估算。是否进入下一里程碑，以退出门禁为准，不以日期为准。
>
> 当前状态：E0、E1、E2、E4、E5 均有不同程度的**部分实现**，E3 未实现，E6 未验证。starter 专用纵切先提供了安全产品壳、固定图、局部 worker、用量与确定性报价能力，但没有改变总体里程碑退出门禁；任何文档、目录、单测或 feature flag 的存在都不能代替生产同等环境证据。

### E0：冻结复杂度与高优先级止血（2–4 天）

目标：建立可信基线，保证后续拆分不会一边治理一边继续恶化。

交付物：

- 固化 `typecheck + build + architecture guard + 安全回归` 门禁。
- 固化生产依赖 audit；vendored 依赖必须校验可追溯来源、SHA-256、包身份和 LICENSE，产品文件解析必须有格式与资源预算。
- 为现有超大文件记录只减不增的行数预算；新生产文件不超过 800 行，后续收紧到 500 行。
- `shared` 禁止反向导入 `src/server`；新 `server/modules` 禁止导入 `routes`。
- 所有非 webhook 遗留入口先阻断匿名访问；全局渠道／插件配置使用精确平台管理员门禁，计费 AI 再由 E1 entitlement、quota、预算和模型 allowlist 收口。
- 支持访问默认关闭，token 有 30 分钟有效期且最大不超过 60 分钟。
- 禁止在新代码保存或返回可恢复密码；历史密码清理由专门迁移执行。
- 明确生产暂时保持单 API 副本；在原子 claim 完成前，自动发布、自动群发保持人工确认。

退出门禁：

- 匿名访问渠道、插件及计费 AI 端点得到 401/403。
- 普通租户无法读取全局配置或触发内部测试接口。
- 过期 support token 必须被拒绝。
- 新增超预算文件或扩大任一债务文件时 CI 失败。
- 当前已知红色测试被登记，不允许用跳过或删除断言伪装通过。
- 生产依赖 audit 为 0；开发依赖残留必须有隔离范围、负责人和升级回归计划，不得把生产 audit 0 宣传为全仓 audit 0。

### E1：请求上下文、统一授权与错误协议（第 1 周）

目标：把租户、安全、固定产品能力和错误从“调用方约定”升级为系统不变量。

交付物：

- 使用可辨识联合类型的 `RequestContext`：客户 actor 携带 `tenantId + userId + orgRole + productProfile`；内部 actor 携带 `platformUserId + platformRole + targetTenantId + supportGrantId`。同一请求不能同时伪装两种 actor，内部路径不能通过填写 `orgRole/productProfile` 获得客户能力。
- `authorize(permission)` 与 `requireEntitlement(capability)` 默认拒绝中间件。
- 所有非公开端点完成 route inventory；公开 webhook 使用独立 router 和验签策略。
- 统一错误结构：

```ts
type ApiError = {
  code: string;
  message: string;
  requestId: string;
  retryable: boolean;
  source?: 'validation' | 'database' | 'queue' | 'provider' | 'policy';
  details?: Record<string, unknown>;
};
```

- 新增 tenant-scoped Repository 门面；业务代码不再直接调用无租户的 `getById/update/delete`。
- 全局 JSON body 降到 1–2 MB；媒体改预签名直传，特例按路由配置。
- IP、账号、租户、能力和模型预算分层限流。

退出门禁：

- 随机 ID 跨租户读、改、删全部返回 404/403。
- `starter_198` 直接调用内部高级 API 全部返回 403。
- 前端不再解析数据库/第三方原始错误。
- 所有响应和日志均可用 request ID 串联。

### E2：领域化模块单体与巨型文件纵切（第 2–4 周）

目标：让每个业务切片能被独立理解、测试和替换。

并行纵切顺序：

1. 抽纯函数、类型和 schema，旧入口保留 re-export。
2. 抽 provider/file/repository adapter。
3. 抽 application service。
4. route 变薄，仅保留 HTTP 适配。
5. 前端用 feature 目录、reducer/状态机和 query cache 替代散落状态。
6. 用 TypeScript AST／依赖图工具取代初版正则 import 扫描，固定模块方向、循环依赖和禁止边；正则仅保留为快速补充检查。

优先切片：

| 原文件 | 第一刀 | 后续目标 |
|---|---|---|
| `AiCreateStudio.tsx` | timeline、字幕、素材匹配、脚本规范化纯逻辑 | `features/studio/{domain,api,state,components}`；主容器低于 500 行 |
| `studio.ts` | TTS、material、render、project、publishing 适配器 | 每组薄 Controller + application service；单文件低于 500 行 |
| `videos.ts` | crawl、analysis、media、thumbnail、ops | 每个能力独立 router/service/repository |
| `digitalEmployees.ts` | command/query、approval、event/SSE、workflow repository | 明确 workflow aggregate 与状态迁移器 |
| `DigitalEmployeePage.tsx` | 客户 simple shell 与 internal console 分离 | 客户只看到今天/待决策/成果 |

退出门禁：

- 运行时循环依赖为 0。
- `server` 生产代码对 `src` 的 import 为 0。
- Controller 不包含领域判断、磁盘读写或 provider 调用。
- 新模块单文件不超过 500 行；分支只允许债务预算下降。
- 核心工作流 characterization tests 与拆分前结果一致。

### E3：PostgreSQL 唯一事实源（第 3–6 周，可与 E2 后半并行）

目标：消除 PocketBase 超级用户 + 本地 JSON 双事实源，形成可证明的租户隔离和事务边界。

交付物：

- 所有业务表统一 `tenant_id NOT NULL`，核心关系有 FK、复合唯一键和状态约束。
- PostgreSQL RLS 作为纵深防御；每个事务设置租户上下文。
- 工作流、capability／entitlement、用量、归因、审批、审计和 outbox 使用事务；遗留 subscription 字段只做可审计迁移、冻结与退役，不在 E3 建设 SaaS 订阅域。
- 建立幂等键：`tenant_id + capability + idempotency_key`。
- 迁移流程：schema → 回填 → 影子读比对 → 限量切读 → 切写 → 停止双写 → 清理旧源。
- 本地 JSON 仅保留 fixture，不参与生产读写和降级。
- 媒体统一到对象存储，元数据和对象 key 强制租户归属。

退出门禁：

- 删除容器本地数据并重启后业务数据不丢失。
- RLS 直接 SQL 测试无法跨租户访问。
- 影子读关键表差异为 0；迁移可回滚且完成恢复演练。
- PocketBase/JSON 退出业务事实源后才允许删除兼容代码。

### E4：持久队列、独立 Worker 与统一任务中心（第 5–8 周）

目标：API 可横向扩展，长任务可恢复且任何外部副作用只执行一次。

交付物：

- Redis + BullMQ；API 只做校验、事务落库和 enqueue。
- AI、crawl、media/render、publish、follow-up 分 Worker pool 和并发预算。
- 可选登录态发布使用独立 session broker、用户在场控制通道和每次独占的隔离浏览器 Worker；临时 Cookie／token 不进入业务库、队列 payload、outbox、事件、备份、日志或模型，完成／取消／硬 TTL 后销毁数据密钥。
- `workflow_run → task → attempt → event → approval` 持久状态机。
- 原子 claim/CAS、租约、心跳、指数退避、超时、取消、DLQ。
- 外部动作采用事务 outbox、provider receipt、inbox 去重与未知结果对账。
- 统一事件序号；SSE 通过 cursor 断线续传，Redis 只广播，PostgreSQL 保存可重放事件。
- SIGTERM 停止接单、停止续租、drain 与优雅退出。

退出门禁：

- 2 个以上 API 副本不启动任何后台扫描器。
- 50–100 个 Worker 并发抢同一任务只产生一次业务效果；若 provider 结果未知，先用幂等键／receipt 主动对账，绝不盲目重试。
- 杀死 Worker 后任务在租约到期后恢复。
- 已获得 provider receipt 的发布/发送不会重发。
- 页面关闭、断网、重新登录后仍可从同一任务断点恢复。

### E5：AI 运行平台、证据协议与产品分层（第 7–10 周）

目标：AI 的质量、成本和执行边界均可观测、可版本化、可按产品能力控制。

交付物：

- 统一 AI Gateway：`capability + model route + prompt/version + input/output schema + timeout/retry/fallback`。
- 结构化输出由 schema 校验，不再在各路由用正则提取 JSON。
- 统一成本账本：预占、结算、释放；维度包括 tenant/run/task/capability/model。
- Prompt 回归集、离线 eval、线上质量采样、脱敏 trace。
- AI 结论统一使用产品 PRD §9 定义的 canonical `EvidenceEnvelopeV1`；工程实现放入 `shared/contracts`，其他模块和文档不得复制一份字段缩水的同名类型。

- `starter_198` 固定开放“灵小枢 + 灵小图／灵小量／灵小售”四 Agent 团队，但只允许用户操作灵小枢，且工作图模板化、成本可控、关键对外动作默认人工确认。
- `internal_delivery` 才开放 Agent／任务图编辑、模型/provider、批量生产、诊断与人工接管。

退出门禁：

- 每次 AI 调用均可追溯 prompt 版本、模型、token、成本、结果 schema 和证据来源。
- 超预算调用在进入 provider 前被拒绝或排队。
- 198 用户无法通过前端、API 或重放旧请求触达内部能力。
- 质量回归集低于阈值时禁止发布。

### E6：千人并发与持续运行门禁（第 9–12 周及持续）

目标：用容量证据而不是单机经验确认生产承载力。

将“1,000 位以上用户同时使用”的目标拆成四类分别建模：

1. 登录后普通读取与首页刷新。
2. SSE 长连接与事件重放。
3. 上传/下载和对象存储流量。
4. AI、渲染、采集、发布等异步任务入队与 Worker 消费。

最低验收指标：

| 场景 | 门槛 |
|---|---|
| 混合并发基线 | 1,200 个已登录会话持续 ≥ 30 分钟，覆盖普通读写、SSE、上传、入队、发布／报价与内部诊断 |
| 普通读 API | 上述负载下 p95 ≤ 500 ms、p99 ≤ 1.5 s，错误率 < 1%；p95 < 300 ms 作为优化目标而非 GA 硬门槛 |
| 普通写/入队 | p95 ≤ 800 ms，错误率 < 1% |
| SSE | 1,200 个工作台同时保持连接；≥120 events/s 下断线重连按 cursor 补齐，无跨租户事件 |
| 原子任务领取 | 50–100 并发抢占只产生一次业务效果；未知 provider 结果进入对账，不盲重试 |
| Worker 故障 | lease 到期后恢复，完成动作不重复 |
| 租户隔离 | 随机跨租户测试 100% 拒绝，RLS 测试同样拒绝 |
| 备份恢复 | 校验 checksum，在隔离环境恢复并通过行数、对象清单和业务冒烟 |
| 资源余量 | 峰值 CPU p95 ≤65%、内存及数据库／Redis 池峰值 ≤70%，任一队列不得持续增长 |
| 耐久与故障 | ≥4 小时 soak，季度 24 小时；覆盖滚动部署、Worker/Redis/PostgreSQL 故障与恢复 |

唯一可执行负载定义以产品 PRD §15.2 的版本化 `load_profile_198_ga_v1` 为准，包含 RPS、文件尺寸、数据规模、租户分布、provider 延迟／故障模型和突发流量；本文与 PRD 不允许各自维护两套数字。可观测性至少覆盖：请求量/延迟/错误、SSE 连接／事件／补发、队列深度/等待/重试/DLQ、任务成功率、发布与发送回执、数据库连接池、Redis、对象存储、AI token/成本/质量、租户级配额和 SLO。

## 6. 工程质量红线

- 禁止新的全局可变业务状态、运行期 JSON 事实源和进程内分布式锁。
- 禁止 route-to-route、server-to-src 和 domain-to-infrastructure 反向依赖。
- 禁止以 `any`、空 `catch`、返回空数组或假成功掩盖数据源故障。
- 禁止在日志、API、后台页面、备份中出现密码、token、secret 或未脱敏客户消息。
- 禁止没有幂等键的发布、发送、扣费、生成和订单状态变更。
- 禁止仅靠 UI 隐藏控制固定产品能力和内部能力。
- 禁止全局大请求体；媒体不穿过 JSON/base64 主链路。
- 禁止解析未校验类型／签名或无展开量、行列、单元格和文本预算的用户文件；vendored 依赖缺 SHA-256／版本／LICENSE 任一校验即失败。
- 单元测试覆盖规则，集成测试覆盖租户/事务/队列，契约测试覆盖 provider，端到端测试覆盖关键旅程；源码正则测试只能作为补充。
- 任一安全、迁移、恢复、质量或 DLQ 门禁失败时禁止发布。

## 7. 当前已落地范围与真实边界

当前工作区除 E0 守卫外，也完成了若干 starter 专用 E1/E2/E4/E5 纵切。下列项目按“代码已落地”描述，不等同于对应里程碑退出门禁全部通过：

- 将一组被服务端引用的纯领域契约迁入 `shared/contracts`，旧前端路径保留兼容 re-export。

## 8. 发布、回滚与决策机制

每个里程碑采用同一发布模板：

1. 在隔离环境运行迁移、测试和基线压测。
2. 对内部租户开启 feature flag，观察错误、队列、成本和数据差异。
3. 对少量测试租户灰度，保留旧读路径和可逆开关。
4. 达到门禁后扩大范围；任何跨租户、重复外部动作、数据不一致立即回滚。
5. 数据切换只回滚应用读写方向，不执行破坏性反向迁移；以备份和 forward fix 恢复。
6. 里程碑完成后删除临时双写、旧锁、旧路由和过期 feature flag，避免“迁移脚手架”变成新债务。

需要形成 ADR 的关键决定：租户上下文与 RLS、能力模型、工作流状态机、outbox/idempotency、对象 key 规范、AI evidence envelope、数据迁移切换点和 SLO。
