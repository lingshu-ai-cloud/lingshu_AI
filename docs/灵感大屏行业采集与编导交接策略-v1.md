## 1. 产品定位

灵感大屏是供人工和 AI 共同浏览、筛选、理解和引用的轻量灵感池，不承担脚本编辑、分镜生产、素材编排、批量裂变或成片制作。

灵感大屏只维护一种核心对象：`InspirationItem`。每条灵感包含三层信息，但字段必须允许“平台没有返回”，不能为了卡片完整而推断或补写：

1. **原始内容**：可播放或可预览的公开视频／图片、来源链接、平台、内容 ID，以及数据源实际返回的作者、发布时间和公开指标。每个字段同时保存 `value`、`source` 和 `verificationStatus`。作者或发布时间没有返回时显示“暂未获取”，不交给模型猜测。
2. **灵感解读**：内容标签、钩子、结构、证明方式和适用方向。每项区分可观察事实与模型推断，并记录分析版本、字段置信度和是否需要复核。
3. **使用关系**：收藏状态、关联任务、系统生成的使用记录和一条可选用户备注。首期不建设复杂的灵感集管理体系。

“权利状态”不是平台元数据的同义词。系统默认将外部平台内容标为 `reference_only`；只有用户自有内容、明确授权文件或可核验的平台许可，才能改成 `owned`、`licensed` 或其他更宽的使用范围。平台公开可见、采集成功或 YouTube 标为 Creative Commons，都不能自动推导出“可下载、可商用或可二创”。

用户或编导 Agent 选择一条灵感后，系统将最小必要信息交给编导生产页面。脚本、分镜、素材匹配和成片生产在后续页面完成。

全文中的“灵感大屏”和“灵感中心”指同一个产品模块：前者是项目讨论名称，后者是建议的前端名称。由于内容已覆盖行业起量、对标账号和创新参考，前端不再使用“爆款灵感”作为总页面名称。用户前端看到的是“发现范围”；后台版本化语义对象是 `MarketKeywordSet`；定时任务保存的是“采集计划／执行快照”。后文提到关键词策略时，指 `MarketKeywordSet` 的内部能力，不是另一个前端配置入口。

```text
市场词簇与采集策略
  → 候选内容入库
  → 低成本筛选与排序
  → 按需深度分析
  → 人工或 AI 选择灵感
  → InspirationHandoff
  → 编导 Agent 形成 DirectorBrief
```

## 2. 先确定数据能不能稳定获得

结合当前代码与平台公开接口，首期不能把四个平台写成同样可靠的“API 数据源”。

本文中的 **Actor** 专指 **Apify Actor**：部署并运行在 Apify 平台上的一个具体采集程序，不是编导 Agent、内容 Agent 或数字员工。每个 Actor 都有自己的输入 schema、支持的平台对象、输出字段、运行限制和计费方式。例如当前代码默认使用 `clockworks/tiktok-scraper`、`apify/instagram-scraper`、`apify/facebook-posts-scraper`，视频下载还可能使用独立的 downloader Actor。账号／视频 Actor 通常负责主页、帖子和公开指标；如果需要评论正文，往往要选择支持评论输出的模式或另外的评论 Actor。评论 Actor 尚未在本文中确定，因此不能提前承诺字段和成本。

| 来源 | 当前采集路径 | 能稳定承诺的字段 | 不能承诺的字段／能力 | 成本与首期结论 |
| --- | --- | --- | --- | --- |
| YouTube | Apify YouTube Actor | Actor 实际返回的视频 ID、链接、标题、频道、发布时间、封面与公开指标 | 字段完整率取决于 Actor 输出；公开视频不等于获得下载、商用或二创权 | 适合关键词、账号和明确链接采集；按 Actor 计费模型设置上限 |
| TikTok | Apify TikTok Actor | Actor 实际返回的链接、内容 ID、作者、描述、发布时间与公开指标 | 全站覆盖、历史深度和持续可用性不能承诺 | 标成 `best_effort`，使用结果上限、预算和失败熔断 |
| Instagram | Apify Instagram Actor | 公开内容采集成功时的链接、作者、发布时间、封面／媒体 URL 与部分指标 | 临时媒体 URL 可能过期；非公开内容、字段完整率与持续可用性不能承诺 | 关键词、Hashtag、账号和 URL 以所选 Actor 的真实输入能力为准 |
| Facebook | Apify Facebook Actor | 公开页面／帖子采集成功时的链接、作者／页面、发布时间、媒体与互动字段 | 关键词覆盖、历史深度、私有内容与字段完整率不能承诺 | 优先已确认账号和链接；关键词采集以 Actor 的真实搜索能力为准 |

Apify 当前公开定价同时存在按结果和按计算资源两种模式，因此产品不能写死“每条固定成本”。每次运行必须同时设置 `maxResults`、`maxRunCost`、超时、租户日／月预算和熔断条件。采集阶段只保存页面展示与排序需要的元数据；L1 优先使用来源封面、预览和文本。完整视频下载及 L2／L3 分析只发生在用户打开、收藏、任务召回，或候选满足已批准的高表现／创新升级规则且仍在预算内时。这样才能控制成本，而不是依赖一个看似便宜的单价。

每个字段采用以下状态：

```ts
type SourceFieldStatus = 'verified_from_source' | 'missing' | 'expired';

interface SourceField<T> {
  value?: T;
  status: SourceFieldStatus;
  provider: 'apify' | 'user';
  fetchedAt: string;
}
```

主题、风格等模型解读使用独立的分析字段，并记录 `model_inferred`、模型版本和置信度；作者、发布时间、互动量、许可和权利状态等来源字段中不允许出现模型推断。

## 3. 行业模板改为企业角色 × 目标市场 × 搜索意图

上一版的七套行业采集重点主要来自产品设计推演，缺少真实查询数据与客户采用数据，不能作为默认规则上线。它们应删除为系统预设；未来若由客户搜索词、收藏／采用漏斗和成片结果验证，再沉淀为可选模板。

SEO 与 GEO 产品更接近可复用的方法是：从少量种子词、网站或已有关键词开始，按国家和语言扩词，结合竞品缺口与搜索意图聚类，再由用户选择要持续跟踪的主题。GEO 在此基础上把词簇改写成特定角色会提出的完整问题，并按国家、语言、品牌和竞品观察回答与引用差异。

因此，灵感池使用 `MarketKeywordSet`，而不是先写死 `IndustryInspirationProfile`：

| 维度 | 数据来源 | 示例 | 是否允许模型生成 |
| --- | --- | --- | --- |
| 企业事实 | 商品库、企业官网、用户填写、知识库 | 品类、型号、材料、工艺、认证 | 只能改写，不能发明 |
| 企业角色 | 用户选择 | 工厂、品牌方、进口商、经销商、零售商 | 否 |
| 沟通对象 | 用户选择或任务继承 | 品牌采购、进口商、经销商、终端消费者 | 可推荐，需可见 |
| 目标市场 | 用户选择 | 国家／地区、语言、本地称呼、币种 | 可翻译，需保留原词 |
| 搜索意图 | 规则与搜索结果验证 | 信息、商业调研、交易、导航／售后 | 可分类，保留置信度 |
| 真实需求词 | 站内搜索、广告搜索词、询盘、客服、CRM、评论 | 客户原话、常见问题、异议 | 只做清洗和聚类 |
| 竞品差距 | 用户确认的竞品域名／账号与搜索结果 | 对方覆盖而本方缺失的主题 | 可发现，需显示来源 |
| 表达词 | 高表现内容反推 | review、comparison、how to、test、factory tour | 可扩展，需用样本验证 |

最终查询不是简单拼接所有词，而是保存为可追溯组合：

```text
产品实体／问题
  × 企业角色与沟通对象
  × 市场、语言和本地叫法
  × 搜索意图
  × 内容表达形式
```

## 4. 四类经营关系如何使用关键词

这里需要区分“企业是谁”和“这条内容说给谁听”。同一家工厂既可能向进口商招商，也可能替品牌客户展示 OEM 能力；海外经销商既会向上游找货，也会向本地消费者卖货。行业名称本身不足以决定关键词。

| 经营关系 | 首批种子事实 | 面向该对象的需求／意图词 | 灵感检索重点 |
| --- | --- | --- | --- |
| 工厂 → 海外进口商／经销商 | 产品、材料、工艺、产能、交期、MOQ、认证、目标国家 | supplier、manufacturer、wholesale、lead time、quality control、compliance、distributor | 采购顾虑、能力证明、工厂与质检证据、询盘转化 |
| 工厂 → 海外品牌／自有品牌客户 | 可定制项、OEM／ODM、打样、包装、私标、知识产权边界 | private label、custom、OEM、ODM、sample、packaging、certification | 定制流程、打样前后、设计到交付、案例证据 |
| 品牌方 → 终端消费者 | 品类、差异卖点、使用场景、价格带、渠道、本地表达 | 问题、场景、benefit、review、comparison、how to、best、price | 真实使用、评测比较、教程、UGC、购买顾虑 |
| 海外经销商 → 本地终端消费者／零售商 | 本地库存、价格、门店／配送、售后、适配性、代理品类 | in stock、near me、local delivery、dealer、price、support、for [use case] | 本地场景、库存与服务、到店／下单、消费者问题 |

表内词只是词族标签，不是系统直接投放的固定英文词。真正的词应按以下优先级产生：

1. 先读取商品、官网、知识库和用户指定市场，形成可核验的 3—5 个种子主题。
2. 加入客户真实表达：询盘、客服、CRM、站内搜索、广告搜索词和公开评论。
3. 加入用户确认的竞品账号／域名，寻找其覆盖而本方缺失的主题。
4. 按目标国家和语言扩展同义词、长尾问题和本地叫法；同一句查询在不同国家分别保存。
5. 按信息、商业调研、交易和售后意图聚类，去掉无关、重复和不可验证词。
6. 先展示少量检索样本与命中原因，由用户删除、保留或补充；只有被保存的词簇才进入定期采集。
7. 根据“被打开 → 收藏 → 加入任务 → 编导采用 → 成片表现”调整词簇，不根据模型偏好自动改行业策略。

GEO 词集使用同一套事实与角色，只把高价值词簇写成自然问题。例如工厂面向德国品牌采购时，可形成“哪些 [品类] 制造商支持 [认证] 和小批量私标？”；经销商面向本地消费者时，可形成“在 [城市／国家]，哪种 [品类] 适合 [场景]？”方括号内容必须来自企业与市场配置。GEO 问题用于发现被 AI 引用的来源和竞品内容，不直接当作视频标题。

## 5. 采集任务如何形成

采集任务有四类触发来源：

1. **基础词簇供给**：维持已保存的企业角色、目标市场和核心主题的基本覆盖。
2. **用户主动配置**：用户添加关键词、账号、链接、产品或排除条件后产生。
3. **生产任务补充**：编导 Agent 接到具体任务后，发现现有灵感不足，提出定向检索需求。
4. **创新探索补充**：从相邻行业／场景，或已采内容与评论中发现的新问题、新场景出发，寻找可迁移表达。

每个 `InspirationCollectionRun` 至少记录：

| 字段 | 含义 |
| --- | --- |
| `keywordSetId` | 企业角色、沟通对象、市场与词簇版本 |
| `discoveryMode` | 行业起量、对标账号或创新参考；一次运行可包含多种模式，但分别统计 |
| `innovationBriefId` | 创新探索运行可选；指向相邻场景或内容／评论信号形成的探索命题 |
| `triggerType` | 基础供给、用户配置或生产任务补充 |
| `productionContext` | 可选的产品、受众、市场和内容目标 |
| `sourceScope` | 平台、账号、广告库、关键词或用户提供链接 |
| `queryFamilies` | 种子事实、真实需求词、角色、意图与语言变体，不只保存最终字符串 |
| `queryEvidence` | 每个词来自商品、官网、询盘、竞品、用户输入或模型扩展 |
| `rightsPolicy` | 允许保存链接、分析、下载或二创的范围 |
| `stopReason` | 正常完成、重复率过高、无有效结果、额度受限或来源失败 |
| `qualityStats` | 召回量、去重后数量、有效候选、收藏／采用情况和分析成本 |

系统先提供检索预览和少量样本。用户保存词簇后才进入持续运行；Agent 为某个生产任务临时补充的词必须在运行记录中可见，不得静默写回企业长期策略。

## 6. 创新采集与候选内容处理

### 6.1 创新型素材的两条采集路径

创新型素材是灵感池的补充供给，用来找到行业爆款和长期对标账号之外的真实参考。首期不把它扩展成泛创意搜索，也不单独追逐所谓“全网最新形式”，只保留两条与现有采集模式重合较低的路径。

#### 路径一：相邻行业与相邻场景迁移

这一条路径保留当前业务问题、目标对象或证明目标，同时放宽具体产品和行业，从相邻行业、相似使用场景中寻找可以迁移的表达方式。

```text
当前产品／任务
  → 提取用户问题、使用场景或证明目标
  → 寻找具有相同问题／场景／证明目标的相邻行业
  → 通过 Apify 按平台关键词、Hashtag、账号或明确链接采集
  → 判断表达方式能否迁移到当前产品
```

可以扩展的维度包括：

- 相同痛点，不同产品，例如干燥、密封、耐用、便携、清洁或快速操作；
- 相同场景，不同行业，例如家庭、通勤、户外、门店、仓库、工厂或专业工作环境；
- 相同证明目标，不同品类，例如材料对比、压力测试、过程展示、前后变化或质量检查；
- 相同沟通对象，不同供应关系，例如面向采购商证明工艺、认证、交付或定制能力。

查询不能只使用宽泛的 `creative`、`viral` 或 `innovative`。每组查询至少保留一个业务锚点，再叠加一个相邻行业或场景表达：

```text
业务锚点 × 相邻行业／场景 × 内容表达形式
```

例如，护肤产品想补充“质地与吸收”的表现方式，可以从食品质地、清洁产品溶解过程或材料微距展示中寻找形式参考；B2B 工厂想补充“质量证明”，可以从电子、包装或机械行业的检测过程寻找拍摄和叙事方法。编导 Agent 只能迁移结构、镜头作用、证明顺序和表达形式，不能迁移对方产品结论、参数或认证。

#### 路径二：从内容与评论中发现新问题、新场景

这一条路径使用已经通过 Apify 取得的标题、描述、字幕、评论正文和公开互动，发现现有关键词库没有覆盖的真实表达。只有取得评论正文时才能分析具体问题；只有评论总数时不能生成新的需求场景。

系统重点识别：

- 新的使用场景和使用人群；
- 消费者反复出现的痛点、疑问和比较对象；
- 采购商关于 MOQ、样品、规格、认证、定制、交期、代理和运输的问题；
- 用户对现有内容的误解、反对意见和未被回答的问题；
- 同一问题在不同国家、语言和平台上的本地表达。

发现信号后不直接把评论改写成创意，而是形成一个可追溯的 `InnovationSignal`：

```ts
interface InnovationSignal {
  sourceType: 'content' | 'comment';
  sourceId: string;
  sourceUrl: string;
  signalType: 'new_problem' | 'new_scene' | 'new_audience' | 'new_objection' | 'new_proof_need';
  observedText: string;
  targetMarket?: string;
  confidence: number;
  occurrenceCount: number;
}
```

编导 Agent 将多个相近信号合并成探索命题，例如“如何表现运输中不会泄漏”“如何向小批量买家展示定制流程”或“如何在干燥气候下展示使用过程”。采集执行器再使用该命题的产品词、场景词、问题词和本地表达调用 Apify，寻找真实存在的参考内容。

#### 创新素材的入池条件

创新素材不要求具有行业头部播放量，但必须同时满足：

1. Apify 返回可访问的真实平台内容 ID 或来源 URL；
2. 与一个已确认的用户问题、场景、目标对象或证明目标有关；
3. 相比当前同行爆款与对标账号内容，能够补充新的场景或表达方式；
4. 编导 Agent 能明确说明可以借鉴什么、必须替换什么以及生产需要什么；
5. 不虚构产品效果、参数、认证、询盘或成交结果。

创新参考建议占每日有效入池素材的 10%—20%。这是跨行业／跨场景探索预算，不要求每天机械凑满；没有通过上述条件的内容时允许少入库。其余 80%—90% 留给行业起量和对标账号增量，两者的具体比例根据用户画像和实际有效率调整。

灵感卡片只增加三个轻量字段：

- `发现的新场景／问题`；
- `可借鉴的表达方式`；
- `迁移到当前产品时必须替换的内容`。

用户仍在同一个灵感池中浏览，通过“创新参考”筛选查看，不新增独立重页面。用户选择后，系统按照现有 `InspirationHandoff` 交给编导生产。

### 6.2 第一阶段：建立可浏览灵感条目

所有候选先完成确定性处理：

- 来源、平台、内容 ID、链接和采集时间；作者、发布时间、封面和指标仅在数据源确实返回时写入；
- 标题、描述、时长、画幅、封面及平台允许获得的公开指标；
- 精确文件去重、来源链接去重和相似视频聚类；
- 数据可访问性，以及由规则或授权证据决定的分析、下载与二创边界；
- 与 `MarketKeywordSet`、产品、任务和词族的命中关系。

这一阶段完成后即可进入灵感池浏览，不要求等待全片深度分析。页面需明确显示“待解读”“快速解读完成”或“深度分析完成”。

### 6.3 第二阶段：低成本快速解读

当前仓库配置的视频分析提供方是 Qwen。首期沿用现有调用与数据结构，对通过基础质量检查的视频执行当前链路能够完成的语音／画面理解和粗标签；缺失的 ASR、OCR 或镜头信息直接标记缺失，不为了形成完整解读另建一套重型分析系统。快速解读判断：

- 内容实际在讲什么，与行业或任务是否相关；
- 开头、产品、人物、场景、证明和 CTA 是否可识别；
- 是同行事实参考、相邻场景参考还是跨行业表达参考；
- 是否存在重复、低清、信息缺失、违规或无法使用的问题；
- 是否值得进入更昂贵的策略或逐镜分析。

每项输出携带 `evidenceType`（平台元数据、画面／声音观察或模型推断）、`confidence` 和 `needsReview`。快速解读不输出精确的动作、镜头连续性或生产指令，也不能据此直接生成高保真裂变脚本。

### 6.4 第三阶段：按需策略分析与精确分析

进入策略分析的条件包括：用户打开详情或收藏、编导任务召回、表现证据较强、内容新颖且可迁移，或者快速分析不能支持判断。

策略分析提取：

- 钩子类型与前十秒组织；
- 信息、卖点和证明的出现顺序；
- 内容节奏、情绪推进和 CTA；
- 适合的行业、产品、受众和经营目标；
- 需要的真实素材、人物、场景与制作难度；
- 可以迁移、必须替换和不可迁移的内容。

只有准备进入具体生产、需要逐镜参考的视频，才执行连续时间线的精确分析。精确分析必须区分：

- `observedFacts`：画面和声音中确实存在的事实；
- `inferredIntent`：模型对创作目的的推断及置信度；
- `causalGap`：跳剪或缺失导致无法确认的过程。

精确分析还应记录镜头作用、环境、景别、运镜、角度、构图、动作起止状态、空间连续性、字幕、对白、环境声、音乐、音效和转场。不得补写听不清的台词、未出现的动作、品牌、价格、型号、认证或产品效果。

## 7. 什么样的灵感可以交给编导

“已经爬到”不等于“可以生产”。交接分为三个等级：

| 等级 | 条件 | 编导可以怎样使用 |
| --- | --- | --- |
| `discovery_reference` | 元数据与快速解读完成，相关性基本可信 | 用于选题发散和查找更多参考，不直接生成逐镜导演方案 |
| `strategy_reference` | 策略分析完成，迁移边界和适用方向明确 | 用于选择钩子、结构、证明顺序、节奏和 CTA |
| `production_reference` | 连续逐镜分析通过校验，来源和权利边界清楚 | 用于形成可执行分镜目标，但仍需替换参考中的产品事实和独特表达 |

出现以下任一情况，不能作为 `production_reference`：

- 时间线缺失或重叠，关键镜头未被解析；
- ASR、OCR、产品身份或关键动作置信度不足且未标记复核；
- 参考中的品牌、参数、认证、价格或效果无法验证；
- 视频只有高播放表象，没有可识别的结构或证明方式；
- 来源失效，或版权／分析／二创权限不清；
- 需要照搬原台词、人物、案例或独特表达才能成立。

这类内容仍可留在灵感池供人工浏览，但页面和 API 必须准确标注它能被如何使用。

## 8. 交给编导 Agent 的最小契约

灵感大屏不生成 `DirectorBrief`，只生成轻量的 `InspirationHandoff`：

```ts
interface InspirationHandoff {
  inspirationId: string;
  analysisId: string;
  analysisVersion: number;
  readiness: 'discovery_reference' | 'strategy_reference' | 'production_reference';
  source: {
    platform: string;
    sourceUrl: string;
    author?: string;
    publishedAt?: string;
  };
  taskContext: {
    videoTaskId?: string;
    productId?: string;
    targetMarket?: string;
    targetAudience?: string;
    userNote?: string;
  };
  whySelected: string[];
  reusableLogic: {
    hookTypes: string[];
    revealOrder: string[];
    proofPlacement: string[];
    pacing: string;
    emotionalProgression: string;
    ctaPosition: string;
  };
  adaptationBoundary: {
    reusable: string[];
    mustReplace: string[];
    prohibited: string[];
  };
  productionImplications: {
    requiredEvidence: string[];
    likelyAssetNeeds: string[];
    difficulty?: 'low' | 'medium' | 'high';
    risks: string[];
  };
  evidenceRefs: Array<{
    startTime?: number;
    endTime?: number;
    description: string;
    confidence: number;
    needsReview: boolean;
  }>;
  rights: {
    mayAnalyze: boolean;
    mayUseOriginalMedia: boolean;
    mayAdapt: boolean;
    note?: string;
  };
}
```

页面不需要把所有字段都展开给普通用户。用户主要看到：为什么推荐、可以借鉴什么、需要替换什么、制作可能需要什么，以及“开始借鉴”。结构化字段主要用于 Agent 交接和追溯。

## 9. 编导 Agent 接到灵感后的推进方式

编导 Agent 不能把 `InspirationHandoff` 直接转换成仿制脚本。它需要完成以下步骤：

1. 读取经营任务、产品事实、受众、平台、时长、预算和素材能力。
2. 判断所选灵感与当前任务是否真正适配；不适配时说明原因并检索替代灵感。
3. 只保留参考中的钩子类型、揭示顺序、证明位置、节奏、情绪推进和 CTA 位置。
4. 将品牌、产品、台词、人物、案例、价格、参数、认证和独特表达替换为经过验证的企业信息。
5. 先产出视频层方案：选题、叙事结构、核心卖点、事实依据、CTA 和总时长。
6. 再产出分镜目标：每镜作用、必须证据、理想视觉、动作、声音、连续性、允许变化和验收条件。
7. 将 `DirectorBrief` 交给内容 Agent，由内容 Agent 决定具体素材片段和技术实现。

如果灵感只达到 `discovery_reference`，编导只能将其用于选题发散；如果达到 `strategy_reference`，可以复用结构；只有达到 `production_reference`，才可以读取精确镜头证据辅助分镜设计。

## 10. 多条灵感如何共同进入一个任务

一个视频任务可以引用多条灵感，但每条必须标明用途，避免把多个视频机械拼接：

| 引用角色 | 示例 |
| --- | --- |
| `primary_structure` | 使用 A 的钩子与整体信息顺序 |
| `proof_reference` | 使用 B 的检测证明展示方式 |
| `visual_rhythm` | 使用 C 的镜头长度和转场节奏 |
| `cta_reference` | 使用 D 的询盘收尾位置和动作 |

同一角色默认只有一个主参考；其他参考作为补充。参考之间发生冲突时，编导以经营目标、产品事实和当前素材条件为准，不能简单取并集。

## 11. 人工动线与 Agent 自动动线

### 11.1 人工选择

```text
浏览／搜索灵感
  → 卡片直接收藏，或打开现有详情
  → 查看来源字段状态、推荐理由与分析可信度
  → 点击“用于创作”
  → 选择已有／新任务，可选填写一句备注
  → 开始借鉴
  → 进入编导生产页面
```

页面只增加三类轻量状态：来源信息旁的“已获取／暂未获取”，统一的“仅供参考”权利徽标，以及“AI 解读／待复核”状态。收藏是卡片上的单击开关；任务关系和备注放在“用于创作”的小弹层中；使用记录由系统自动生成，在详情中只读展示。首期不增加独立灵感集页面、复杂批量编排或多步表单。

如果分析等级不足，用户仍可先关联任务；系统在后台升级分析，完成后更新任务。只有升级失败或关键证据需人工判断时才要求用户处理。

### 11.2 Agent 自动选择

编导 Agent 根据任务检索灵感池时，必须返回候选及理由，至少包括行业／任务相关性、可迁移逻辑、证据强度、分析等级、权利状态和与近期任务的重复情况。

默认由 Agent 自动选择少量主参考并继续生产；人工可以在生产页面查看、更换、添加或移除参考。用户修改参考后形成新的 `DirectorBrief` 版本，已经开始的下游制作按影响范围更新。

## 12. 运行反馈如何改进采集

采集策略不直接用播放量自我强化，而是使用完整漏斗：

```text
被采集
  → 进入有效候选
  → 被打开／收藏
  → 被加入任务
  → 被编导采用
  → 形成样片／成片
  → 获得自有成片公开表现或人工采用反馈
```

每个 `MarketKeywordSet` 应按企业角色、沟通对象、市场、词簇、账号、平台和表达标签统计漏斗表现。可以据此提高有效来源的优先级、降低长期无效或重复来源，并发现当前灵感池缺少哪种证明方式或表达类型。

外部平台表现与企业自己发布后的公开表现必须分别保存。外部跑量只能说明值得研究；企业自有成片的公开表现和人工采用反馈，才能继续验证该表达是否适合自身产品、账号和目标市场。当前灵感采集不读取订单、GMV 或实时成交。

## 13. 首期落地建议

首期不需要同时覆盖所有行业和所有深度能力。建议：

1. 选择一种真实经营关系，例如“工厂 → 海外品牌采购”，用商品事实、一个目标市场和一组真实询盘建立首个 `MarketKeywordSet`。
2. 为四个平台接入的 Apify Actor 建立能力与字段映射，逐个平台明确支持的查询类型、字段完整率、成本和失效处理。
3. 先实现元数据状态、去重、Qwen 快速解读和人工浏览，确保灵感池可用。
4. 只对被打开、收藏、任务召回，或命中已批准高表现／创新升级规则且仍在预算内的内容升级策略分析。
5. 打通 `InspirationHandoff → DirectorBrief`，验证一条灵感如何形成一条可执行视频任务。
6. 根据词簇的收藏、采用和成片结果沉淀行业经验；在此之前不提供未经验证的行业固定模板。

## 14. 竞品依据与适用边界

- [Semrush Keyword Strategy Builder](https://www.semrush.com/kb/1058-keyword-strategy-builder)：从少量种子词或既有关键词出发，按主题、页面、意图、搜索量、难度和竞品数据组织词簇。本文借鉴其“先输入事实与种子，再聚类和筛选”的流程，不照搬其 SEO 页面生产目标。
- [Ahrefs Keywords Explorer](https://help.ahrefs.com/en/articles/5331899-how-to-use-the-keyword-ideas-reports-in-keywords-explorer)：从种子词扩展匹配词、相关词和搜索建议。本文借鉴其可追溯扩词方式。
- [OtterlyAI Prompt Research](https://help.otterly.ai/add-prompts)：可由关键词、URL、品牌／域名／行业产生待选问题，并绑定国家、语言、主题和 persona；同一个问题在不同国家分别计量。本文据此将 GEO 设计为“角色 × 市场 × 完整问题”，而不是一份全球通用关键词表。
- [YouTube Data API `search.list`](https://developers.google.com/youtube/v3/docs/search/list)：支持查询、语言、地区、时间、排序和许可类型等条件；[Videos resource](https://developers.google.com/youtube/v3/docs/videos) 返回视频详情。字段与配额仍应以实际项目凭证和接口返回为准。
- [TikTok Research API `query videos`](https://developers.tiktok.com/doc/research-api-specs-query-videos/)：能够返回公开视频字段，但访问需要特定研究权限，因此不能作为本商业产品的默认稳定接口。
- [Apify pricing](https://apify.com/pricing) 与 [Facebook Posts Scraper](https://apify.com/apify/facebook-posts-scraper)：表明平台同时存在按计算资源和按结果收费，Actor 价格也会调整。因此本文只规定预算上限与熔断，不承诺长期固定单价。

以上依据支持的是关键词形成方法、数据字段边界和成本控制方法，不证明某个行业天然应抓哪些内容。行业经验只有在真实客户数据与生产漏斗验证后，才可以从“假设”升级为系统模板。

## 15. 关键词策略的产品设计与前端动线

关键词能力控制在五个维度：种子词、国家／语言、搜索意图、竞品缺口和主题聚类。系统内部可以保存来源、版本与效果数据，但前端不向普通用户暴露查询公式、权重和大量单词列表。

### 15.1 关键词如何产生

每个策略服务于一组明确的“产品 × 市场 × 沟通对象”，生成过程如下：

1. **种子词**：从用户选择的商品、企业知识和用户补充内容中提取 3—5 个种子主题。种子主题优先使用品类、核心问题和应用场景，不把整段商品描述当关键词。
2. **国家／语言**：每个目标国家分别生成一份本地词集，保留原词、翻译词和本地常用叫法。同一英文词不能默认代表所有英语市场。
3. **搜索意图**：将候选词归入“了解问题、比较方案、准备采购／购买、使用与售后”四组。页面使用业务语言展示，不要求用户理解 SEO 术语。
4. **竞品缺口**：只读取用户确认的竞品域名、账号或品牌；找出竞品反复覆盖而当前策略缺失的主题，并显示来源样本。系统不得自动把模型猜测的品牌加入竞品名单。
5. **主题聚类**：宽主题只用于页面分组；每个宽主题必须继续拆成包含具体产品、具体问题和可观察证据的精准采集单元。用户确认采集单元，不逐个管理几十个查询变体。

每个采集单元显示：具体产品、客户问题、希望在画面中看到的动作／证据、市场／语言、意图、2—5 个查询变体和产生依据。系统内部再保存 Actor 参数、来源、版本和采用漏斗。

### 15.2 页面改动范围

#### A. 灵感中心：唯一的发现范围维护入口

现有“爆款灵感”页面建议改名为“灵感中心”。顶部继续保留搜索、平台、内容形式和更多筛选，并在同一工具栏增加一个轻量的“发现范围”选择器：

```text
[发现范围：工业连接器 · 德国 · 品牌采购 ▾]  [管理]
```

- 切换发现范围后，灵感列表按对应 `MarketKeywordSet` 过滤。
- “管理”打开右侧抽屉，不新增一级导航或独立关键词后台。
- 抽屉第一屏只编辑产品、目标市场／语言、沟通对象和已确认竞品。
- 第二屏按宽主题分组展示精准采集单元；用户可以保留、删除或补充采集单元。
- 每个主题展开后才显示代表词、来源与少量命中样本。默认不展示完整长词表。
- 底部只有“保存并采集”一个主按钮；保存前显示本次平台、回看范围、最大条数和预计成本上限。

灵感卡片只补两个与关键词有关的轻量信息：“命中主题”和“为什么出现”。详情抽屉可进一步查看命中的代表词与来源，不在卡片上堆叠关键词标签。

#### B. 编导 Agent 设置：引用策略，不重复编辑

当前“爆款采集与导演规则”中的“AI 推荐关键词”自由文本框，改成：

```text
关键词策略：工业连接器 · 德国 · 品牌采购 · 8 个主题
[更换策略] [去灵感中心管理]
```

这里继续保留采集平台、采集时间、回看天数和每次最多条数，因为这些属于 Agent 的执行节奏。关键词、国家、意图和竞品在此只显示摘要，避免 Agent 设置与灵感中心产生两份相互覆盖的数据。

如果尚无策略，系统根据当前企业商品给出“创建关键词策略”入口；用户完成灵感中心抽屉后返回原位置，不丢失 Agent 配置。

#### C. 编导生产任务：显示本任务采用的策略快照

现有生产任务顶部已经展示买家问题、证据要求、生产预算和产出目标。在“查看编导过程与完整约束”中补充只读的：

- 本任务使用的产品、市场、沟通对象；
- 命中的主题簇与灵感数量；
- 编导 Agent 临时补充了哪些查询及原因；
- 最终采用了哪些灵感，分别承担结构、证明或节奏参考。

生产页面不承担长期关键词编辑。用户发现方向不对时点击“调整”，选择“市场／受众不对”或“主题不对”，编导 Agent 为当前任务重新检索；只有用户勾选“同时影响后续同类内容”时，才把纠正建议送回关键词策略等待确认。

#### D. 企业中心：继续维护事实，不增加关键词表单

企业中心继续维护产品、市场、客户类型、官网、认证与真实业务信息。关键词策略读取这些事实，但不在企业中心再增加一套关键词输入。这样企业事实仍是一份，关键词只是其面向特定市场的检索视图。

#### E. 定时任务：展示“采什么、何时采、采多少”

定时任务页面必须体现关键词策略，因为它是采集计划真正执行的地方。但它引用灵感中心维护的策略，不另存一份可长期漂移的关键词配置。

当前定时任务卡片直接显示并编辑“检索关键词”，新建任务弹窗也要求粘贴关键词。建议改成以下结构：

```text
策略：工业连接器 · 德国 · 品牌采购 · v3
主题：验厂与质检（8）｜小批量私标（6）｜交期与 MOQ（5）
平台：YouTube、TikTok    回看：近 7 天    每次最多：20 条
频率：每天 09:00        预计月度上限：¥xx
```

任务卡片默认只展示策略名称与前三个主题，展开后再显示五类信息：

- 种子主题及代表词；
- 国家和语言；
- 已启用的意图组；
- 已确认竞品及由其产生的缺口主题；
- 本任务实际启用的主题簇。

任务卡片上的“编辑”分成两类：

- **更换关键词策略**：从现有 `MarketKeywordSet` 中选择，下一次运行使用新策略和新版本。
- **调整本任务范围**：临时停用某些主题，或补充少量任务专用词；只生成 `TaskKeywordOverride`，不回写长期策略。

新建视频／图文采集任务时，现有自由文本“采集关键词”区域改为：

1. 选择产品与关键词策略；
2. 展示国家／语言、意图、竞品和主题簇摘要；
3. 用户勾选本任务要运行的主题；
4. 设置平台、回看天数、单次上限、预算上限和执行频率；
5. 在“高级设置”中保留临时补充词输入，并继续使用现有的自动清洗与确认能力。

自由关键词不再作为默认主入口，但不能直接删除，因为它仍适合一次性热点、临时活动和故障补采。所有临时词都要标记“仅此任务”，并在执行记录中展示实际提交给各平台的清洗结果。

定时任务保存的是策略引用与执行快照：

```ts
interface ScheduledCollectionScope {
  keywordSetId: string;
  keywordSetVersion: number;
  discoveryModes: Array<'momentum' | 'account' | 'innovation'>;
  enabledClusterIds: string[];
  accountIds: string[];
  innovationBriefIds: string[];
  taskOverrides: string[];
  platforms: string[];
  lookbackDays: number;
  resultLimit: number;
  modeLimits?: Partial<Record<'momentum' | 'account' | 'innovation', number>>;
  maxRunCost?: number;
}
```

每次运行继续保存当时展开后的最终关键词、平台清洗结果和策略版本。这样即使长期策略后来更新，也能解释历史任务当时为什么采到了某条内容。

### 15.3 用户前端动线

#### 首次建立策略

```text
进入灵感中心
  → 选择一个产品
  → 系统带出已有目标市场与客户类型
  → 用户确认国家／语言和沟通对象
  → 可选添加竞品域名、品牌或账号
  → 系统生成主题簇并展示少量命中样本
  → 用户删除明显无关主题，保存并采集
  → 回到灵感流浏览结果
```

用户必须做的判断只有三个：卖什么、在哪个市场、说给谁听。种子词扩展、意图分类和聚类由系统完成，但生成结果在保存前可见。

保存策略后，如果用户需要持续采集，页面提供“设为定时采集”：

```text
保存关键词策略
  → 点击“设为定时采集”
  → 跳转定时任务并自动带入策略、主题和推荐平台
  → 用户只确认频率、回看范围、数量与预算上限
  → 创建任务
  → 返回任务卡片查看下次执行时间
```

用户也可以从定时任务页面开始：选择“新建社媒采集任务”后，先选择已有策略；如果没有策略，再跳转灵感中心创建，完成后返回新建任务弹窗。

#### 日常人工浏览与创作

```text
进入灵感中心
  → 默认恢复上次发现范围
  → 按主题／平台浏览，或搜索已有灵感
  → 查看“为什么出现”和分析可信度
  → 收藏，或点击“用于创作”
  → 选择已有／新任务并填写可选备注
  → 编导页面读取本条灵感和当前策略快照
```

“搜索已有灵感”和“修改长期发现策略”必须是两个动作：搜索框只影响当前列表；只有进入“调整发现范围”并保存，才改变后续采集。

#### 编导 Agent 自动生产

```text
任务读取产品、市场与沟通对象
  → 选择匹配的已保存关键词策略
  → 从已采集灵感中召回候选
  → 库存不足时发起一次任务级补充检索
  → 记录临时查询、命中主题和选择理由
  → 锁定少量参考并形成 DirectorBrief
  → 用户在生产页继续／调整／放弃
```

任务级补充检索不会自动改写长期策略。只有某个补充主题在多次任务中被采用，系统才在灵感中心提示“建议加入长期采集”，由用户一次确认。

### 15.4 首期实现顺序

1. 将现有单一 `products.searchKeywords` 升级为可版本化的 `MarketKeywordSet`，同时保留旧字段作为迁移输入。
2. 在灵感中心增加发现范围选择器和管理抽屉，先支持产品、国家／语言、沟通对象、竞品和主题簇。
3. 将定时任务的新建弹窗和任务卡片改成“策略引用 + 主题选择 + 执行参数”，把自由关键词降到高级设置。
4. 将编导 Agent 设置中的自由关键词框替换为策略引用，保留现有采集执行参数。
5. 给灵感记录补充 `keywordSetId`、`clusterId` 和命中依据；给定时任务运行和生产任务保存不可变的策略快照。
6. 最后接入收藏、采用和成片结果反馈，用真实漏斗调整主题优先级。

首期不建设关键词排名大盘、SEO 内容规划器、跨国家对比报表或全量竞品监控。这些能力会让灵感池变成另一套 SEO 产品，超过它为人工和 Agent 提供灵感的职责。

## 16. 关键词的决策逻辑与用户输入

### 16.1 系统按照什么逻辑决定关键词

系统不从“行业名称”直接生成一张词表，而是先确定一次采集代表哪种经营关系，再逐层形成查询。

```text
企业与商品事实
  → 本次要影响的对象
  → 对象在目标市场的需求与问题
  → 对应的搜索意图
  → 本地语言和常用表达
  → 已确认竞品覆盖的缺口
  → 形成精准采集单元并按宽主题分组
  → 按平台改写为实际查询
  → 用少量搜索结果验证
```

具体决策规则如下：

1. **锁定事实范围**：读取用户选中的产品、品类、功能、材料、应用场景、认证和可提供的服务。缺少企业依据的卖点不进入关键词。
2. **锁定经营关系**：同一个产品必须明确本次是工厂找进口商、工厂找品牌客户、品牌找消费者，还是经销商找本地消费者／零售商。经营关系决定使用采购语言还是消费语言。
3. **形成种子主题**：从产品实体、客户问题和使用场景中形成 3—5 个主题，例如“食品级软管”“小批量 OEM”“高温环境泄漏”，而不是直接生成几十个长尾词。
4. **覆盖四类意图**：围绕每个主题生成了解问题、比较方案、准备采购／购买、使用与售后四类查询。并非每个主题都必须覆盖四类；与当前经营关系不相符的意图会被删除。
5. **市场本地化**：按国家和语言转换专业叫法、单位、拼写和自然表达。翻译词必须与原始事实绑定，不能改变产品含义。
6. **补竞品缺口**：只使用用户确认的竞品，提取其反复覆盖且与本企业产品相关的主题。竞品品牌词单独标记，默认用于研究，不用于模仿或冒充。
7. **聚类与过滤**：合并同义词，删除重复、过宽、无关、无法由企业事实支持或容易带来错误受众的词。每个主题保留少量代表词供用户判断。
8. **平台适配**：先读取每个 Apify Actor 声明的输入能力，例如 `keyword`、`hashtag`、`account` 或 `url`，再把主题编译成该 Actor 可接受的输入。账号主页采集使用账号，不强行拼关键词。平台适配只改变查询形式，不改变主题本身。
9. **小样本验证**：每个主题先取少量结果，检查相关率、重复率、数据可得性与单次成本。没有有效样本的主题不直接进入定时采集。
10. **反馈调优**：后续根据打开、收藏、加入任务、编导采用和成片结果调整主题优先级。系统可以推荐增删主题，但长期策略变更需要用户确认。

系统最终确认的是“精准采集单元”，不是宽主题或某个单词。一个采集单元内部可以包含本地词、英文词和平台查询变体，但必须同时指向同一个具体产品、具体问题和可观察证据。

### 16.2 用户必须提供什么

首次生成策略只有三项必填信息：

| 必填信息 | 用户需要确认什么 | 为什么必须由用户确认 |
| --- | --- | --- |
| 产品／服务 | 本次为哪个商品、品类或服务找灵感 | 系统不能自行决定企业当前主推什么 |
| 目标市场 | 国家／地区和主要语言 | 搜索结果、叫法、竞品和购买问题都受市场影响 |
| 沟通对象 | 进口商、品牌采购、经销商、零售商或终端消费者 | 它决定采购词、渠道词还是消费词 |

以下信息为强烈建议，但可以后补：

- 目标对象最常见的一个问题或购买顾虑；
- 已确认的竞品品牌、域名或社媒账号；
- 企业希望重点证明的能力，例如 MOQ、交期、定制、认证、售后或本地库存；
- 明确排除的词、竞品、受众和内容类型。

用户不需要提供搜索量、关键词难度、完整长尾词表、意图标签或平台语法。系统生成这些候选，并把判断依据和样本交给用户确认。

### 16.3 初始信息在哪里提供

信息只在三个位置录入，各自职责不同：

#### 企业中心：录入长期事实

企业中心保存可跨任务复用的信息：

- 企业角色与主要业务；
- 产品、品类、功能、材料、应用场景与真实卖点；
- 可验证的认证、生产／服务能力和不能承诺的边界；
- 常做的目标市场和客户类型；
- 官网、商品页和已有品牌资料。

这些信息是关键词生成的事实底座。已经存在的数据自动带入，用户不需要在灵感中心重复填写。

#### 灵感中心的“调整发现范围”抽屉：确认本次策略

首次进入或新建发现范围时，抽屉先展示系统从企业中心带出的内容：

```text
产品：工业连接器
市场：德国／德语
沟通对象：品牌采购
```

用户只补齐缺失项，并可选填写一个客户问题和竞品。随后系统生成主题簇和少量样本，用户在这里完成最终确认：

- 哪些主题保留；
- 哪些主题删除或改名；
- 是否缺少一个重要主题；
- 竞品缺口是否确实与自己有关。

保存后形成一个版本化的 `MarketKeywordSet`。因此，灵感中心是“决定采什么”的页面。

#### 定时任务：提供执行信息

定时任务不再要求用户重新决定关键词，只选择已有策略并提供：

- 需要执行的主题簇；
- 采集平台；
- 执行频率；
- 回看天数；
- 单次结果上限与预算上限；
- 可选的一次性临时词。

因此，定时任务是“决定何时采、去哪采、采多少”的页面。

如果用户从具体生产任务发起，产品、市场和沟通对象优先从任务上下文带入；用户只需确认或纠正。这个任务产生的临时查询默认只服务本次生产，不自动变成长期策略。

### 16.4 用户实际看到的确认过程

```text
第一步：确认范围
产品 [工业连接器 ▾]
市场 [德国 ▾]  语言 [德语 ▾]
沟通对象 [品牌采购 ▾]
竞品 [可选]

第二步：确认主题
✓ 产品选择与应用场景
✓ 供应商比较与验厂
✓ 小批量 OEM／私标
✓ 认证与质量证明
○ 安装与售后

第三步：查看样本
每个主题显示 3—5 条搜索样本、命中原因和预计有效率

第四步：保存策略
[仅保存] [保存并设为定时采集]
```

如果企业中心资料足够，用户只需要确认第一步和第二步。只有系统无法确定市场、沟通对象，或样本相关性过低时，才要求补充信息，避免把关键词配置做成一份长问卷。

### 16.5 任务级精准查询的具体设计

以下结构用于生产任务缺少某类具体证据时的定向查询，不承担灵感池的主要召回。完整的长期采集还需要第 17 节的大词与中词层。任务级查询分三层保存，避免把业务概念、用户看到的采集目标和 Apify 实际输入混在一个字符串字段中。

#### 第一层：业务范围 `KeywordScope`

```ts
interface KeywordScope {
  productId: string;
  market: string;
  language: string;
  companyRole: 'factory' | 'brand' | 'distributor' | 'retailer';
  audienceRole: 'brand_buyer' | 'importer' | 'distributor' | 'retailer' | 'consumer';
  verifiedCompetitors: Array<{ type: 'brand' | 'domain' | 'account'; value: string }>;
}
```

这一层全部来自企业事实与用户确认，模型不能自行改动。

#### 第二层：用户确认的精准采集单元 `ContentSearchUnit`

“供应商能力”“认证与质量”“使用场景”只能作为后台分组，不能直接拿去搜索。真正驱动采集的对象必须进一步收窄为：

```text
具体产品／部件
  + 具体场景、问题或采购顾虑
  + 画面中可观察的动作、过程或证据
  + 可选的内容形式
```

一个采集单元只解决一个内容问题。例如：

```text
M12 connector + waterproof concern + IP68 immersion test
circular connector + corrosion concern + salt spray test
custom connector + buyer wants to see customization + mold-making process
connector assembly + installation error + pin insertion tutorial
low-volume custom connector + MOQ concern + sample-to-production process
```

这种颗粒度才能搜到可直接浏览和对标的视频，而不是泛行业资讯。

```ts
interface ContentSearchUnit {
  id: string;
  groupLabel: string;
  productEntity: string;
  buyerQuestion: string;
  observableEvidence: string;
  contentPattern?: 'test' | 'process' | 'comparison' | 'tutorial' | 'case' | 'demo';
  intent: 'learn' | 'compare' | 'buy' | 'use';
  queryVariants: string[];
  evidence: Array<'product' | 'website' | 'inquiry' | 'competitor' | 'user'>;
  status: 'suggested' | 'approved' | 'rejected';
}
```

例如“工业连接器 · 德国 · 品牌采购”不能只形成“认证与质量”主题，而应拆成更具体的采集单元。以下仅展示拆解方法，具体产品和能力必须来自企业事实：

| 后台分组 | 精准采集单元 | 查询变体示例 | 希望搜到的内容 |
| --- | --- | --- | --- |
| 防水与质量验证 | M12 连接器的 IP68 浸水测试 | M12 connector IP68 immersion test；M12 Stecker IP68 Wassertest | 有产品、浸水动作、测试过程或结果的视频 |
| 耐腐蚀验证 | 圆形连接器盐雾测试 | circular connector salt spray test；Rundsteckverbinder Salzsprühtest | 盐雾设备、样品前后状态、检测过程 |
| 定制过程 | 定制连接器从开模到样品 | custom connector mold making process；kundenspezifischer Stecker Werkzeugbau Muster | 设计、模具、打样或样品确认过程 |
| 安装问题 | 连接器端子插针与退针 | connector terminal pin insertion removal；Steckverbinder Kontakt einsetzen auspinnen | 手部操作、工具、正确与错误步骤 |
| 采购顾虑 | 小批量定制从样品到量产 | low volume custom connector sample production；Stecker Kleinserie Muster Serienfertigung | 样品确认、工序或小批量生产证据 |

如果用户只提供“工业连接器”，系统信息不足以生成以上采集单元。它必须继续读取具体产品系列、应用环境、可证明能力和客户真实问题；缺什么就只追问缺失项。若企业没有 IP68、盐雾测试、小批量定制等事实，相应单元不能出现。

#### 第三层：Apify 任务参数 `PlatformQuery`（仅后端）

这一层不是新的关键词策略，也不需要用户理解。它只是把用户已经确认的精准采集单元，填入不同 Apify Actor 要求的参数格式。

例如用户确认的采集单元是：

```text
M12 连接器的 IP68 浸水测试
```

系统已经生成两个经过确认的查询变体：

```text
M12 connector IP68 immersion test
M12 Stecker IP68 Wassertest
```

后端根据所选 Actor 的 schema 决定把它放进 `searchQueries`、`hashtags` 或其他输入字段。Actor 若不支持关键词而只支持账号或 URL，这个 Actor 就不执行该关键词单元，不能把词硬塞进去。

```ts
interface PlatformQuery {
  clusterId: string;
  platform: 'youtube' | 'tiktok' | 'instagram' | 'facebook';
  actorId: string;
  queryType: 'keyword' | 'hashtag' | 'account' | 'url';
  query: string;
  language: string;
  market: string;
  enabled: boolean;
}
```

`PlatformQuery` 由后端适配器根据 Actor 能力生成。例如某个 Actor 支持关键词数组，就提交已经确认的查询变体；只支持 Hashtag 时，只有能自然转换为 Hashtag 的采集单元才执行；只支持账号时，只提交用户确认的账号。系统不得因为某个平台接口需要输入，就凭空制造与业务无关的词。

### 16.6 候选词如何取舍

首期不设计一套看似精确但没有数据校准的固定权重。候选采集单元依次经过四道门：

1. **事实门**：产品、场景和证据动作能否追溯到商品、官网、询盘、用户输入或已确认竞品；不能追溯就删除。
2. **精度门**：是否同时包含具体对象与具体问题／动作。“connector quality”“factory capability”一类宽词不能单独执行。
3. **对象门**：是否符合当前沟通对象。例如面向进口商时关注 MOQ、compliance 和交付证据，面向消费者时关注使用问题、比较和教程；角色错位就删除。
4. **样本门**：通过 Apify 小样本采集后，结果是否大部分相关、是否出现足够新内容、字段是否可用、成本是否在上限内；不合格则暂停该采集单元并提示用户。

通过四道门后，再按真实反馈排序：被打开、收藏、用于创作和被编导采用的采集单元优先。播放量只作为候选内容的外部表现信号，不决定关键词策略。

## 17. 大词发现、中词扩簇、小词验证

上一节的精准采集单元只能承担定向验证，不能独立承担整个灵感池的供给。如果所有任务都使用“具体产品＋具体问题＋具体动作”的小词，结果量会过小，也容易错过正在起量的新场景。

GEO 产品采用的是分层结构，而不是只跟踪大量孤立问题。以 Semrush AI Visibility 为例：用户先输入宽的 topic 或 product category，系统发现 related topics，再下钻到具体 prompts、意图、品牌和来源；单条 prompt 通常过于稀疏，因此需求量在 topic 层估算。竞品研究再补充对手出现而本品牌缺失的 topics、prompts 和 sources。这种方法同时保留覆盖面与解释精度。

社媒采集应借鉴这个结构，但把“相关 topic”替换为可以从视频内容中观察到的场景、问题、卖点和表达关系。

### 17.1 三层关键词

| 层级 | 定义 | 作用 | 示例：护肤 | 是否直接长期大量执行 |
| --- | --- | --- | --- | --- |
| 大词／发现词 | 品类、核心需求、人群入口 | 打开足够大的内容池，发现新关系 | 护肤、skincare、skin care routine | 是，但限制结果量和重复率 |
| 中词／场景簇 | 品类与肤质、问题、场景、卖点或内容形式的组合 | 获得既有量又与创作相关的素材 | 干皮护肤、换季起皮、妆前保湿、屏障修护、保湿测评 | 是，作为主要供给 |
| 小词／验证词 | 具体对象＋具体问题＋具体动作／证据 | 验证某个卖点或补足编导证据 | dry skin foundation flaking test、moisturizer hydration test | 按需执行，不承担主要供给 |

大词不是泛行业名称。它至少要落在用户可能持续消费内容的类别、问题或人群入口；例如“美妆行业”过大，“护肤”可以作为发现词。小词也不是越长越好，它只在需要找具体证据、动作或制作参考时使用。

### 17.2 相关内容如何扩成关键词簇

系统首先用大词抓一批种子内容，再从真实内容而非模型常识中提取关联信号：

- 标题、描述、Hashtag 和账号类别；
- ASR 中反复出现的问题、场景和产品叫法；
- OCR 中出现的卖点、测试、步骤和人群词；
- 同一内容中高频共现的词；
- 同一作者连续覆盖的相邻主题；
- Apify Actor 如果能返回相关推荐、相关搜索、音乐／话题或关联账号，则作为额外边，但不能假设所有 Actor 都提供这些字段；
- 高表现内容与普通内容之间显著不同的场景、钩子或证明方式。

形成的是一张可追溯的内容关系图：

```text
护肤
  ├─ 肤质
  │   ├─ 干皮
  │   │   ├─ 起皮
  │   │   ├─ 卡粉
  │   │   └─ 换季紧绷
  │   └─ 油皮
  ├─ 使用场景
  │   ├─ 妆前
  │   ├─ 夜间修护
  │   └─ 换季
  └─ 卖点／证据
      ├─ 保湿
      ├─ 屏障
      ├─ 吸收速度
      └─ 前后对比
```

每条边必须保存依据，例如来自多少条视频、哪些字段、哪些账号或哪些高表现样本。模型可以给节点命名和合并近义词，但不能凭空建立“护肤 → 某功效”的关系。

### 17.3 一轮采集如何运行

每轮不是只提交一组关键词，而是运行一个查询组合：

1. **发现查询**：从少量大词获取新内容和新关联，控制重复率与单词最大抓取量。
2. **扩簇查询**：选择最近增长、与企业产品相关、或被高表现内容频繁覆盖的中词继续采集。这一层构成灵感池的主体。
3. **验证查询**：围绕当前生产任务缺少的卖点、动作或证据运行小词，结果直接交给编导判断。
4. **对标查询**：采集已确认竞品账号近期内容，提取其新增场景和表达，再与己方词簇做差距比较。
5. **创新探索查询**：按照第 6.1 节，从相邻行业／场景，或内容与评论中出现的新问题、新场景形成探索命题，避免系统只重复已有偏好。

不预设永久固定比例。系统保证每层都有预算，再根据有效素材率动态移动下一轮额度：

- 大词结果多但重复或无关时，减少该大词额度，保留其已验证的中词分支；
- 中词持续产生被收藏、采用的内容时，提高该场景簇额度；
- 小词无结果时，不继续无限扩写，而是退回父级中词寻找新的实际表达；
- 某个相关节点只产生高播放但与企业任务无关的内容时，降低业务相关性，不因播放量继续放大；
- 新节点连续多轮产生有效灵感后，才升级为长期中词。

### 17.4 如何判断“起量内容”值得扩簇

系统先在同一平台、相近发布时间和相似账号量级内比较，不能直接把不同平台的绝对播放量放在一起。一个内容节点值得扩簇，需要同时满足：

- 有可获得的表现信号，且相对同账号或同批内容突出；
- 内容中可以识别具体场景、问题、卖点或表达机制；
- 与当前产品、市场或沟通对象存在可解释的连接；
- 不是由单个偶然爆款或重复搬运造成；
- 进入该节点的进一步采集成本在预算范围内。

如果缺少账号基线、曝光或完整互动数据，只能标成“表现信号较强”，不能断言为爆款。真正决定词簇长期价值的仍是收藏、用于创作、编导采用和成片表现。

### 17.5 用户如何控制而不管理大量词

前端展示三层结构，但交互重点放在中词场景簇：

```text
发现入口：护肤

系统发现的相关场景
✓ 干皮与起皮          128 条内容 · 近 7 日上升
✓ 妆前卡粉            76 条内容 · 采用率较高
✓ 换季屏障修护        54 条内容 · 新发现
○ 油皮控油           与当前产品关联较弱

定向证据
· 保湿前后对比
· 妆前起皮测试
```

用户确认大词入口和要持续跟踪的中词簇；小词由编导任务按需发起。用户可以屏蔽错误分支，也可以把某个新场景加入长期跟踪，不需要直接维护底层所有查询变体。

### 17.6 对现有关键词设计的修正

因此，`KeywordScope` 下面不应只有精准 `ContentSearchUnit`，而应保存：

```ts
interface SocialKeywordGraph {
  discoverySeeds: DiscoverySeed[];
  sceneClusters: SceneCluster[];
  evidenceQueries: ContentSearchUnit[];
  edges: KeywordRelation[];
}
```

- `DiscoverySeed` 是少量大词入口；
- `SceneCluster` 是灵感池的主要采集和排序单位；
- `ContentSearchUnit` 降级为任务级证据查询；
- `KeywordRelation` 保存相关关系及其视频证据。

Apify 仍只负责执行采集。大词、中词和小词的形成、关系维护、预算调度和效果反馈由灵枢自己的策略层完成，不能依赖某个 Actor 自动替系统决定。

## 18. 中词的构成与企业资料采集

### 18.1 中词不是产品卖点列表

产品手册、产品目录、规格表、商品页和培训资料都可以作为中词候选的主要输入，但不能把其中的栏目标题直接当作中词。手册更擅长描述供给侧事实，例如产品类别、功能、材料、适用范围、认证、操作方法和限制；消费者痛点、采购顾虑和真实说法需要由询盘、客服、评论、售后和搜索行为补充。

中词应是一个仍有足够内容量、同时能约束创作方向的“需求／场景组合”：

```text
产品类别或产品任务
  + 人群／使用场景／问题／期望结果／决策顾虑中的一个
```

例如：

| 原始资料 | 不应直接作为中词 | 可以形成的中词候选 |
| --- | --- | --- |
| 面霜；含神经酰胺；用于日常保湿 | 神经酰胺含量、产品参数 | 干皮日常保湿、换季屏障修护、妆前保湿 |
| M12 连接器；IP68；适用户外设备 | IP68 参数、连接器质量 | 户外设备防水连接、潮湿环境连接器、设备连接防水验证 |
| 便携榨汁杯；可充电；易清洗 | 电池容量、刀头规格 | 通勤早餐、办公室鲜榨、榨汁杯清洗困难 |

表中的中词仍是候选。例如“换季屏障修护”只有在产品资料、客户反馈或采集结果能支持产品与该场景的关系时才启用；不能从“含神经酰胺”直接断言产品可以修复任何皮肤问题。

### 18.2 中词可以包含什么

系统从以下八类信息中形成中词：

| 中词维度 | 含义 | 例子 |
| --- | --- | --- |
| 产品类别／任务 | 用户实际寻找的产品或要完成的事情 | 保湿面霜、工业防水连接、便携榨汁 |
| 使用人群 | 具有共同需求的人群，不使用未经证实的敏感推断 | 干皮人群、户外设备工程师、通勤人群 |
| 使用场景 | 时间、地点、环境或工作环节 | 妆前、换季、户外潮湿环境、办公室早餐 |
| 问题／失败状态 | 用户正在避免或解决的问题 | 起皮、卡粉、连接进水、清洗麻烦 |
| 期望结果 | 用户想达到的状态 | 持久保湿、稳定连接、快速清洗 |
| 决策顾虑 | 购买或采购前反复比较的因素 | 是否闷痘、MOQ、交期、兼容性、售后 |
| 卖点机制 | 产品通过什么方式解决问题 | 神经酰胺屏障、密封结构、可拆洗杯体 |
| 证明方式 | 用户希望看到什么才相信 | 使用前后、测试、拆解、操作过程、案例 |

中词通常组合其中两个维度。例如“干皮＋妆前保湿”“户外设备＋防水连接”“便携榨汁杯＋清洗困难”。组合三个以上维度后往往会变成小词，应交给任务级验证查询。

“开箱、测评、教程、前后对比、工厂参观”等属于内容形式词，可以与中词组合执行，但不单独代表用户需求。例如“干皮保湿＋测评”成立，“产品测评”本身过宽。

### 18.3 可以从用户哪里获得中词

按精度从高到低，输入来源分为四组：

其中 A—C 是用户可选导入的第一方资料，不是 Apify 自动获得的数据，也不是启用灵感采集的前提。用户没有提供时，系统只使用企业中心已有事实和 Apify 取得的公开内容；成交、GMV 和订单量不进入对标账号评分。

#### A. 企业事实资料

- 产品目录、产品手册、规格表和报价单；
- 官网、商品详情页、宣传册和销售培训资料；
- 认证、检测报告、应用说明和安装／使用说明；
- 产品图片、包装文字和既有视频素材。

这组资料产生产品类别、功能、应用场景、机制、证明方式和边界。所有提取结果保留文件、页码／表格行或原文位置。

#### B. 客户原话

- 询盘邮件、WhatsApp／客服对话和 CRM 备注；
- 销售通话纪要、常见问题和报价前问题；
- 评论、私信、问答、用户评价和展会记录；
- 搜索词、站内搜索和广告搜索词。

这组资料最适合产生问题、使用场景、比较因素和客户自己的表达。出现频次不能直接等同于市场需求量，但可以用来提高候选中词的可信度。

#### C. 售后与交易资料

- 退换货原因、投诉、故障描述和使用错误；
- 安装咨询、维修记录和售后工单；
- 成交／丢单原因、样品反馈和复购原因。

这组资料可以发现购买前没有写进手册、但实际影响使用和决策的问题。

#### D. 外部内容验证

- 用户确认的竞品账号、网站和商品页；
- 大词种子采集获得的视频标题、字幕、Hashtag 和评论问题；
- 高表现内容中的场景、问题、卖点和证明方式共现。

外部内容用于验证和扩展，不能反向改写企业自己的产品事实。

### 18.4 从资料到中词的处理过程

```text
上传或读取企业资料
  → 提取带原文引用的产品事实
  → 按产品系列合并同义字段
  → 从客户原话提取场景、问题和决策顾虑
  → 建立“产品事实—客户问题—可证明能力”连接
  → 生成中词候选
  → 用 Apify 做少量样本采集
  → 展示样本与依据给用户确认
  → 加入长期场景簇
```

系统需要区分三种状态：

- `verified_fact`：资料明确写出，例如材料、功能、适用环境；
- `customer_evidence`：客户原话或交易资料中真实出现的问题；
- `hypothesis`：模型从功能推测的潜在场景或痛点。

只有前两类可以直接生成默认启用的中词。`hypothesis` 必须显示“待验证”，经过用户确认或社媒小样本证明相关后才能启用。

### 18.5 用户需要提供的最小资料

首轮不要求用户一次提交所有资料。最小输入是：

1. 一个产品目录、商品页或产品手册；
2. 本次重点产品或产品系列；
3. 目标市场与沟通对象；
4. 至少一个真实客户问题。如果暂时没有，可以先用大词采集发现，但系统要标记需求侧证据不足。

提高准确度最有效的补充资料，不是继续上传更多宣传册，而是提供少量真实询盘、FAQ、评论、售后问题或丢单原因。

### 18.6 前端如何收集而不增加重表单

企业中心现有产品导入继续作为长期资料入口，支持目录、手册、表格、商品页和图片。导入完成后生成“可用于发现灵感的信息”预览：

```text
系统识别
产品类别：保湿面霜
使用人群：干皮（来自产品说明）
使用场景：日常、妆前
产品机制：神经酰胺、保湿
可证明内容：质地、使用步骤
待验证推测：换季屏障修护
```

灵感中心的发现范围抽屉只要求用户：

- 选择本次重点产品；
- 勾选系统识别出的事实与客户问题；
- 删除错误项；
- 对“待验证推测”选择启用、忽略或补充依据；
- 可选粘贴 3—10 条客户原话。

系统随后生成中词候选，并为每个候选显示“来自哪里”和少量社媒样本。用户确认的是中词场景簇，不需要重新阅读或标注整份手册。

## 19. GEO 思路能否找到行业爆款

### 19.1 结论

GEO 的 Topic／Prompt 分层可以解决“行业语义范围如何展开、如何避免只搜少量小词”的问题，但不能单独解决“哪些社媒内容正在起量、为什么爆、是否值得编导借鉴”。如果产品只做大词、中词和小词，再把搜索结果交给内容 Agent，最终只能得到行业相关内容库，不能稳定得到行业相关爆款库。

完整系统需要把三套机制串起来：

```text
语义召回：找得到行业相关内容
  → 表现识别：找出相对正在起量的内容
  → 创作可迁移分析：判断为什么有效以及能否用于本企业
```

GEO 思路主要服务第一段，部分服务竞品和来源缺口；后两段必须按社媒内容逻辑单独设计。

### 19.2 GEO 方法可以借鉴什么

GEO 产品通常用宽 topic 进入，用 related topics 承载需求规模，再用具体 prompts 解释用户问题、意图、品牌和来源。Semrush 的公开说明还明确指出，单条 prompt 往往过于具体，因此在 topic 层估算需求量，并将语义方向相近的 prompts 聚合；竞品模块则关注对手出现而本品牌缺失的 topics、prompts 和 cited sources。

灵感池可以借鉴：

- 大词作为发现入口，而不是长期唯一查询；
- 中词聚合同一需求方向下的真实场景和问题；
- 小词解释具体意图并支持定向验证；
- 从竞品内容中发现己方缺少的场景簇；
- 按国家、语言和沟通对象分别维护语义空间；
- 不用单条长尾词的结果量代表整个需求。

这些能力可以提高行业相关内容的召回率与可解释性。

### 19.3 GEO 方法不能直接解决什么

社媒搜索与推荐不是纯语义检索。平台会综合内容表现和用户行为。YouTube 官方将推荐相关信号概括为观看／搜索历史、订阅、赞踩、反馈与满意度，并在内容表现中关注吸引力、观看参与和满意度；TikTok 官方说明推荐还使用用户互动，以及 captions、sounds、hashtags 等视频信息。由此可见，关键词只描述“内容讲什么”，不能完整描述“用户是否愿意看、看多久、是否分享，以及平台是否继续放大”。

只依赖 GEO 关键词会有四个缺口：

1. **搜索偏差**：只能得到文字元数据或 Actor 搜索能够召回的内容，遗漏推荐流中标题弱、语义隐含但表现很强的视频。
2. **表现盲区**：关键词相关不等于正在起量，绝对播放量也可能只是大账号积累。
3. **形式盲区**：相同主题可以因开场、人物、镜头、声音、剪辑和证明顺序产生完全不同的结果。
4. **个性化缺失**：Apify 采集结果不等同于真实用户经过长期观看行为训练后的推荐流。

因此，不应向用户承诺“配置关键词即可找到行业爆款”。更准确的产品承诺是：“用语义策略扩大行业相关内容召回，再从真实表现和内容结构中筛选值得借鉴的高潜素材。”

### 19.4 灵枢应采用的五路召回

为了接近用户刷视频时的相关内容扩散，同时补充跨行业和跨场景参考，候选池至少由五路组成：

| 召回通道 | 解决的问题 | 主要输入 |
| --- | --- | --- |
| 关键词召回 | 建立行业语义覆盖 | 大词、中词、小词及本地语言变体 |
| 对标账号召回 | 获取同行持续发布与近期高表现内容 | 用户确认的品牌、达人、经销商和专业账号 |
| 内容关系扩展 | 从一条有效视频继续发现相关场景和表达 | Hashtag、声音、作者、共现词、相关推荐等 Actor 实际返回字段 |
| 表现反向扩展 | 从正在起量的视频反推新场景和新查询 | 相对表现、发布时间、内容标签、ASR／OCR 与视觉分析 |
| 创新探索召回 | 补充现有行业爆款和对标账号没有覆盖的可迁移表达 | 相邻行业／场景，以及内容与评论中发现的新问题、新场景 |

某个 Apify Actor 如果没有返回相关推荐、声音或关联账号，就只使用它真实提供的边，不伪造“推荐流数据”。产品需要记录每条候选来自哪一路召回，才能评估哪种方式真正产生了可用灵感。

### 19.5 爆款识别与关键词分开

关键词负责召回，爆款由独立的 `MomentumScore` 判断。首期不使用跨平台统一播放量，而在平台内进行相对比较：

- 内容发布距今多久；
- 播放、点赞、评论和分享中实际可获得的指标；
- 相对同账号近期内容的表现；
- 相对同一场景簇、相近发布时间内容的表现；
- 多次快照之间是否仍在增长；
- 是否为重复搬运、付费投放或异常互动迹象；
- 指标完整度和结论置信度。

如果只能获得一个时间点的播放量，就只能标记“高表现候选”；只有具有时间快照或可靠账号基线时，才可以标记“正在起量”。不同平台的指标口径分别计算，最终只转换为平台内分位或相对等级。

### 19.6 内容 Agent 需要的不是关键词，而是创作证据

高表现候选还需要经过 `TransferabilityScore`：

- 是否能识别具体的用户问题或场景；
- 前几秒如何建立吸引力；
- 卖点和证明以什么顺序出现；
- 画面、声音、人物、字幕和节奏各自承担什么作用；
- 哪些机制可以迁移，哪些产品事实和独特表达必须替换；
- 企业是否拥有实现该方案的真实素材与能力。

只有同时满足“行业相关”“表现信号较强”“创作机制可解释”“企业有条件执行”的内容，才交给编导 Agent。内容 Agent 接收的是编导锁定的脚本、分镜目标、素材要求与验收条件，不直接读取关键词后自行创作。

### 19.7 推荐的产品漏斗

```text
大词／企业资料建立初始行业图谱
  → Apify 多通道采集候选
  → 从真实内容扩展中词和关系边
  → 平台内相对表现筛选
  → 多模态分析创作机制
  → 人工收藏／编导采用
  → 内容 Agent 按 DirectorBrief 生产
  → 成片数据反哺词簇、来源和创作机制
```

这个漏斗中，GEO 分层是行业图谱和查询扩展模块，不是完整爆款引擎。决定产品能否达到理想采集效果的关键，是能否补齐内容关系扩展、平台内表现判断和创作可迁移分析。

参考依据：

- [Semrush AI Visibility 数据说明](https://www.semrush.com/kb/1607-semrush-ai-visibility-data)：具体 prompt 过于稀疏，因此使用 topic 聚合相关 prompts 并在 topic 层估算需求。
- [YouTube 推荐机制](https://support.google.com/youtube/answer/16089387)：推荐不仅使用搜索语义，还使用观看历史、互动、反馈和满意度等信号。
- [YouTube 内容表现](https://support.google.com/youtube/answer/16559650)：内容表现关注吸引力、参与度和满意度，标题、缩略图、开场和留存都会影响传播。
- [TikTok For You 推荐说明](https://newsroom.tiktok.com/how-tik-tok-recommends-video-for-you?lang=en-MY)：推荐综合用户互动与 captions、sounds、hashtags 等视频信息。

## 20. 产品决策：借鉴 GEO，但不建设 GEO 产品

### 20.1 决策结论

灵感大屏保留 GEO 的语义组织方法，但不以关键词研究、Prompt 监测或品牌 AI 可见度为产品主线。产品核心目标是：

> 用尽量少的企业信息和种子内容，持续发现行业内正在起量的内容、值得长期观察的账号，以及真实且可以迁移的创新参考。

因此，GEO 是后台的行业语义约束和冷启动工具；社媒内容关系扩散、表现识别与创作可迁移分析才是爆款发现的主引擎。

### 20.2 为什么不能完全照搬 GEO

完整照搬 GEO 容易把产品带向关键词研究、Prompt 跟踪、品牌提及、引用来源和可见度报告。用户可能维护大量主题和查询，却仍然无法回答：

- 哪些视频正在相对起量；
- 哪种开场、人物、画面、声音或节奏促成传播；
- 哪些表达可以迁移到当前企业；
- 企业是否具有完成该表达所需的产品事实和素材。

这些问题必须由社媒表现数据、多模态分析和编导判断解决。

### 20.3 为什么不能完全抛掉 GEO

如果只按播放量、热门账号或平台推荐关系追内容，系统容易持续向泛娱乐热点漂移。它会找到热门内容，却无法解释内容与企业产品、客户、市场和经营目标的关系。

GEO 方法仍需要保留三项能力：

1. **主题层级**：描述品类、需求、场景和问题之间的关系，例如“护肤 → 肤质 → 干皮 → 起皮”。
2. **竞品缺口**：发现竞品持续覆盖而企业当前缺少的场景、问题、卖点和来源。
3. **市场与受众分层**：区分国家、语言，以及品牌采购、进口商、经销商、零售商和消费者。

这三项作为后台结构存在，不包装成独立 GEO 功能，也不要求普通用户理解 Prompt、Topic Volume 或 AI Visibility 等概念。

### 20.4 最终产品架构

```text
GEO 方法提供行业边界
  +
社媒原生方法发现和判断爆款
```

完整流程为：

```text
企业产品、市场和沟通对象
  → 少量行业入口词
  → 对标账号与种子内容
  → 关键词、账号、Hashtag、声音和内容关系扩散
  → 平台内相对表现与增长判断
  → 爆点及创作机制分析
  → 编导 Agent 判断是否采用
  → 内容 Agent 按 DirectorBrief 生产
```

关键词只是召回入口之一。系统还要从已找到的有效视频继续发现：

- 相关场景与用户问题；
- 相邻作者、账号与内容系列；
- 高频共现的 Hashtag、声音、卖点和表达形式；
- 相对账号基线快速起量的新内容；
- 在多个账号中重复成功的创作机制。
- 相邻行业／场景中能够迁移的表达方式，以及内容和评论暴露的新问题、新场景。

只有 Apify Actor 实际返回的数据才可以成为关系边；缺少相关推荐、声音或账号关联字段时，系统不得假装获得了平台推荐图谱。

### 20.5 大词、中词、小词的新定位

| 层级 | 产品职责 |
| --- | --- |
| 大词 | 冷启动和周期性发现入口，帮助系统打开行业内容空间 |
| 中词 | 主要由真实内容、客户问题和产品事实共同形成的场景簇，是日常采集主体 |
| 小词 | 编导任务需要具体动作、证明或制作参考时使用的临时查询 |
| 对标账号与种子视频 | 与关键词同级的召回入口，用于进入真实社媒内容网络 |

产品不以“关键词数量”衡量策略成熟度，而看有效场景覆盖、候选相关率、重复率、收藏率、编导采用率和成片结果。

### 20.6 首期产品收敛

首期用户只需要：

1. 选择产品、目标市场和沟通对象；
2. 确认少量行业入口词；
3. 可选添加对标账号或参考视频；
4. 查看系统从真实采集内容中发现的场景簇；
5. 保留、屏蔽或加入长期跟踪。

后台负责：

- 通过 Apify 执行关键词、账号和明确链接采集；
- 从标题、描述、Hashtag、ASR、OCR 和视觉分析中形成内容关系；
- 在平台内识别相对高表现和增长候选；
- 分析钩子、证明方式、结构和制作条件；
- 将合格内容交给编导 Agent，而不是直接交给内容 Agent。

首期不建设 GEO 排名大盘、Prompt 日常监测、AI 引用份额或复杂关键词工作台。这些能力不直接提高行业爆款发现与视频生产的成功率。

## 21. 围绕三类灵感供给的产品交互与 Agent 协作

### 21.1 产品设计原则

用户进入灵感中心是为了找到值得借鉴的方向和素材，不是为了维护关键词库。产品前台围绕三个问题组织：

1. 当前在为哪个产品、市场和对象找内容；
2. 系统最近发现了哪些相关场景、起量候选、对标账号增量和创新参考；
3. 哪些内容值得交给编导继续生产。

大词、中词、小词、关系图、Apify Actor 参数和预算调度属于后台策略。用户只有在需要纠偏时才逐层查看来源与查询依据。

### 21.2 前端页面分工

#### A. 企业中心：提供事实底座

继续使用现有企业与产品资料入口，支持产品目录、手册、表格、商品页、图片和客户资料。系统提取产品类别、场景、卖点、证据与边界，并保留原文引用。

企业中心回答“企业真实拥有什么”，不展示爆款内容，也不配置定时采集。

#### B. 灵感中心：发现与选择的主页面

现有页面改名为“灵感中心”，并在顶部增加一个轻量的“发现范围”栏：

```text
[工业连接器] [德国] [品牌采购]   来源：关键词＋6 个对标账号
[调整发现范围]
```

范围栏下方不展示关键词表，而展示三组可横向浏览的内容：

```text
最近发现的场景
[户外防水连接 ↑] [小批量定制] [端子安装错误 ↑] [盐雾与腐蚀]

正在起量
[视频卡片] [视频卡片] [视频卡片]

与你的产品高度相关
[视频卡片] [视频卡片] [视频卡片]

创新参考
[相邻场景卡片] [新问题卡片] [跨行业表达卡片]
```

场景卡片显示：场景名称、来自多少条内容、近一轮新增量、当前相关度、是否有起量候选，以及关系来源。用户操作只有：

- `持续跟踪`：加入长期中词场景；
- `暂不关注`：降低该分支采集额度；
- `查看内容`：过滤到该场景；
- `为什么发现`：展开产品事实、客户原话、对标账号或内容共现依据。

视频卡片首屏只显示：

- 平台、作者、发布时间和来源状态；
- 命中场景；
- “高表现候选”或“正在起量”及置信度；
- 一句话推荐理由；
- 收藏、暂不相关、用于创作。

创新参考卡片不强制显示“正在起量”，改为显示“新在哪里、可借鉴什么、迁移时必须替换什么”。三类内容仍使用同一个 `InspirationItem` 和同一详情页，不新增独立页面。

播放量、点赞等具体指标放在卡片次级区域；关键词、查询变体和 Actor 信息只在“为什么出现”中查看。

#### C. 发现范围抽屉：负责冷启动和纠偏

用户点击“调整发现范围”后打开右侧抽屉，而不是进入复杂配置页：

```text
1. 产品、市场、沟通对象
2. 行业入口词
3. 对标账号／参考视频
4. 已跟踪场景
5. 排除内容
```

- 产品、市场和沟通对象优先从企业中心带入；
- 系统推荐少量大词，用户只确认或删除；
- 用户可添加对标账号或粘贴一条参考视频；
- 中词由真实内容扩展后出现在“已跟踪场景”，不要求用户预先完整填写；
- 小词不在这里长期维护，由具体编导任务按需产生。

保存前先执行小样本预览，展示内容相关性、可获得字段和预计单次成本。主按钮为“保存并开始发现”。

#### D. 定时任务：展示发现计划的执行状态

定时任务卡片显示：发现范围、启用的采集模式、当前跟踪场景、对标账号、创新探索命题、平台、运行频率、单次上限、预算、上次结果和下次执行时间。

```text
德国品牌采购 · 工业连接器
入口：industrial connector
跟踪：户外防水、定制打样、端子安装
来源：4 个平台 · 6 个对标账号
每天 09:00 · 每次最多 40 条 · 单次预算上限 ¥xx
上次：新增 18 条 · 起量候选 3 条 · 有效场景 2 个
```

用户可以暂停任务、调整频率与预算、关闭某个场景，或更换发现范围。底层查询词仍在展开详情中只读展示；一次性补词放在高级设置。

#### E. 编导生产页面：展示采用依据

用户从灵感卡片点击“用于创作”后，只需选择已有任务或新建任务，并可写一句备注。生产页面顶部显示：

- 参考内容及其场景；
- 为什么判断它值得采用；
- 表现结论和置信度；
- 可迁移的钩子、结构、证明顺序与节奏；
- 必须替换的产品事实和版权边界；
- 仍缺少的企业素材或证据。

用户可以继续、调整或放弃。调整时选择“场景不对、受众不对、表现判断不可信、无法生产、其他”，这些反馈会回到发现策略，但不会直接改写长期配置。

### 21.3 四条用户动线

#### 首次建立发现范围

```text
进入灵感中心
  → 选择产品、市场和沟通对象
  → 系统读取企业资料并推荐少量入口词
  → 用户可选添加对标账号或参考视频
  → Apify 小样本预览
  → 用户确认相关性
  → 保存并开始发现
  → 返回灵感流查看首批候选
```

#### 日常浏览

```text
进入灵感中心
  → 查看新发现的场景和起量候选
  → 按场景浏览或搜索已有内容
  → 收藏／暂不相关／用于创作
  → 系统记录反馈并调整下一轮召回
```

#### 从具体生产任务补充灵感

```text
编导任务发现缺少参考
  → 自动带入产品、市场、受众与缺口
  → 先查已有灵感池
  → 不足时启动任务级小词与关系扩展
  → 返回少量候选和选择理由
  → 编导锁定参考并继续 DirectorBrief
```

用户不需要离开生产任务配置长期关键词。任务级查询默认不写回长期场景，只有多次被采用后，灵感中心才提示“建议长期跟踪”。

#### 从定时任务查看结果

```text
打开采集任务
  → 查看本轮新增、过滤、失败与成本
  → 查看新场景和起量候选
  → 点击候选回到灵感中心
  → 必要时暂停错误分支或调整预算
```

### 21.4 Agent 分工

不新增用户需要配置的“爬虫 Agent”。现有编导 Agent 负责发现目标与采用决策，Apify 和分析能力作为其工具与后台子任务。

产品责任边界明确为：编导 Agent 对“发现什么、为什么采用、如何进入创作”负责；定时任务和 Apify 对“按批准计划执行”负责。

```text
经营 Agent 给出经营目标
  → 编导 Agent 制定发现范围与采集计划
  → 定时任务按计划调用 Apify
  → 编导 Agent 分析、筛选并选择灵感
  → 内容 Agent 按 DirectorBrief 生产
  → 经营 Agent 回收发布与业务结果
```

定时任务不是一个数字员工。它不判断行业方向、不扩大关键词和账号范围、不决定哪些内容值得生产，只执行 `DiscoveryBrief` 中已经确定的平台、来源、频率、回看范围、数量、预算和重试规则。

| 角色／能力 | 输入 | 责任 | 输出 |
| --- | --- | --- | --- |
| 经营 Agent | 经营目标、重点产品、市场、内容结果 | 决定本轮内容目标与资源边界，提供发布后的业务反馈 | `BusinessContentGoal` |
| 编导 Agent | 经营目标、企业事实、发现范围、历史采用结果 | 制定发现计划、发起采集／分析请求、读取执行结果、选择参考、锁定创作目标 | `DiscoveryBrief`、`InspirationHandoff`、`DirectorBrief` |
| Apify 采集工具 | 编导批准的关键词、账号、URL、平台、预算 | 执行真实采集，返回原始字段与运行成本 | `CollectionRunResult` |
| 分析能力 | 视频、图片、元数据与历史快照 | 场景归类、关系扩展、相对表现和创作机制分析 | `CandidateEvidence` |
| 内容 Agent | 已锁定的 `DirectorBrief` 与企业素材 | 执行脚本、分镜、配音、字幕、剪辑和质检 | 样片、成片与质检结果 |

经营 Agent 不直接选爆款；内容 Agent 不自行重新搜索灵感或改写编导目标；Apify 工具不决定哪些内容值得生产。

编导 Agent 在系统内部可以拆成发现范围规划、定时采集编排、场景扩簇、起量候选识别、创作可迁移分析和 `DirectorBrief` 生成等能力，但用户看到的仍是一个对内容方向负责的编导 Agent，不新增“灵感 Agent”或“爬虫 Agent”。

### 21.5 Agent 之间的交接对象

#### `DiscoveryBrief`

由编导 Agent 在采集前形成：

```ts
interface DiscoveryBrief {
  productId: string;
  market: string;
  audience: string;
  discoverySeeds: string[];
  trackedSceneIds: string[];
  competitorAccounts: string[];
  discoveryModes: Array<'momentum' | 'account' | 'innovation'>;
  innovationBriefId?: string;
  platforms: string[];
  lookbackDays: number;
  resultLimit: number;
  budgetLimit?: number;
  productionGap?: string;
}
```

#### `CandidateEvidence`

采集与分析后生成：

```ts
interface CandidateEvidence {
  inspirationId: string;
  discoveryPath: Array<'keyword' | 'account' | 'relation' | 'performance' | 'innovation'>;
  sceneIds: string[];
  relevance: { level: 'high' | 'medium' | 'low'; reasons: string[] };
  momentum: { level: 'rising' | 'high_performance' | 'unknown'; reasons: string[]; confidence: number };
  novelty?: { level: 'high' | 'medium' | 'low'; reasons: string[]; confidence: number };
  transferableMechanisms: string[];
  evidenceRefs: string[];
  limitations: string[];
}
```

不同通道采用不同准入门槛：行业起量素材需要相关性、表现证据和可解释性；对标账号素材需要账号持续价值和内容可解释性；创新素材需要真实来源、业务锚点、新场景／新表达和可迁移性，不强制达到行业头部播放量。通过对应门槛后才生成既有的 `InspirationHandoff`。随后编导 Agent 将企业事实、素材能力和生产目标合并为 `DirectorBrief`，再交给内容 Agent。

### 21.6 自动化程度与人工控制

沿用现有建议、协作、托管三类常用模式：

| 模式 | 系统自动完成 | 人工必须完成 |
| --- | --- | --- |
| 建议 | 生成发现范围、场景和候选建议 | 确认范围、启用采集、逐条选择参考 |
| 协作 | 自动采集和扩簇，高置信候选进入待选区 | 处理新场景、临界表现和生产采用 |
| 托管 | 在预算和已批准范围内自动采集、分析并选少量主参考 | 处理越界场景、事实不足、成本超限和生产审批 |

无论采用哪种模式，新增平台、扩大预算、改变市场／受众、使用未确认竞品或改变权利边界，都必须形成可见变更。普通的同义词扩展和已批准场景内查询不要求逐次确认。

### 21.7 页面状态与闭环

```text
范围待确认
  → 小样本验证
  → 持续发现
  → 新场景待判断
  → 起量候选待采用
  → 编导已采用
  → 内容生产中
  → 成片结果已回流
```

反馈分为三种，避免把所有行为都当正向信号：

- `相关性反馈`：相关／不相关，更新场景和召回通道；
- `创作反馈`：收藏／采用／放弃及原因，更新可迁移判断；
- `经营反馈`：发布后的真实表现和业务结果，更新长期优先级。

外部视频高表现只提高研究优先级；只有企业自己的成片结果才能证明某种场景和创作机制适合自身。

### 21.8 首期需要改动的页面

1. **灵感中心**：增加发现范围栏、场景横条、起量候选分区、“为什么出现”和“不相关”反馈；复用现有卡片、详情、收藏和分析面板。
2. **定时任务**：把自由关键词主入口改成发现范围引用，增加场景、账号、预算和本轮结果摘要；自由补词保留在高级设置。
3. **编导 Agent 设置**：显示默认发现范围和自动化边界，不重复维护关键词。
4. **编导生产页面**：在现有任务上下文中显示参考内容、采用依据、表现置信度和缺失素材；复用继续、调整、放弃。
5. **企业中心**：复用产品导入，增加提取结果的来源、事实／推测状态和纠错，不增加独立关键词页面。

首期不增加新的一级导航，不建设图谱可视化编辑器，也不要求用户理解 Agent 内部步骤。关系图首先用于后台检索、解释与预算调度。

## 22. 基于账号的素材采集逻辑

### 22.1 账号采集的价值

账号采集与关键词采集解决不同问题：

| 方式 | 主要价值 | 主要缺口 |
| --- | --- | --- |
| 关键词采集 | 发现未知内容、新场景和新账号，覆盖面更广 | 结果容易受文字表达影响，可能漏掉标题弱但表现强的内容 |
| 账号采集 | 持续观察一个创作者、品牌或渠道的选题变化、内容系列和相对表现 | 容易形成固定账号偏见，错过新进入者和行业外的新表达 |

账号采集更接近“关注一批稳定信号源”。它可以得到同一账号内更可靠的内容基线，也能看到账号如何连续测试同一个场景、卖点或形式。这对识别“某条内容相对该账号平时明显起量”尤其重要。

两条通道必须形成循环：

```text
关键词找到有效视频
  → 发现高价值账号
  → 账号持续采集发现新场景
  → 新场景生成中词
  → 中词再发现更多账号与内容
```

### 22.2 需要跟踪哪些账号

账号不只等于直接竞品。按照它能提供的信号分为五类：

| 账号类型 | 主要学习内容 | 示例角色 |
| --- | --- | --- |
| 同类品牌／工厂 | 产品卖点、证明方式、上新与商业表达 | 品牌、制造商、OEM／ODM 工厂 |
| 专业创作者 | 用户问题、教程、测评方法和信任表达 | 垂类达人、工程师、教练、化妆师 |
| 渠道账号 | 本地市场语言、价格与购买顾虑 | 经销商、零售商、买手、门店 |
| 用户／评测账号 | 真实使用场景、问题和比较维度 | 测评者、真实用户、维修／安装作者 |
| 行业媒体／展会 | 新产品、新技术、趋势和行业事件 | 行业媒体、协会、展会账号 |

系统还可以保留少量“表达参考账号”，用于学习镜头、节奏和结构，但必须与事实参考账号分开。表达参考不能成为产品参数、用户效果或企业能力的依据。

### 22.3 账号从哪里来

账号来源分为三类：

1. **用户提供**：企业已知竞品、客户、经销商、行业达人和参考账号。直接进入候选／试采队列，并显示账号角色供用户确认；用户明确固定的账号才直接进入长期跟踪。
2. **内容反推**：关键词或场景采集命中高相关、高表现视频后，将作者加入候选账号。
3. **关系发现**：使用 Apify Actor 实际返回的关联账号、提及、合作作者或同一话题高频作者。没有真实字段时不推断平台关系。

系统可以自动试采候选账号最近少量内容，但只有达到跟踪门槛后才进入长期定时任务。试采不等于确认其为竞品。

### 22.4 账号是否值得长期跟踪

不用粉丝数或单条最高播放量直接决定。每个账号按以下证据判断：

- 与当前产品、市场和沟通对象的相关度；
- 最近内容中有效灵感的命中率；
- 是否持续产生新场景，而不是长期重复；
- 是否出现相对账号自身基线突出的内容；
- 内容中的创作机制是否能够解释和迁移；
- 作者身份、来源和字段是否稳定可获得；
- 采集成本、失败率和重复率是否可接受。

账号状态分为：

```text
候选账号
  → 试采观察
  → 长期跟踪
  → 降频观察
  → 停止跟踪
```

连续产生有效灵感的账号提高频率；长期无新内容、重复率高或与业务偏离的账号降频，而不是立即删除历史数据。

### 22.5 账号采集计划

账号采集按增量执行，不在每次任务中重复拉取完整主页：

- 保存每个平台账号 ID、主页 URL、最近成功采集时间和最新内容标识；
- 每次只取最新内容，并按来源 URL／内容 ID 去重；
- 根据账号真实发布频率调整检查周期；
- 新账号先小批量回看，长期账号只做增量；
- 对新内容先做低成本元数据和快速解读；
- 只有相对表现突出、命中新场景或被任务召回时才升级深度分析；
- 每个账号、每个平台设置单次结果与成本上限。

定时任务可以同时包含关键词通道和账号通道，但运行记录必须分别统计新增量、有效率、起量候选数、重复率和成本，才能判断哪条通道有价值。

### 22.6 账号采集的前端交互

“发现范围”抽屉增加“参考账号”区域：

```text
长期跟踪
[品牌 A · 同类品牌] [达人 B · 专业创作者] [经销商 C · 德国渠道]

系统新发现
[账号 D · 来自“妆前卡粉”场景 · 3 条高表现候选]
[持续跟踪] [先观察] [不相关]
```

账号卡片显示：平台、名称、用户确认的角色、发现来源、相关场景、近期新增、有效灵感数、相对起量候选数、上次采集和下次计划。首屏不堆粉丝数和全部历史指标。

用户可以：

- 粘贴账号主页或从已有对标账号选择；
- 确认／修改账号角色；
- 持续跟踪、降频、暂停或标记不相关；
- 查看该账号贡献了哪些场景和被采用内容；
- 将账号的一条视频设为种子内容，继续做关系扩展。

不建设独立“账号监控”一级页面。账号作为发现范围的一部分，在灵感中心管理，在定时任务查看执行状态。

### 22.7 编导 Agent 如何使用账号

编导 Agent 负责：

1. 根据产品、市场和沟通对象提出首批账号类型，而不是凭空编造具体账号；
2. 读取用户已有账号和关键词采集产生的候选作者；
3. 提交账号试采请求，由定时任务调用 Apify，随后读取结果判断是否值得长期跟踪；
4. 从账号近期内容中识别新场景、相对起量内容和重复成功的创作机制；
5. 将新场景交回关键词／场景图谱，将合格视频交给 `InspirationHandoff`；
6. 根据采用率和成片结果调整账号频率。

经营 Agent 只提供目标和预算；定时任务按计划调用 Apify；内容 Agent 不直接关注账号或从账号主页自行挑选素材。

### 22.8 账号与关键词的联合排序

候选视频进入同一个灵感池，但保留召回来源：

```ts
type DiscoveryPath =
  | { type: 'keyword'; seedId: string; sceneId?: string }
  | { type: 'account'; accountId: string }
  | { type: 'relation'; parentInspirationId: string; relationType: string }
  | { type: 'innovation'; innovationBriefId: string; signalId?: string };
```

同一内容若同时被关键词和账号通道命中，只保存一条内容，并叠加发现依据。多通道命中可以提高“与当前发现范围相关”的可信度，但不能直接提高爆款判断；爆款仍依据平台内表现和时间数据判断。

首期至少分别回答两个运营问题：

- 哪些场景词持续带来可用灵感；
- 哪些账号持续带来可用灵感。

这样才能逐步将采集预算从低效词和低效账号移向真正支持编导生产的来源。

### 22.9 对标账号的三条发现路径

对标账号不应只从爆款素材反推。当前数据采集统一以 Apify 为主，不接订单、GMV 或实时成交数据，因此账号发现只依赖能够从社媒公开页面持续获得的证据。系统并行使用三条路径：

1. **内容反推路径**：关键词、场景或相关推荐命中高价值内容，再聚合作者并试采主页；
2. **用户指定路径**：用户提供已知竞品、优秀品牌、厂家、经销商或创作者账号，系统直接试采；
3. **公开稳定表现路径**：账号长期保持稳定的浏览、互动和发布，或者评论区持续出现消费需求／采购意图，进入候选。

三条路径最终汇入同一个候选池，并保留发现来源。系统不推断账号销量或成交能力，也不把公开互动描述为真实成交。

#### 先识别用户经营画像，再选择指标口径

账号采集计划不能先抓数据、再猜用户需要什么。初始设置先确认用户经营模式、产品、市场和目标对象，随后加载对应的账号评价模板：

| 用户画像 | 主要内容目标 | 对标账号重点 |
| --- | --- | --- |
| B2C 品牌 | 触达消费者、建立兴趣和促进购买决策 | 稳定触达、互动质量、消费者问题与反馈、内容迁移价值 |
| 海外 B2B 厂家 | 吸引采购商、经销商或品牌客户咨询 | 疑似采购意图、专业证明、稳定互动、持续发布 |
| B2B2C／渠道型 | 同时影响渠道和终端消费者 | 将渠道采购信号与消费者反馈分开统计 |

初始信息至少包括：

- 经营模式：B2B、B2C 或 B2B2C；
- 产品／品类和目标国家／语言；
- 目标对象：消费者、采购商、经销商、品牌方或其他角色；
- 内容目标：消费兴趣、采购咨询、代理合作、品牌曝光或组合目标；
- 用户已经知道的竞品、优秀账号和需要排除的账号。

这些信息优先复用企业中心已有资料，缺失项在首次创建采集计划时集中补齐。用户可以修改画像；修改后系统重新计算账号评价，不删除已经采集的原始证据。

同样的公开数据在不同画像下含义不同。例如，C 端账号的一万次播放需要结合收藏、消费者问题和使用反馈判断；B2B 厂家即使播放较低，只要评论中稳定出现 MOQ、报价、样品、认证或代理问题，也可能具有较高参考价值。

#### C 端品牌账号：重点判断消费者内容能力

直接面向消费者的品牌即使没有单条超级爆款，只要持续产出相关内容、获得稳定触达，并在评论区反复出现消费者问题和使用反馈，就值得进入候选。系统判断的是“公开内容是否值得借鉴”，不判断该品牌实际卖了多少货。

| 证据层 | 可用信号 | 使用限制 |
| --- | --- | --- |
| 内容表现 | 浏览量、点赞、评论、分享、收藏、发布频率及相对账号基线 | 跨平台绝对值不可直接比较，应优先看同平台、同账号的时间序列 |
| 消费者反馈 | 评论中的使用场景、痛点、效果反馈、购买问题和复购表达 | 评论是公开需求信号，不是订单证据 |
| 创作价值 | 是否反复使用有效钩子、产品证明、场景和内容形式 | 需要由编导 Agent 判断能否迁移到当前产品 |

#### 海外 B2B 厂家账号：重点判断稳定获客能力

B2B 厂家的内容不一定产生消费品式的大播放，但如果持续吸引经销商、采购商或渠道商评论和咨询，或者在较小粉丝基数上保持稳定互动，就可能具有更高的业务参考价值。

系统需要将评论区区分为：

- **强询盘信号**：明确询问 MOQ、报价、样品、交期、认证、规格、定制、代理、批发、运输或联系方式；
- **弱采购信号**：表达合作、分销、进口、采购兴趣，但缺少明确需求；
- **普通互动**：泛赞美、表情、抽奖参与、互粉和无关评论；
- **风险互动**：机器人、重复模板、广告和明显垃圾评论。

仅凭公开评论，系统只能标记为“疑似询盘”，并记录语言、意图类别、证据文本和置信度。编导 Agent 可以据此学习厂家如何呈现产能、认证、工艺、交期和合作条件，但不能把疑似询盘数量直接写成有效询盘或成交能力。

#### Apify 数据可用边界

不同平台和 Actor 返回字段不同，产品不能假定每条内容都有全部指标。账号判断按实际返回字段降级：

| 数据 | 用法 |
| --- | --- |
| 账号 ID、主页、粉丝数、发布时间 | 作者去重、账号体量和更新稳定性 |
| 视频 ID、标题／文案、浏览、点赞、评论数、分享／收藏 | 内容表现和账号基线；缺失字段保持空值 |
| 评论正文、评论时间、评论点赞与回复 | 消费需求／采购意图理解；需要单独调用评论采集 Actor |
| 评论总数但无正文 | 只能计算互动量，不能判断询盘或消费者痛点 |
| 订单、GMV、实时成交 | 当前不采集、不展示、不参与评分 |

关键词／账号 Actor 与评论 Actor 应拆成两级任务：先低成本采集账号和内容指标，只有进入候选的账号及其代表内容才抓取有限数量评论。这样才能控制 Apify 结果费、代理和模型分析成本。

完整处理动线为：

```text
确认用户画像与目标
  → 选择 B2C／B2B／混合指标模板
  → Apify 采集账号和内容公开指标
  → 用账号基线、相关性和稳定性筛出候选
  → Apify 采集候选账号代表视频的评论正文
  → 模型识别消费者需求或疑似采购意图
  → 编导 Agent 判断可借鉴的场景、证明和表达方式
  → 进入长期跟踪、继续观察或停止
```

字段缺失时必须按能力降级：

```text
只有播放、点赞、评论数 → 只能判断公开内容表现
有一段时间的账号内容 → 可以判断账号基线和更新稳定性
有评论正文 → 可以识别消费者需求或疑似采购意图
有多期评论正文 → 可以判断相关信号是否持续
没有订单数据 → 不展示、不估算、不参与评分
```

评论分析必须遵守三个口径：

```text
评论总数不等于已经取得评论正文
评论正文不等于有效询盘
疑似询盘不等于成交
```

#### 各类账号共用的基础指标

共性指标包括浏览量、粉丝量、发布频率、点赞、评论、分享以及可获得时的收藏数。产品上不采用单个绝对阈值，而是形成四组派生指标：

```text
触达能力：近期内容浏览量中位数、浏览量／粉丝量
互动质量：（赞 + 评论 + 分享 + 收藏）／浏览量，以及有效评论占比
稳定程度：近 30／60／90 天内容的中位数、波动范围和持续发布情况
业务相关性：相关内容占比、疑似询盘率、产品／市场／受众匹配度
```

粉丝量用于理解账号体量，不能单独决定是否值得对标；浏览量用于判断触达，也要同时看发布时间和账号自身基线。对 C 端品牌提高消费者反馈、内容迁移和稳定触达的权重；对 B2B 厂家提高疑似询盘质量、专业证明和稳定性的权重。

建议为发现证据补充结构：

```ts
type AccountDiscoverySource =
  | 'content_hit'
  | 'user_nominated'
  | 'stable_performance'
  | 'inquiry_signal'
  | 'competitor_or_channel_list';

interface AccountDiscoveryEvidence {
  source: AccountDiscoverySource;
  metric?: string;
  value?: number | string;
  period?: string;
  provenance: string;
  confidence: number;
  observedAt: string;
}
```

### 22.10 从关键词结果发现高价值作者

不能因为某条关键词结果播放高，就直接把作者升级成长期对标账号。正确路径是“内容命中 → 作者聚合 → 主页试采 → 账号画像 → 持续价值判断”。

```text
关键词／场景采集命中视频
  → 规范化作者身份
  → 聚合同一作者的多条命中记录
  → 触发账号试采
  → 建立近期内容与账号基线
  → 判断账号角色、持续相关性和生产价值
  → 晋级长期跟踪，或继续观察／淘汰
```

#### 第一步：从视频提取稳定作者实体

每条采集结果需要尽量保存平台账号 ID、主页 URL、handle、展示名称和作者头像。账号唯一键优先使用 `platform + platformAccountId`；拿不到平台 ID 时才使用规范化主页 URL。展示名称不能作为唯一键，因为名称可能重复或变化。

同一作者在多个关键词、场景或任务中被命中时，合并到一个 `AuthorCandidate`，保留每次发现路径：

```ts
interface AuthorDiscoveryEvidence {
  inspirationId: string;
  keywordSetId?: string;
  sceneId?: string;
  query?: string;
  discoveredAt: string;
  relevanceReasons: string[];
  momentumLevel: 'rising' | 'high_performance' | 'unknown';
}
```

#### 第二步：决定是否值得试采主页

满足以下任一条件，可以进入小批量试采，但仍不等于长期跟踪：

- 多个相关查询或场景反复命中同一作者；
- 一条高表现候选与当前产品、市场和受众高度相关；
- 用户收藏、用于创作或手动标记“关注作者”；
- 已确认竞品、经销商、专业作者或行业媒体；
- 编导 Agent 需要判断该视频是一次偶然，还是账号持续能力。

试采读取账号最近一段内容，用于建立账号画像。只出现一个偶然爆款、但其他内容完全无关的作者，不应自动晋级。

#### 第三步：建立账号价值向量

“高价值作者”不是一个只由粉丝数或播放量组成的总分，而是一组可以解释的判断：

| 判断维度 | 要回答的问题 | 所需证据 |
| --- | --- | --- |
| 主题持续相关性 | 近期是否持续覆盖当前产品、场景或受众 | 多条近期内容的场景命中与占比 |
| 起量发现价值 | 是否反复产生相对自身基线突出的内容 | 同账号近期样本、发布时间与公开表现 |
| 场景发现价值 | 是否持续带来词库中没有的新问题和使用场景 | 新场景贡献与后续验证结果 |
| 创作迁移价值 | 钩子、证明、结构和形式是否能够被分析和迁移 | 深度分析与编导采用记录 |
| 市场与对象匹配 | 语言、地区、受众和商业角色是否符合当前范围 | 账号资料、内容语言、渠道与场景 |
| 原创与来源可信度 | 是原创、品牌官方、专业作者还是搬运聚合 | 账号身份、重复内容和来源关系 |
| 更新稳定性 | 是否仍在持续发布，是否有足够新内容 | 发布时间序列与增量采集结果 |
| 采集可用性 | Apify 是否能稳定取得内容和必要字段 | 成功率、字段完整率、重复率与成本 |

不同角色采用不同侧重点：品牌／工厂账号重产品事实和证明方式；专业创作者重问题洞察和内容迁移；经销商重本地市场与购买语言；行业媒体重新品和趋势。不能用同一个播放量公式评价所有账号。

#### 第四步：账号晋级与降级

账号先经过硬门槛，再考虑长期价值：

1. 作者身份能够稳定去重；
2. 与当前产品、市场或沟通对象存在可解释关系；
3. 近期不止一条内容能够贡献有效场景、起量候选或创作参考；
4. 不是明显的重复搬运、无关聚合或失效账号；
5. Apify 采集成本和字段完整度在允许范围内。

通过后，编导 Agent 记录晋级理由并进入 `tracked`。后续若长期无有效内容、重复率过高、角色发生变化或采集成本失控，先降频到 `watching`，再决定是否停止。

```ts
type AccountTrackingStatus =
  | 'candidate'
  | 'trial'
  | 'tracked'
  | 'watching'
  | 'stopped';
```

### 22.11 数字员工跑通账号晋级所需的 Gap

当前系统已经具备对标账号的人工保存、删除、主页采集、最近采集时间／数量，以及部分内容的账号内公开表现基线。但当前账号记录主要是 URL、名称、handle、头像、备注和最近采集结果，还不足以支持编导 Agent 自动晋级。

| Gap | 当前不足 | 需要补充 |
| --- | --- | --- |
| 作者稳定身份 | 展示名和 URL 容易变化，跨次结果可能无法可靠合并 | 平台账号 ID、规范化主页、别名历史、合并记录 |
| 发现路径 | 账号无法解释由哪个词、场景、视频或任务发现 | `AuthorDiscoveryEvidence` 与首次／最近发现来源 |
| 询盘识别 | 评论数无法区分真实采购意图和普通互动 | 评论正文采集、意图分类、多语言词表、垃圾过滤、证据文本和置信度 |
| 账号角色 | 只有“对标账号”概念 | 品牌、工厂、达人、经销商、用户、媒体、表达参考等角色及置信度 |
| 试采状态 | 保存后基本直接成为可采账号 | `candidate → trial → tracked → watching → stopped` 状态机 |
| 内容历史 | 只有最近采集时间和新增数量 | 账号内容时间序列、最新内容标识、增量游标和去重历史 |
| 账号基线 | 部分视频可计算临时公开基线，但未形成稳定账号画像 | 按平台保存样本期、指标口径、中位表现、分布和更新时间 |
| 持续相关性 | 无账号级场景覆盖与命中率 | 近期内容的场景分布、相关内容比例和变化趋势 |
| 新场景贡献 | 无法知道账号是否真正扩展了灵感池 | 新节点贡献、验证通过率及被长期采用情况 |
| 创作价值 | 无账号级收藏、采用和成片反馈 | 账号贡献内容的打开、收藏、采用、放弃原因和企业成片结果 |
| 原创与搬运判断 | 高播放聚合号可能被误升为高价值账号 | 内容重复、首发线索、品牌／作者身份与来源可信度 |
| 市场与受众 | 缺少语言、地区、受众和渠道角色 | 账号画像字段及其证据来源 |
| 成本与可靠性 | 只看到单次采集结果 | 账号级成功率、空跑率、字段完整率、平均成本和熔断状态 |
| 决策审计 | Agent 无法解释为什么关注或停用 | 晋级／降级理由、使用的证据、策略版本和操作者 |

### 22.12 编导 Agent 的账号决策协议

编导 Agent 每次处理作者候选时输出结构化决定：

```ts
interface AccountTrackingDecision {
  accountId: string;
  decision: 'trial' | 'track' | 'watch' | 'stop';
  accountRole: string;
  reasons: string[];
  evidenceVideoIds: string[];
  relatedSceneIds: string[];
  missingEvidence: string[];
  nextReviewAt?: string;
  recommendedCadence?: string;
  confidence: number;
}
```

自动化模式决定谁确认：

- **建议模式**：Agent 推荐试采与长期账号，用户确认；
- **协作模式**：Agent 可自动试采，长期晋级和停用由用户确认；
- **托管模式**：Agent 可在已批准市场、角色和预算内自动晋级、降频，越界账号和身份不清账号交给用户；
- 无论何种模式，用户手动添加、固定或屏蔽的账号优先级最高。

账号决策完成后，定时任务读取三类对象执行 Apify：本轮获准小批量试采的 `trial`、持续增量采集的 `tracked`，以及到期需要复核的 `watching`。`trial` 使用单独的账号数、每账号内容数和成本上限。采集完成后由编导 Agent 更新账号证据和下次决策，不由调度器自行改变账号状态。

### 22.13 最关键的首期补齐顺序

1. 统一保存平台作者 ID、主页 URL和内容到作者的稳定关联；
2. 保存“内容命中／用户指定／稳定表现／询盘信号 → 作者”的发现路径；
3. 增加候选、试采、跟踪、观察、停止状态；
4. 建立账号近期内容样本和平台内表现基线；
5. 增加账号角色、场景覆盖、有效内容率和采集成本；
6. 记录编导 Agent 的晋级／降级理由；
7. 最后接入收藏、采用和企业成片结果，形成长期价值反馈。

完成前四项后，数字员工才具备从关键词结果中“发现并验证账号”的基础能力；完成全部七项后，才具备自动维护长期对标账号池的闭环。

## 23. 每日 10—20 条素材下的账号积累周期与成本

### 23.1 计算口径

本节将“每天采集 10—20 条素材”解释为：经过来源去重、基础相关性过滤后，最终进入用户灵感池的有效不重复素材，而不是 Apify 返回的原始行数。这 10—20 条可以由行业起量、对标账号和创新参考三类内容共同组成。

按每月 30 天计算：

```text
有效入库素材：300—600 条／月
```

如果 10—20 条指的是原始抓取量，而不是有效入库量，则以下账号积累速度需要按实际有效率等比例下调。

### 23.2 从素材到长期账号的漏斗

长期账号不能由一条高播放内容直接产生；同样也不需要全部等待爆款素材反推。账号池由“素材反推候选”和“账号直接候选”共同形成。直接候选包括用户指定的品牌／厂家／经销商、稳定获得消费需求或疑似询盘的账号，以及公开表现长期稳定的账号。

只计算素材反推路径时，用于首轮预算的基准假设为：

| 环节 | 基准假设 | 300 条素材 | 600 条素材 |
| --- | --- | ---: | ---: |
| 有效不重复素材 | 用户可浏览的真实候选 | 300 | 600 |
| 去重后的独立作者 | 约 50%—65% 的内容来自不同作者 | 150—195 | 300—390 |
| 触发账号试采 | 约 15%—25% 的独立作者具备重复命中、高表现、人工收藏或角色价值 | 23—49 | 45—98 |
| 通过试采成为长期账号 | 约 30%—40% 的试采账号具备持续相关性、基线价值和采集稳定性 | 7—20 | 14—39 |

这些比例是产品预算假设，不是已经验证的业务事实。上线后必须用真实漏斗替换。

表中的 300／600 条必须解释为“适合反推同行账号的素材”，不能直接使用三类灵感的总入池量。跨行业／跨场景的创新参考虽然可以贡献创作方法，其作者通常不是本行业长期对标账号，应从账号反推漏斗的分母中排除。若账号可发现素材占总入池量的比例为 `p`，表中各数量需要整体乘以 `p`：

```text
账号可发现素材量 = 总有效素材量 × p
```

创新参考已确定占总有效素材的 10%—20%，因此账号可发现素材的理论上限为 80%—90%；如果其余内容缺少稳定作者字段或与长期账号跟踪无关，真实 `p` 还会更低。下面原始区间适用于“每日 10—20 条均为账号可发现素材”的上界场景；按创新占比折算后的规划区间另列一行。

直接候选应单独计算：假设用户初始提供 5—10 个明确账号，系统再通过竞品／渠道名单和公开稳定表现发现 10—25 个候选；其中约 40%—60% 通过试采，则首月可额外形成约 6—21 个长期账号。这里的数量不占用每日 10—20 条灵感素材额度，但会增加账号试采成本。

按基准中位数估算：

```text
10 条／天：素材反推每月约形成 10—12 个长期账号
20 条／天：素材反推每月约形成 20—24 个长期账号
直接候选路径：首月可额外形成约 6—21 个长期账号
```

只靠素材反推，数学上达到 30 个账号分别约需 2.5—3 个月和 1.25—1.5 个月。加入直接候选后，候选数量通常不再是主要限制；但账号仍需两到三次主页采集验证持续价值，因此不能承诺在首次发现时立即形成 30 个可信账号。

综合数量与观察周期，建议对外使用以下区间：

| 日有效素材 | 达到 30 个可信长期账号的基准时间 | 说明 |
| --- | --- | --- |
| 10 条／天均可用于账号反推 | 8—14 周 | 上界场景；数量积累是主要限制 |
| 20 条／天均可用于账号反推 | 5—9 周 | 上界场景；观察周期成为主要限制 |
| 创新参考占 10%—20%，其余内容均可反推账号 | 约 9—18 周（10 条／天）；约 6—11 周（20 条／天） | 仍是偏乐观估算；作者字段缺失会继续拉长 |
| 素材反推 + 15—35 个直接候选 | 4—8 周 | 主要等待账号试采与持续性验证 |
| 高度垂直、作者重复或 Apify 字段不足 | 3—5 个月 | 独立作者和试采通过率会明显下降 |

“30 个账号”也不应成为机械 KPI。如果前 15 个账号已经稳定贡献大部分有效灵感，继续凑数会提高成本并稀释质量。

### 23.3 原始抓取量

为了每天获得 10—20 条有效不重复素材，不能只抓 10—20 条原始结果。首期可按 25%—40% 的有效入库率预算：

```text
每天有效 10 条 → 原始抓取约 25—40 条
每天有效 20 条 → 原始抓取约 50—80 条
每月关键词／关系召回原始行数约 750—2,400 条
```

账号发现还会产生额外行数。加入用户指定、稳定互动和疑似询盘信号后，候选来源更多，但每个候选仍采用同一套小样本试采：

- 每月试采约 20—100 个候选账号；
- 每个候选首次读取约 8—12 条近期内容；
- 增加约 160—1,200 条账号试采结果；
- 已晋级账号采用增量采集，首月按平均 15 个活跃跟踪账号、每周每账号最多 5 条新内容计算，约 300 条结果。

因此首月每用户的 Apify 视频／账号结果量建议按约 1,200—3,900 行预算，而不是只按 300—600 条最终素材计费。若启用评论正文采集，还要另加“候选账号数 × 代表视频数 × 每条视频评论上限”的评论结果量；评论 Actor 可能采用不同计费事件，不能混入视频结果行数直接套同一单价。

### 23.4 Apify 采集成本

不同 Actor、套餐和事件类型差异很大，不能用一个固定单价。当前公开价格示例包括：

- YouTube Scraper 约 $2.40—$5／1,000 个视频；
- TikTok 不同 Actor 和模式约 $2.50—$12.50／1,000 个结果；
- Instagram 常见约 $1.30—$2.70／1,000 个结果；
- Facebook 官方 Actor 公开说明约 $5—$8／1,000 个帖子，其他 Actor 可能更低。

以混合平台的综合结果单价 $2.50—$8／1,000 行做预算，1,200—3,900 行约为：

```text
Apify 结果费：约 $3—$31／用户／月
```

这只是边际结果费。还需考虑 Apify 套餐最低月费、Actor 启动费、代理、存储、失败重试和部分 Actor 的附加事件。多个用户共享同一 Apify 套餐时，套餐费应按总体并发和用量分摊，不能给每个用户重复计算一份完整套餐。

### 23.5 分析成本必须分层

如果 300—600 条素材全部下载并做深度视频分析，成本会显著增加。推荐分四层：

| 层级 | 处理对象 | 每月数量示例 | 处理内容 |
| --- | ---: | ---: | --- |
| L0 元数据过滤 | 1,200—3,900 条原始结果 | 全部 | 去重、时间、作者、公开指标、标题与描述 |
| L1 快速理解 | 300—600 条有效素材 | 全部入库素材 | 优先使用来源封面／预览、短文本、粗场景和相关性 |
| L2 策略分析 | 有效素材的约 15%—25% | 45—150 条 | 钩子、结构、证明、节奏和可迁移性 |
| L3 精确分析 | 有效素材的约 5%—10% | 15—60 条 | 连续时间线、分镜动作、声音与生产约束 |

账号试采阶段默认只做 L0 和有限 L1，不对候选账号的所有历史视频做 L2／L3。

Qwen 模型本身按 Token 或音频时长计费。公开价中，`qwen3-vl-flash` 低阶输入为人民币 0.15 元／百万 Token、输出 1.5 元／百万 Token；`qwen3-asr-flash-filetrans` 中国内地输入为 0.00022 元／秒。实际视频帧会产生多少 Token 取决于抽帧数量、分辨率和提示词，必须记录真实账单，不能只用模型单价反推总成本。

L3 是从 L2 中继续升级的子集，不应把 45—150 条 L2 与 15—60 条 L3 相加为独立视频数。真正容易失控的是视频下载和代理流量。例如部分下载 Actor 按成功视频计费，部分按 MB、视频秒数或代理流量计费。若按每条需要策略／精确分析的视频综合下载成本 $0.08—$0.25 做暂估，45—150 条唯一视频约为：

```text
下载与媒体传输：约 $4—$38／用户／月
```

### 23.6 每用户月度边际成本区间

在分层分析成立、短视频为主、只下载 L2／L3 内容的前提下：

| 成本项 | 月度区间 |
| --- | ---: |
| Apify 视频元数据与账号试采 | $3—$31 |
| Apify 评论正文采集 | 未包含在上述区间；按所选评论 Actor、候选视频数和评论上限单独核算 |
| 视频下载、代理和媒体传输 | $4—$38 |
| Qwen 快速／策略／精确分析 | 建议先按 ¥5—¥30 预留，再以真实 Token 和时长校准 |
| 存储、队列与失败重试 | 建议在前述美元成本上增加 15%—25% 运维缓冲 |

因此，首期合理的边际预算不是“几美元”，而是：

```text
不启用评论正文采集的基准：约 $15—$60／用户／月，另加少量人民币模型费用
不启用评论正文采集的保守上限：约 $30—$100／用户／月
```

启用评论正文采集后，必须在这一区间上追加评论 Actor 和评论理解成本。只有确定平台、Actor、每个账号抽取的视频数和每条视频评论上限后，才能给出新的总价。如果下载并深度分析全部 300—600 条素材、抓取大量评论、使用高分辨率视频或频繁全量回抓账号，成本可能明显超过 $100／用户／月。

### 23.7 降本关键点

1. 原始结果先做 URL、内容 ID、作者和相似内容去重，再调用模型；
2. 作者聚合使用已有元数据，不为每条视频单独查询作者主页；
3. 候选账号只试采 8—12 条，晋级后才进入增量跟踪；
4. L1 使用封面、少量帧和文本，只有 L2／L3 下载视频；
5. 同一个视频被关键词、账号和关系通道重复命中时只分析一次；
6. 账号基线数据复用，不在每轮重复抓完整历史；
7. 为每个用户设置原始结果、试采账号、深度分析和美元成本四类月度额度；
8. 每次运行记录 Actor、事件数、媒体字节、模型 Token、音频秒数和最终有效素材数。

### 23.8 上线后必须验证的五个参数

成本与账号周期最终取决于以下真实参数：

```text
有效入库率
独立作者率
候选作者试采率
试采账号晋级率
每条 L1／L2／L3 的真实成本
```

首批用户运行两到四周后，应按行业、平台和 Actor 分别回算这些参数。只有完成这一轮校准，产品才能给出可信的套餐额度和“预计多久形成 30 个对标账号”的提示。

账号周期还需要额外记录：账号可发现素材占比、直接候选数量、各发现来源的试采通过率，以及疑似询盘分类的抽样准确率。系统只依据 Apify 返回的公开评论判断“疑似采购信号是否持续”，不把它描述为真实询盘或成交能力。

## 24. 评论 Actor 的首轮选型与测试策略

### 24.1 Actor 在本方案中的含义

本文中的 Actor 均指 Apify Actor，即运行在 Apify 平台上的具体采集程序，不是编导 Agent、内容 Agent 或数字员工。灵枢负责形成任务参数、预算和字段要求；Actor 负责访问目标平台并返回结构化结果；定时任务负责调用和记录运行；编导 Agent 读取结果并作出内容与账号判断。

```text
编导 Agent 形成采集要求
  → 定时任务提交平台 URL、数量和费用上限
  → Apify Actor 执行采集
  → 返回 Dataset、运行状态和费用事件
  → 灵枢完成字段校验、保存与分析
```

不同 Actor 的输入 schema、支持对象、返回字段、失败方式和计费事件可能完全不同。视频／账号 Actor 返回主页、帖子和公开指标；评论 Actor 返回评论正文、评论 ID、时间、点赞和回复关系。只有评论总数而没有评论正文时，系统不能识别消费者痛点或疑似采购意图。

### 24.2 评论 Actor 第一轮候选

2026-09-23 读取 Apify 公开 Actor 元数据后，首轮候选为：

| 平台 | 候选 Actor | 免费套餐当前公开事件价 | 单视频 20 条评论估算 | 第一轮判断 |
| --- | --- | ---: | ---: | --- |
| YouTube | `apihq/youtube-comments-scraper` | `$0.0004／条` | `$0.008` | 价格低；重点验证评论关闭、失败行和时间字段 |
| TikTok | `automation-lab/tiktok-comments-scraper` | 启动 `$0.005` + `$0.003／条` | `$0.065` | 四者单条最贵；只做候选内容抽样，首轮不抓回复 |
| Instagram | `apidojo/instagram-comments-scraper-api` | 每帖子 `$0.0075`，含前 15 条；之后 `$0.0005／条` | `$0.010` | 重点验证 Reels、分页、重复和地区差异 |
| Facebook | `apify/facebook-comments-scraper` | 启动约 `$0.001` + `$0.0025／条` | `$0.051` | 首轮优先官方 Actor 的成熟度，不先追求最低社区报价 |

四个平台各测试一条公开视频、每条最多 20 条顶级评论，预计事件费合计约 `$0.134`。价格会随 Actor 和套餐变化，生产系统不能永久写死本表价格，应记录每次运行实际发生的收费事件。

### 24.3 冒烟测试方法

每个平台选择一条未登录也能访问、页面可见至少 30 条评论的公开视频。首轮统一限制：

```text
视频数：1／平台
最大评论数：20／视频
回复：关闭
排序：top／ranked；不支持时记录 Actor 默认值
最大运行费用：$0.10／Actor
超时：5 分钟
```

验收至少包括：

1. 评论 ID、正文、父评论 ID和来源视频 ID／URL；
2. Unicode、emoji 和多语言文本是否原样返回；
3. 评论时间、点赞数和回复数是否存在，缺失时是否保持空值；
4. 同一输入重复运行时能否使用评论 ID 去重；
5. 评论关闭、内容删除、访问受限和结果不足时是否返回可解释状态；
6. Actor run ID、状态、耗时、结果数、收费事件和实际美元费用；
7. 20 条上限是否生效，单次费用是否保持在 `$0.10` 以内。

YouTube 和 Facebook 的最终参数名必须在运行前读取 Actor 当前 input schema；不能照搬其他 Actor 的字段。详细输入示例和字段验收清单见 [Apify评论Actor第一轮确认-2026-09-23.md](./Apify评论Actor第一轮确认-2026-09-23.md)。

### 24.4 生产中的评论抽样策略

评论采集不覆盖全部入池视频，而只服务两类任务：验证候选账号是否持续出现消费者需求／疑似采购信号，以及从内容和评论中发现新的问题与场景。

```text
先用视频和账号公开指标筛选
  → 选择候选账号的代表视频
  → 每条先抓 20 条顶级评论
  → 有价值但证据不足时增加到 50 条
  → 只有需要理解对话上下文时才抓回复
```

假设 30 个长期账号，每周每账号选择一条代表视频、每条最多 20 条评论：

```text
30 个账号 × 4 周 × 20 条 = 2,400 条评论／用户／月
```

若四个平台平均分布，按本轮免费套餐事件价估算，评论采集约 `$3.9／用户／月`：

| 平台 | 约 600 条评论的费用 |
| --- | ---: |
| YouTube | `$0.24` |
| TikTok | 约 `$1.82`，含每周一次批量启动费 |
| Instagram | 约 `$0.30`，按每条代表视频 20 条估算 |
| Facebook | 约 `$1.50`，另加少量启动费 |

该估算不包括评论模型理解、失败重试和回复采集。TikTok 评论占比过高、每条视频抓取 100—500 条、默认抓回复或对全部素材抓评论，都会明显提高成本和噪声。

当前工作区没有配置 `APIFY_TOKEN`，因此本轮已经完成候选 Actor、公开字段、当前事件价格、公开运行统计和测试方案确认，但尚未产生真实运行记录或账单。配置 Token 后应先按第 24.3 节执行总预算约 `$0.15` 的四平台冒烟测试，再用真实业务候选账号运行一周。
