> 产品方案版本：v1.0
> 存档日期：2026-08-24
> 文档状态：目标架构已确认，P0–P5 产品能力已完成本地开发
> 本地代码基线：`codex/three-environment-deployment` / `adf1996`
> 包版本：`package.json` 为 `0.1.0`；仓库当前没有 Git tag
> 实施进度：P0–P5 已于 2026-08-24 完成本地开发、全量回归、生产构建和页面验收；P5 采集与看板已就绪，真实客户试点数据仍待后续采集

## 1. 决策摘要

不再把“产品发现、需求澄清、报价、信任、风险处理”等内容合并成固定的线性八节点。

灵小枢智能客服采用七个相互独立、可以分别更新的状态维度：

1. 生命周期（Lifecycle）
2. 当前意图（Intent）
3. 交易证据（Deal Evidence）
4. 知识状态（Knowledge）
5. 权限与风险（Authority & Risk）
6. 商务文档（Artifacts）
7. 渠道与会话归属（Channel & Ownership）

阶段推进必须由可观察事件触发，例如“报价已审批并发送”“样品已确认”“收到 PO”“PI 已确认”“付款已收到”。模型可以识别和建议事件，但高风险阶段与商务承诺不能仅凭模型推断直接写入。

```text
对话状态 =
生命周期
× 当前意图
× 交易证据
× 知识状态
× 权限与风险
× 商务文档
× 渠道与会话归属

回复策略 =
先回答客户当前问题
+ 最多一个主要推进动作
+ 必要的审批、转人工或安全降级
```

## 2. 为什么不用固定八节点

原八节点同时混合了四种不同概念：

| 原内容 | 实际性质 | 新架构归属 |
|---|---|---|
| 产品发现、需求澄清 | 客户意图与发现动作 | 意图 + 交易证据 |
| 采购资格判断 | 信息完整度与商机判断 | 交易证据 |
| 产品与能力验证 | 部分业务需要的可选流程 | 生命周期可选阶段 + 知识 + 文档 |
| 信任、资质 | 客户意图、知识证据与风险 | 意图 + 知识 + 文档 + 风险 |
| 样品与报价 | 两类不同业务事件 | 可选验证阶段 + 报价阶段 |
| 商务谈判 | 销售生命周期阶段 | 生命周期 |
| 成交 | 生命周期结果 | 生命周期 |
| 投诉、赔偿、通话、转人工 | 风控和会话控制 | 权限风险 + 渠道归属 |

外贸企业的产品复杂度、报价方式、样品流程、买家组织和采购手续差异很大，因此生命周期必须可配置；意图、证据、风险和文档不能伪装成生命周期阶段。

## 3. 设计原则

### 3.1 七维独立

- 一个客户同一时刻只有一个主生命周期状态，但可以同时存在多个意图。
- “客户问价格”不等于进入报价阶段；只有正式报价被审批并发送，才能形成报价阶段事件。
- “30 天未回复”是互动状态，不是交易生命周期，不能覆盖已经报价或已成交的事实。
- BANT、SPIN、MEDDPICC、SPICED 用来描述需要收集的证据或对话方法，不直接作为生命周期。

### 3.2 事实可追溯

每个重要字段必须保留：

- 当前值
- 确认状态
- 来源消息或文档 ID
- 提取方式：规则、模型、工具或人工
- 置信度
- 首次发现时间与最后更新时间
- 人工确认者（如有）

### 3.3 事件驱动

- 对话消息先写入事件，再更新状态投影。
- 同一个事件重复消费不得重复推进阶段。
- 人工修正通过新的修正事件完成，不直接覆盖历史。
- 时间流逝只改变互动状态、SLA 和跟进任务，不自动修改交易里程碑。

### 3.4 权限优先于生成

生成回复之前先确定当前动作是否允许自动执行。价格、折扣、付款条款、确定交期、赔偿、独家、合同和正式报价等动作必须经过企业权限规则。

## 4. 七维状态定义

### 4.1 生命周期

推荐默认主干：

| 状态 | 含义 | 默认进入条件 |
|---|---|---|
| `new_inquiry` | 新线索或新询盘 | 收到首条有效客户消息 |
| `discovery_qualification` | 需求发现与资格判断 | 已识别至少一个具体需求、产品方向或采购问题 |
| `technical_sample_validation` | 技术、能力或样品验证 | 交易确实需要技术确认、打样、检测或样品；简单批发可跳过 |
| `proposal_quote` | 方案或正式报价 | 经授权的方案/报价文档已发送 |
| `negotiation_approval` | 谈判、内部审批或采购手续 | 买家提出价格/条款异议，或进入审批、合同、采购流程 |
| `closed` | 赢单、输单或暂缓 | 发生已配置的成交、输单或暂缓事件 |
| `fulfillment_relationship` | 履约、售后、复购 | 赢单后进入订单履约；后续复购可以创建新商机 |

`closed` 必须包含结果字段：

```ts
type DealOutcome = 'won' | 'lost' | 'on_hold';
```

企业可以配置什么事件代表赢单。默认只接受正式事件，例如：

- 已接受的 PO
- 双方确认的 PI 且满足企业付款条件
- 已签合同
- 已创建并确认订单
- 已收到付款

仅有“我很感兴趣”“准备下单”不得直接标记赢单。

互动状态另设：

```ts
type EngagementStatus = 'active' | 'waiting_buyer' | 'waiting_seller' | 'dormant_30d' | 'dormant_60d';
```

### 4.2 当前意图

意图采用多标签，另有一个本轮主意图：

```ts
type ConversationIntent =
  | 'greeting_process'
  | 'product_discovery'
  | 'specification_fit'
  | 'quantity_moq'
  | 'customization_oem'
  | 'sample_validation'
  | 'quality_certification_trust'
  | 'price_quote'
  | 'delivery_shipping_incoterm'
  | 'payment_contract'
  | 'negotiation_competition'
  | 'order_progress'
  | 'complaint_aftersales'
  | 'human_or_call_request'
  | 'other';
```

每次识别输出：主意图、次意图、证据消息、置信度和是否需要澄清。意图可以每轮变化，不直接改变生命周期。

### 4.3 交易证据

现有 BANT 保留，但升级为更适合复杂 B2B 的证据集合：

| 证据组 | 主要字段 |
|---|---|
| 需求与结果 | 产品、用途、业务目标、痛点、期望结果 |
| 产品要求 | SKU、规格、材质、包装、认证、定制、技术接口 |
| 商业规模 | 数量、频次、预算或目标价、预计订单价值 |
| 市场与交付 | 国家/市场、用途渠道、时间、关键事件、交付地点 |
| 决策结构 | 当前联系人角色、经济买家、决策者、影响者、内部支持者 |
| 决策方式 | 决策标准、评估流程、审批流程、采购手续 |
| 竞争情况 | 现有供应商、替代方案、竞品比较口径 |
| 真实性与风险 | 企业身份、公开可核验信息、冲突信号、合规/欺诈风险 |

建议统一证据结构：

```ts
interface EvidenceField<T> {
  value?: T;
  status: 'unknown' | 'inferred' | 'provided' | 'verified' | 'conflicted';
  sourceEventIds: string[];
  extractor: 'rule' | 'model' | 'tool' | 'human';
  confidence: number;
  confirmedBy?: string;
  updatedAt: string;
}
```

资格分数用于排序和提醒，不作为自动成交或自动报价依据。分数必须能回溯到证据，不能只保存一个不可解释的总分。

### 4.4 知识状态

知识判断至少分为：

| 状态 | 处理方式 |
|---|---|
| `grounded_static` | 已由企业知识库确认，可直接引用 |
| `grounded_dynamic` | 必须通过库存、订单、物流或报价工具实时查询 |
| `missing` | 企业资料没有答案，澄清或转人工并记录缺口 |
| `ambiguous` | 有多个可能答案，先确认产品、市场或版本 |
| `restricted` | 内部、敏感或无权限信息，不对客户输出 |
| `expired` | 资料已过有效期，必须重新核验 |

知识证据必须记录来源、知识版本、适用产品/市场、有效期和最后核验时间。销售方法、风格记忆和客户历史不能作为产品事实来源。

### 4.5 权限与风险

保留当前 L1-L4 思路，同时把风险等级和执行权限拆开：

```ts
type RiskLevel = 'L1' | 'L2' | 'L3' | 'L4';
type ExecutionMode = 'ai_auto' | 'ai_draft' | 'human_approval' | 'mandatory_handoff';
```

权限判断至少考虑：

- 企业自动化设置
- 当前意图和动作类型
- 知识状态与证据充分度
- 报价、折扣、付款、交期等字段权限
- 客诉、赔偿、合规和欺诈风险
- 客户价值和复杂程度
- 是否发生客户主动要求人工、负面情绪或对话循环

权限判断结果必须包含 `reasonCodes`，并在回复生成之前完成。

### 4.6 商务文档

文档不是知识库附件的同义词。它是某个具体商机中的有状态业务对象：

```ts
type DealArtifactType =
  | 'spec_sheet'
  | 'certificate_or_test_report'
  | 'sample_request'
  | 'technical_proposal'
  | 'quotation'
  | 'proforma_invoice'
  | 'purchase_order'
  | 'contract'
  | 'payment_record'
  | 'shipping_document'
  | 'claim_evidence';

type ArtifactStatus =
  | 'draft'
  | 'pending_approval'
  | 'approved'
  | 'sent'
  | 'acknowledged'
  | 'accepted'
  | 'rejected'
  | 'expired'
  | 'superseded';
```

每个文档保存版本号、关联产品与商机、来源、审批人、发送事件、有效期以及前后版本关系。生命周期只能引用已经落库的文档事件，不能从回复文字推断“报价已发送”。

### 4.7 渠道与会话归属

```ts
interface ChannelOwnershipState {
  channel: 'whatsapp' | 'facebook' | 'instagram' | 'email' | 'other';
  conversationWindow?: 'open' | 'template_required' | 'unknown';
  ownerType: 'ai' | 'human' | 'unassigned';
  executionMode: ExecutionMode;
  assigneeId?: string;
  handoffStatus: 'none' | 'requested' | 'accepted' | 'resolved' | 'returned_to_ai';
  slaDueAt?: string;
  lastInboundAt?: string;
  lastOutboundAt?: string;
}
```

AI 转人工、人工接管、人工回复、人工交还 AI 必须是明确事件。人工接管后 AI 不得继续自动发送；转交时必须提供结构化摘要，而不是让销售重新阅读全部聊天。

## 5. 可观察事件与阶段推进

建议第一批事件：

```ts
type SalesConversationEventType =
  | 'buyer_message_received'
  | 'seller_message_sent'
  | 'intent_detected'
  | 'evidence_observed'
  | 'evidence_human_confirmed'
  | 'technical_requirements_confirmed'
  | 'sample_requested'
  | 'sample_sent'
  | 'sample_approved'
  | 'sample_rejected'
  | 'artifact_created'
  | 'artifact_approved'
  | 'artifact_sent'
  | 'quote_revised'
  | 'buyer_objection_received'
  | 'decision_maker_identified'
  | 'meeting_scheduled'
  | 'purchase_order_received'
  | 'proforma_invoice_confirmed'
  | 'contract_signed'
  | 'payment_received'
  | 'deal_marked_lost'
  | 'deal_put_on_hold'
  | 'human_takeover_requested'
  | 'human_takeover_accepted'
  | 'conversation_returned_to_ai'
  | 'inactivity_threshold_reached';
```

默认转换规则：

| 当前状态 | 事件与前置条件 | 下一状态 |
|---|---|---|
| `new_inquiry` | 识别出具体产品方向、用途或采购问题 | `discovery_qualification` |
| `discovery_qualification` | 需要打样、技术确认或能力验证 | `technical_sample_validation` |
| `discovery_qualification` | 报价必要字段齐全，且正式报价已审批并发送 | `proposal_quote` |
| `technical_sample_validation` | 验证通过，且正式方案/报价已审批并发送 | `proposal_quote` |
| `proposal_quote` | 收到议价、条款异议或进入采购审批 | `negotiation_approval` |
| `proposal_quote` / `negotiation_approval` | 命中企业配置的正式赢单事件 | `closed:won` |
| 任意未关闭状态 | 人工确认客户拒绝、选择其他供应商或项目取消 | `closed:lost` |
| 任意未关闭状态 | 客户明确推迟到未来时间 | `closed:on_hold` 或保持原阶段并创建跟进任务 |
| `closed:won` | 订单进入执行 | `fulfillment_relationship` |

`inactivity_threshold_reached` 只更新 `EngagementStatus` 和跟进任务，不改变上表生命周期。

## 6. 下一最佳动作

每轮只选择一个主推进动作：

```ts
type NextBestAction =
  | 'answer_directly'
  | 'clarify_one_detail'
  | 'collect_missing_evidence'
  | 'recommend_product_or_solution'
  | 'send_approved_artifact'
  | 'create_draft_artifact'
  | 'schedule_call_or_meeting'
  | 'request_human_approval'
  | 'handoff_to_human'
  | 'wait_for_buyer'
  | 'create_followup_task';
```

动作决策输出至少包含：

```ts
interface NextBestActionDecision {
  action: NextBestAction;
  reasonCodes: string[];
  missingPrerequisites: string[];
  requiredArtifactIds: string[];
  requiredExecutionMode: ExecutionMode;
  expectedObservableEvent?: SalesConversationEventType;
}
```

回复遵循：

1. 先回应本轮客户问题或情绪。
2. 如果事实不足，明确不确定性或只问一个最关键问题。
3. 只推进一个主要动作。
4. 生成后执行事实校验和权限校验。
5. 写入回复、证据、动作、权限和结果审计。

## 7. 端到端处理流程

```text
收到渠道事件
  → 写入不可变事件
  → 识别本轮意图
  → 提取/合并交易证据
  → 读取生命周期与互动状态
  → 检索静态知识或调用动态工具
  → 计算权限与风险
  → 选择下一最佳动作
  → 生成回复计划和候选回复
  → 校验事实、承诺、文档和渠道规则
  → 自动发送 / 待审核 / 转人工
  → 写入发送结果与状态投影
```

人工接管包至少包含：

- 客户当前问题
- 生命周期与互动状态
- 已确认交易证据
- 冲突或缺失信息
- 触发转人工的原因
- 最近使用的知识与文档
- 当前文档版本
- 建议下一动作
- AI 是否已经发送承接消息

| 权限风险 | 已有动作风险、出站拦截和转人工 | 风险、执行权限和文档审批仍未形成统一决策对象 |

| 渠道归属 | 已有 WhatsApp 和处理模式 | 缺明确 takeover/handback、窗口状态、负责人和统一 SLA 状态机 |

### 8.4 当前必须先修正的建模问题

P0 开发前，`server/whatsapp/historyImport.ts` 的 `upsertCustomer()` 每次写客户时都会使用最后活跃时间重新计算 `stage`。这使生命周期主要是“活跃/沉默分类”，而不是由报价、样品、PO、付款等业务事件形成的状态。该覆盖问题已在 P0 中修复，以下三项继续作为兼容期约束：

七维架构落地时必须：

1. 把 `silent30/silent60` 迁移到 `EngagementStatus`。
2. 生命周期由事件投影更新，不再由最后活跃时间覆盖。
3. 兼容旧字段一段时间，禁止一次性破坏现有客户数据和前端筛选。

## 9. 下一步开发规划

以下规划从状态基础开始，不先扩大话术库。

### P0：状态模型与兼容层

实施状态：**已完成首批开发**。已落地七维版本化状态、不可变事件与幂等投影器、旧阶段适配、WhatsApp 消息事件接入、生命周期/互动状态分离、前端双标签和回归测试。事件日志独立持久化及后台人工迁移工具仍可在后续运维批次补充，不阻塞当前兼容运行。

目标：建立七维状态的唯一类型定义和版本化存储，先解决数据语义问题。

建议新增：

- `server/sales/conversationState.ts`
- `server/sales/conversationEvents.ts`
- `server/sales/conversationProjector.ts`
- `server/sales/legacyStateAdapter.ts`
- 对应单元测试

工作项：

1. 定义 `SalesConversationStateV1`、七个子状态、状态版本和更新时间。
2. 定义不可变事件、事件 ID、来源、幂等键和人工确认信息。
3. 将旧 `CustomerStage` 映射到新生命周期；将 `silent30/60` 映射到互动状态。
4. 保留旧 API 字段作为兼容投影，避免前端立即失效。
5. 修正 `upsertCustomer()` 的时间覆盖问题。
6. 增加事件重放、重复事件和旧数据迁移测试。

验收条件：

- 旧客户迁移不丢消息、BANT、订单、处理模式和人工待办。
- 相同事件重复处理不会重复推进状态。
- 时间流逝不会把 `proposal_quote`、`closed:won` 等阶段降级。
- 新旧 API 在兼容期可同时工作。

### P1：意图与交易证据

实施状态：**已完成**。已接入多语言多标签意图、通用证据字段、来源事件、冲突处理、人工确认/纠正历史、BANT 兼容投影，以及“买家认证要求不等于卖家认证能力”的字段隔离。现有会话侧栏已展示“值 + 来源 + 状态”。

目标：让系统知道“客户在问什么”和“交易已确认什么”，并保留证据来源。

工作项：

1. 统一现有动作库、知识缺口场景和回复分类为多标签意图模型。
2. 把 BANT 数据迁入通用 `EvidenceField<T>`。
3. 新增业务目标、痛点、决策者、决策标准、决策流程、关键事件、采购手续和竞争情况。
4. 增加字段冲突、撤回和人工确认机制。
5. 防止模型把买家要求误当作卖家能力。
6. 前端客户资料卡展示“值 + 来源消息 + 确认状态”，而不是只显示分数。

验收条件：

- 每个非空关键字段至少有一个来源事件。
- 买家说“需要 CE”不会被记录成“企业拥有 CE”。
- 多轮重复信息不会重复计分或覆盖更高可信证据。
- 人工可以确认、纠正并看到修改历史。

### P2：事件推进与下一最佳动作

实施状态：**已完成**。已落地默认及企业可配置的转换策略、报价/样品/谈判/成交前置条件、`NextBestActionDecision`、单一主要推进动作和回复规划接入。生命周期变化保存触发事件与原因；询价消息本身不会推进报价阶段。

目标：以规则和前置条件决定能否推进，而不是让模型自由修改阶段。

工作项：

1. 建立默认生命周期转换表和企业级配置。
2. 建立报价、谈判、赢单、输单和暂缓的前置条件。
3. 实现 `NextBestActionDecision`，将“先回答 + 一个推进动作”写入回复计划。
4. 把执行权限判断前置到候选回复生成之前。
5. 将当前 reply planner、动作库、BANT/SPIN 接入统一状态，而不是各自读取零散字段。
6. 对每次阶段变化保存触发事件和原因。

验收条件：

- 问价格不会自动进入 `proposal_quote`。
- 只有已审批并发送的报价文档才能推进报价阶段。
- 不满足前置条件时返回缺失条件，不静默推进。
- 每轮最多一个主要推进动作，且不重复询问已确认字段。

### P3：商务文档、权限和人机协同

实施状态：**已完成**。已落地商机级文档版本、审批、发送、过期与替代关系，字段级商业风险，显式接管/接受/交还状态机，结构化交接包、服务端 WhatsApp 24 小时窗口校验，以及人工接管期间 AI 自动发送硬拦截。人工回复后不会再默认模糊恢复 AI。

目标：让报价、样品、PI、PO 和合同真正进入交易状态机。

工作项：

1. 建立商机级文档、版本、审批、发送、过期和替代关系。
2. 把价格、折扣、付款、交期、独家和赔偿配置成字段级权限。
3. 建立 `human_takeover_requested/accepted/returned_to_ai` 状态机。
4. 自动生成结构化人工接管包。
5. 增加 WhatsApp 24 小时窗口/模板状态和发送前校验。
6. 人工回复后明确决定继续人工还是交还 AI，不再默认模糊恢复。

验收条件：

- 未审批文档不能发送或触发阶段推进。
- 人工接管后 AI 不能自动发送。
- 报价修订保留全部版本和发送记录。
- 转人工通知能直接说明客户问题、已知证据、风险、文档和下一动作。

### P4：评测集与质量仪表盘

实施状态：**已完成首版离线基线**。已建立 16 个隐私安全分层用例，覆盖英/中/西/阿语、公开表达模式、模拟企业事实、专家金标准和多轮风险分支；支持一键重复运行、失败明细和零越权硬门槛。当前确定性基线各项为 100%，未授权承诺为 0。该结果仅说明当前基准用例通过，不代表真实成交效果。

目标：在没有真实销售对话时建立可重复、可审计的离线基线。

数据分层：

1. 公开自然表达：公开 RFQ、商品问答、电商售前语料。
2. 模拟企业事实：产品、规格、认证、MOQ、价格权限、付款和物流规则。
3. 销售专家金标准：阶段、意图、交易证据、直接答案、缺失字段、下一动作、禁止承诺、文档和转人工。
4. 多轮分支：正常配合、信息不完整、价格施压、风险/投诉。

离线指标：

- 意图识别正确性
- 交易证据提取与冲突处理
- 生命周期转换准确性
- 直接回答率
- 下一动作专家接受率
- 知识依据正确性
- 文档和条款正确性
- 转人工召回与误报
- 未授权承诺数量
- 多语言自然度与信息保真度

硬门槛：测试集中未授权价格、折扣、付款、交期、认证和赔偿承诺必须为零。

### P5：小规模真实试点

实施状态：**产品采集能力与看板已完成，真实试点待启动**。已接入草稿生成/采用/修改、修改原因、三轮内证据、阶段推进/回退、接管时效、报价、赢单/输单/暂缓、投诉、重复追问和人工纠错事件；模拟客户和历史导入不会污染试点样本。看板在没有真实事件时明确显示“等待真实客户试点”。

目标：验证真实使用效果，而不是仅验证回复看起来合理。

试点时采集：

- AI 草稿采用率与人工修改率
- 人工修改原因
- 三轮内是否获得关键缺失信息
- 阶段推进与回退原因
- 转人工后的阅读和接手时间
- 报价到订单的转化
- 赢单、输单和暂缓原因
- 客户投诉、重复追问和人工纠错

真实转化指标只能用于试点后的产品验证；公开语料和专家模拟不能证明系统已经提升成交率。

## 10. 已完成的首个开发批次

首批按 P0 范围完成，没有同时重写回复生成：

1. 新增七维状态 TypeScript 类型和 schema 版本。
2. 新增事件定义和纯函数投影器。
3. 将旧 `CustomerStage` 做无损兼容映射。
4. 分离生命周期与互动状态。
5. 修复时间覆盖阶段的问题。
6. 增加迁移、幂等、事件重放和阶段不降级测试。
7. 让现有 `draftReply` 只读取新状态的兼容投影，保持当前回复链路可运行。

在 P0 稳定后，P1–P5 已依次接入意图、扩展交易证据、下一最佳动作、商务文档、人机协同、离线评测和真实试点采集，后续模块统一依赖同一状态模型。

## 12. 最终结论

灵小枢下一阶段的核心任务不是继续增加固定节点或话术，而是先建立统一、可追溯的销售对话状态基础。

七维模型解决的核心问题是：

- 生命周期不再被意图和沉默时间污染。
- 客户说法、企业事实和销售判断分别保存。
- 报价、样品、合同和付款成为正式业务对象。
- 每次推进都有可观察事件和证据。
- AI 的回复能力与执行权限分离。
- 人工可以随时接管，并获得完整、结构化上下文。
- 评测可以判断“答得对、推进合理、没有越权”，而不只是比较文字是否相似。

开发顺序确定为：**状态与事件基础 → 意图与交易证据 → 下一最佳动作 → 文档与人机协同 → 评测 → 真实试点**。
