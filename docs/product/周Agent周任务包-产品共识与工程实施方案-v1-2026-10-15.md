状态：**周包总体方向已获用户原则认可；第十节记录分镜要求，第十一节记录本轮获准补充的架构与统一额度实施方向。工程建议、待确认细节和代码现状另行标注，不代表已实现。**

本文区分三种内容：**已达成共识**、**建议实施规则**、**当前代码事实**。代码中存在接口或测试，不等于当前真实周包已端到端执行成功。

## 一、已达成的业务共识

| 事项 | 已确认内容 |
| --- | --- |
| 运营周期 | 北京时间自然周，周一至周日，不展示成跨周的七天滚动计划 |
| 内容目标 | 默认每周制作5条独立原创视频；这里的原创指企业自己的新成片，制作路线采用爆款复刻 |

| 静默确认 | 自动采用模板并留痕，不伪造用户审批、事实证据、平台权限或业务交付 |
| 人工验收 | 成片验收和发布许可在“发布与渠道”的对应真实生产页面操作 |
| 任务异常 | 详情提供实际可用的补排、调整范围、补资料、授权和重试等操作，不能只有说明文字 |
| 卡片状态 | 缺项红色感叹号；实际开始执行后移除；真实交付完成后绿色对勾 |

### 数量必须分开统计

- **新成片数：5。** 不能因为选择4个平台，就自动创建20条独立视频生产任务。
- **平台发布项：每条成片最多4项，默认最多20项。** 这是分发目标，不保证未授权平台也能发布成功。
- 平台格式适配、补产、重试、补发不能被悄悄计算成新的原创内容。
- 客服监听、每日数据回收、周复盘不消耗新视频名额，也不应被混算进视频生产并发。

## 二、建议的周排期与每日 Loop

### 2.1 周级职责

**周一：全周铺排。** 生成5条内容槽位、参考来源策略、产品与经营方向、平台分发范围、每日工作和周末缓冲。系统执行容量核验并自动派单；不增加四份需要用户依次填写的后台表单。

**周二至周五：持续生产。** 原则上每天推进1条新片，已完成的成片可继续向其他平台分发；缺项不影响其他内容或平台的独立执行。

**周六、周日：分发和容错。** 优先处理未完成的原5条视频、未成功的发布项；仍受每条15元、并发3条和真实验收许可约束。正常情况下不额外生成第6、第7条新片。

**周日：目标回收与数据复盘。** 核验5条成片、平台分发、客服情况、成本和未完成原因，形成下周建议。不因某个任务失败就永远无法生成“未达标”的真实复盘。

### 2.2 每日 Loop

```text
当日经营目标与待办
    → 采集/读取有效参考 → 对标筛选 → 编导拆解、选题及脚本分镜
    → 素材与授权就绪 → 内容生产、渲染、导出
    → 成片验收 → 平台适配与发布预检 → 已授权平台发布
    → 当日数据快照 → 次日参考选择与经营调整

每日常驻客服：独立监听 → 识别问题 → 检索资料 → 回复/审批/转人工 → 回执归档
```

每日 Loop 是工作机制，不是每天复制一整套空任务，更不是每天新增5条视频。当天没有新片目标时，制作阶段可以处理未完成内容；没有实际工作则显示明确的待命/无需新增，不伪造已交付。

前一天数据未回传，不应成为次日所有内容的硬依赖：可以沿用上一份仍有效的参考策略并注明数据新鲜度，不能编造反馈结论。

### 2.3 “每天发一条”的建议解释与可行样例

**待确认建议：每天全平台合计至少1个发布项，不要求每天4个平台各发1条。** 将5条成片的20个平台分发项分布到七天，可以保持每天有发布，同时不重复制作、不无依据重发同一平台。

下表只证明数量与依赖可成立，不是已写入系统的固定平台日程。A/B/C/D代表上述4个平台，具体映射及发布时间应服从真实账号、许可和平台约束。

| 日期 | 新成片目标 | 分发样例 | 发布项数 |
| --- | --- | --- | --- |
| 周一 | V1 | V1→A/B/C | 3 |
| 周二 | V2 | V1→D；V2→A/B | 3 |
| 周三 | V3 | V2→C；V3→A/B | 3 |
| 周四 | V4 | V2→D；V4→A/B | 3 |
| 周五 | V5 | V3→C；V4→C；V5→A/B | 4 |
| 周六 | 补产缓冲 | V3→D；V5→C；必要时调整为补发 | 2 |
| 周日 | 补产缓冲、周回收 | V4→D；V5→D；必要时调整为补发 | 2 |

当日成片或授权未就绪时，“每天有发布”是计划目标，不是编造成功回执的理由。是否使用已有合规库存补位，应有可核验的库存绑定和发布许可；不默认重复发布同一内容到同一账号。

如果实际要求是“每天4个平台各1条”，则七天对应28个发布项，超过5条成片各分发一次的20项，需要另行明确库存、重复发布或新增内容规则，不能默认为已同意。

## 三、四个后台环节如何自动衔接

| 环节 | 系统应完成的工作 | 交付物 | 允许局部受阻的情况 |
| --- | --- | --- | --- |
| 目标 | 采用已确认模板，建立5个内容目标及4平台分发范围；冻结本周版本 | 周目标与内容槽位快照、模板采用记录 | 特定产品/事实缺失只影响相应内容，不影响客服 |
| 容量 | 读取实际执行器、并发、供应商能力、费用和资源窗口 | 可执行容量快照、分支准入结果 | 供应商或素材缺项按实际影响范围阻塞 |
| 排期 | 周一至周五各1条，周末预留；普通任务06:00起按依赖推进 | 日归属、任务依赖、平台发布窗口、缓冲安排 | 未授权平台保留缺项；其他已就绪平台继续 |
| 派单 | 把已具备条件的真实任务写入持久队列，由消费者领取 | 队列任务、运行身份、执行事件及真实结果引用 | 分支排队或等待资料，不把所有任务退回草稿 |

“选择任务包并开始执行”是用户的生产启动动作；默认模板采用不应继续要求重复确认，但**启动生产不等于成片验收、发布许可或真实消息发送许可**。

整体状态应分别表示规划、执行、分支缺项及对外授权。已有 `independent_branches` 可以作为过渡，不得把 `draft` 改成 `active` 来掩盖尚未就绪的权威规划。

周包是有限的一周，不是无期限授权。建议以后按已采用的模板实例化下一自然周，但每周保留独立身份、输入快照及目标，不能继承已过期的发布/消息授权，也不能把上周失败任务当成下周新原创重复计数。

## 四、数据模型与执行任务图的调整建议

### 4.1 五类对象，不再混为同一种“任务”

| 对象 | 建议粒度与身份 | 主要职责 |
| --- | --- | --- |
| 周包 | 租户＋项目＋自然周＋版本 | 保存目标、默认规则、配额及修订历史 |
| 内容生产单元 | 周版本＋内容ID＋创意修订 | 一条原创视频的脚本、素材、生产、费用与交付 |
| 平台分发单元 | 内容交付版本＋平台＋账号＋发布目标ID | 适配、许可、预检、发布和回执 |
| 每日运营单元 | 项目＋日期＋策略版本 | 当日目标、参考采集、反馈快照和收尾 |
| 客服常驻单元 | 租户/项目＋渠道账号＋服务日期 | 覆盖24小时，关联真实会话和处理事件 |

这是建议的逻辑模型，不要求新增五套重复数据库或服务。优先扩展现有周包、任务、产物和绑定契约；`motherContentId` 可承接内容身份，但单凭它不能证明某成片可安全复用。

### 4.2 生产与分发拆开，避免四倍制作

每个内容单元只建立一条主生产链，生成真实、可预览且带版本的成片。4个平台分发任务引用这一产物；只有规格确实不同才生成必要的平台派生文件。

复用前校验内容身份、企业事实、素材权利、审核版本、文件哈希和平台规格。不能把其他周、其他内容或其他租户的成片绑定过来，也不能把未验收产物标成已通过。

原有 `adaptationVersionTarget` 不能继续直接用“发布项数−母内容数”解释成必需重新制作的数量。新片、派生文件、发布项应分开计数，并保留旧版本契约的兼容读取。

### 4.3 依赖规则

1. 同一条内容内部按采集证据、编导、素材、制作、审核等真实依赖推进。
2. 不同内容可以独立推进，生产阶段合计最多并发3条。
3. 同一成片的不同平台分发独立准入；一个平台权限失效不能阻塞其他平台。
4. 客服不依赖任何内容生产节点，其会话可反向提供选题建议，但不是每日生产的强制前置。
5. 复盘需要真实结果和缺项清单，不应要求“所有发布都成功”才能报告未达标。
6. 卡片合并只是展示投影，不改变原任务、依赖、执行身份或费用账本。

### 4.4 并发与成本

- 复用现有持久队列和限额机制。视频生产租户限额、任务类型限额与 worker 容量须一致支持3条，不能只把扫描批量或卡片数改成3。
- 生产并发与账号发布限流分开；同一发布账号仍按平台规则串行或限速，不能为达到3而突破平台限制。
- 等待用户验收或权限补齐的任务不长期占用生产名额；供应商已受理、仍在生产或结果未知的任务必须保留对应资源/费用预留，不能当成结束后继续超额提交。
- 客服常驻和采集/回执查询不占据长视频生产名额，但需要各自的限流和消费者容量。
- 建议以内容生产单元归集费用：调用前预留、调用后记账；失败、重试和未知付费结果保留记录，不通过新建任务重置15元额度。
- 建议必要派生、质检和返工也计入该内容单元的15元控制范围；具体费用口径见第九节。5条×15元只是自动测算参考，不增加整周预算确认环节。
- 采集仍采用每日10条的独立数量上限；不能把采集上限误写成每个词、每个平台或每次运行各10条。

## 五、参考采集、数据反馈与客服 Mock

### 5.1 参考来源

零基础默认外部参考；有基础允许按策略分配自有/外部参考，但本次未确认固定比例，不能擅自写死50%。自有参考必须有账号归属、视频身份和可核验指标，不因账号“有基础”就自动认定所有视频都是爆款。

现有“五搜索词生成”“采集结果证据化”“参考选择”“编导分析”应连成实际 producer/consumer 链。自动采用采集策略必须记录 `automatic_template` 来源及策略版本，不能伪造 `approvedBy: user` 或手填分析通过状态。

没有有效参考时，阻塞对应内容并给出详情入口。是否自动改用另一来源策略，需要明确的模板规则、适用条件与留痕，不能在冻结版本中偷偷换参考。

5个词与4个平台不做数量上限的乘法展开。采集计划应在每天合计10条内分配词、来源及平台，并避免第一个来源长期占满所有额度；失败/未知调用的额度处理沿用实际预留记录，不通过换运行ID绕过。

### 5.2 数据回收真正进入次日输入

复用现有指标生产器保存真实平台快照，增加可版本化的反馈结果：来源发布项、统计截止、覆盖范围、数据新鲜度、结论及下一轮策略引用。

次日采集/选题明确读取该反馈版本，并持久化消费关系；仅写 `feedsNextDailyCollection: true` 不算打通。数据不足时显示不足，不把缺失指标当作0，也不把当天短时播放量说成最终效果。

### 5.3 WhatsApp Mock 的工程边界

Mock 通过现有客服适配器端口接入，保留与真实执行相同的事件处理路径，覆盖接收、去重、资料检索、回复草稿、必要审批、转人工、发送结果和重试。

必须增加显式模拟执行模式与模拟证据边界：只在本地测试数据域启用，使用稳定的模拟消息ID及回执，界面和详情显示“模拟”。Mock 验证通过不得解除真实渠道授权阻塞，不得进入真实询盘、真实发布或真实目标达成统计。

模拟运行与真实运行拥有不同的执行身份及结果命名空间。可复用任务定义和处理逻辑，但不能用Mock结果把真实周任务改成已交付；模拟卡片应显示“模拟验证通过”，不冒充真实完成。

生产配置默认禁止 Mock；切到真实模式必须重新校验账号、消息权限、消费者与适用的人工审批。没有新会话可以是“监听中/暂无消息”，不能为了常驻卡片完成而制造客户交付。

## 六、周末补偿、任务详情与周日回收

### 6.1 补偿不是再开一套任务

- 前五天未完成内容保留原内容身份、已产生费用、素材和运行记录；补排的是剩余工作，不是复制完整制作链。
- 平台明确拒绝且允许重试时恢复原发布分支；受理后结果未知时先查询原回执，不重复提交。
- 利用现有补排/修订能力形成新排期版本、影响清单与追溯关系。日期调整与内容/授权范围变更应区别处理，不能为纯技术补排反复要求整周业务确认。
- 若修订改变成片、账号、平台或授权范围，必须使相应旧审核/许可失效，并在生产页面完成所需的重新核验；不能无条件继承旧许可。
- 周末仍做不完时如实列出未完成项；跨周续做需明确承接关系，不能悄悄塞入下一周或伪造本周按时完成。

### 6.2 日历与详情

周视图固定周一至周日，无小时轴。每日置顶常驻服务，普通任务从当日经营安排开始，约7～8个关键节点卡；周一铺排、周日回收可纳入对应经营/数据卡详情，避免再次堆叠汇总卡。

建议关键节点为：常驻客服、经营安排、采集对标、编导选题、素材准备、内容制作、验收发布、数据回收。卡内可以关联多个真实内容对象，详情逐项展开，不以相同标题为由合并不同产物和权限。

每张卡必须给出：真实身份与版本、交付物、依赖、缺项、运行状态、费用及直接操作入口。没有生产对象时提供补齐/建立真实对象的动作，不能跳到任意最新任务或只读信息页冒充生产现场。

成片验收、真实发布许可均进入“发布与渠道”；缺资料、账号和客服配置在对应详情中补充，不新增初始化页面。日历以下原先移除的配置大区不重新堆回。

### 6.3 周日复盘的统计边界

现有代码将周日20:00作为复盘窗口截止，与“周日仍可补发、客服全天值守”存在边界冲突。

**建议两阶段回收，待确认：**周日20:00可生成标明截止时点的阶段性回收；自然周截至次日00:00后，待平台数据到达，再补全全周结果。卡片仍归属本周周日，实际执行/回执时间如实记录，不能把晚到数据回填成20:00前已知。

“复盘报告已生成”和“周目标已达成”必须是不同结果。报告可以真实记录未完成、受阻和样本不足；不能等所有视频/平台成功才允许生成报告，也不能用报告生成替代目标达成。

## 八、分阶段工程实施与验收

### P0：统一契约与迁移规则

确认第九节后升级周包/模板契约，区分内容、派生、分发、常驻和每日反馈。先用测试生成新任务图，再迁移现有本地周包。

旧327项不直接删除、不批量改成功、不修改冻结证据。通过可审计修订映射新旧任务，保留已调用、已付费及未知回执；周一周二的历史计划不能伪造回溯执行。

### P1：默认配置到真实入队

打通任务包选择→模板采用→目标准备→真实资源读取→依赖排期→分支派单。修复默认值没有进入实际消费者、仍被旧整周确认门槛拦住等问题，不增加初始化表单。

验收：5个内容单元、最多20个平台发布项、七天运营职责、并发3；一个资料/渠道缺项不阻塞无依赖分支。

### P2：真实生产与4平台独立分发

复用既有内容生产、审核、验收、发布与回执能力，改造精确绑定和产物复用。权限仍由真实服务端校验。

验收：一条成片可对应4个分发项而不是4次全量生产；重启/重试不重复付费创建；成片版本变化使相应旧验收和发布预检失效。

### P3：独立客服与WhatsApp Mock

建立每日常驻服务身份、事件处理和Mock隔离；缺权限时在详情补齐。保留人工审批与商业承诺边界。

验收：无任何视频任务也能处理模拟客服事件；重复消息不重复回复；Mock不调用真实发送接口，不解除真实权限阻塞，不计入真实目标。

### P4：每日反馈、周末补偿与周回收

接通指标快照→反馈结果→次日策略消费；补排剩余工作与平台分发；实现诚实的周目标回收。

验收：制造两天生产延误和单平台失效，周末能接续原工作且其他分支继续；周复盘显示真实缺口，即使未全部达标也能输出报告。

## 十、四类分镜的技术管线与预算分配

本节是2026-10-15用户补充的明确要求。**路由按单个分镜判断，不按整条视频统一选一个供应商；预算按整条成片统筹，不给每个分镜分别发放15元。** 同一视频可以混合使用下述允许的管线。

### 10.1 已明确的四类分镜与允许管线

| 分镜类型 | 条件 | 允许管线 | 默认规则 |
| --- | --- | --- | --- |
| 真人口播 | 走播等需要明显动态表现的分镜 | **Seedream首帧生图 → Seedance生视频** | 内容Agent判断动态表现要求，不能只因Heygen较便宜就改变必要动作 |
| 真人口播 | 定播、坐播、站播等以稳定口播为主的分镜 | **Seedream首帧生图 → Heygen口播视频** | 在满足动作、人物和口播要求的前提下使用Heygen |
| 产品实拍 | 已有匹配的本地素材 | **本地素材匹配** | 优先复用合格的产品片段 |
| 产品实拍 | 需要生成的关键产品镜头，且整片预算允许 | **Seedream首帧生图 → Seedance生视频** | 作为可选产品生成路径；优先给关键、S级产品镜头分配预算 |
| 工厂实拍 | 工厂、产线、工序等镜头 | **仅本地素材匹配** | 不安排Seedream/Seedance生成工厂画面来替代实拍 |
| D2C | 消费者场景、体验或使用演示类镜头 | **仅本地素材匹配** | 不因预算有余额就转为AI生成，也不自动改成数字人口播 |

“产品实拍”沿用本次分镜分类名称；实际采用生成路径时，详情和凭据必须标明“生成产品镜头”，不能因分类名称而将其伪称为真实拍摄。

此前助手提出的“默认不使用真人/数字人口播”不是用户认可的制作规则，**本节明确替代该建议**。是否出现真人口播，取决于参考分镜及当前内容需要。

### 10.2 已明确的预算优先级

1. **先统筹整片预算与分镜组合。** 每条成片仍以15元为控制边界，不能给每种管线各用15元，也不能在每个平台分发时重置制作额度。
2. **优先保障真人口播分镜。** 根据走播/稳定口播分别选定Seedream＋Seedance或Seedream＋Heygen，并计算其总费用占用。
3. **其余分镜以本地匹配为主。** 如果真人口播已用尽可分配的生成预算，其余产品、工厂和D2C分镜全部走本地匹配。
4. **有余量时优先提升关键产品镜头。** 真人口播预算安排完成后，若仍有足够空间，可挑选关键的S级产品镜头，使用Seedream＋Seedance提升表现。
5. **工厂和D2C不参与生成预算升级。** 本轮要求已经将这两类限定为本地匹配，不能把“优先产品”解释为花剩的钱后还可生成工厂或D2C镜头。
6. **不要求花完预算。** 产品生成是满足关键镜头需要的选择，不是为了消耗余额而增加调用；真人口播不存在时，也按同一原则统筹产品关键镜头与本地素材。

这里的“S级镜头”表达关键镜头的质量与重要性要求，不等于已经确定某个模型档位、固定单价或所有镜头都要付费生成。具体评级和选择依据需要由工程实现记录，不可直接把所有产品分镜标成S级。

### 10.3 建议的预算规划与执行顺序

本小节是将上述要求落到现有管线的工程建议，不是已经完成的实现，也不预设供应商当前报价。

```text
分析参考视频与当前产品事实
    → 对每镜分类，并判断真人口播的动态要求
    → 检索、验证本地可用素材，形成缺项清单
    → 核验允许的生成管线、授权、时长与实际报价
    → 为必要制作/审核/合成及已发生费用保留整片额度
    → 优先分配真人口播预算
    → 其余镜头以本地方案组成完整可交付计划
    → 用真实余量评估关键产品镜头的Seedream＋Seedance升级
    → 冻结分镜路由、输入版本与预算预留
    → 逐项执行、质检、合成和真实成片验收
```

- **先确认完整可交付组合，再启动付费调用。** 不能先把钱花在真人口播上，之后才发现工厂/D2C没有本地素材、整片无法完成。
- 可分配余额应扣除已发生费用、正在执行或结果未知的付费预留、必要后续处理费用，以及适用的返工预留。不能只按“15元减去真人视频接口标价”计算余额。
- 本地匹配意味着不额外调用画面生成，不代表素材分析、配音、质检和合成一定没有成本；应按实际计费链路纳入核算，不能伪填0元。
- 价格、时长、供应商能力或人物/产品身份不能核验时，先记录缺项，不凭固定示例价格宣称能够在15元内完成。
- 产品本地素材缺失时，可以评估已允许的产品生成路线；只有真实输入、预算及能力均满足才可执行。不能借此把所有素材缺口都变成付费生成需求。
- 必需真人口播本身超出预算时，不擅自改为不符合动作要求的便宜管线，也不追加预算；保留该内容分支受阻，提供可用的换参考、补素材或调整方案入口。
- 工厂/D2C本地匹配失败时，明确要求补充素材或调整参考，不自动走AI生成。纯预算降级不能覆盖素材真实性、人物授权或产品身份约束。
- 调用失败、重试和结果未知仍归属原内容预算。未知结果先对账，不换任务ID重复调用；产品升级失败后若要回到本地方案，应形成可追溯的计划修订，不能隐去已发生费用。

### 10.4 内容Agent需要给出的分镜决策记录

建议每镜保存以下信息，供详情展示、实际调用和验收共用；不是让用户逐镜重新填写一份表单：

- 分镜ID、参考镜头ID、原时间区间、目标时长及叙事功能。
- 四类素材分类，以及有依据的走播/定播/坐播/站播判断；无法确定时保留不确定性。
- 是否关键/S级镜头、选择依据及是否需要产品生成升级。
- 本地匹配来源、截取区间、产品SKU/人物身份、可用性和授权凭据。
- 选定管线、首帧输入与生成结果、供应商/模型及冻结版本。
- 报价依据、预计费用、已预留费用、实际费用及剩余额度。
- 选路原因、降级/修订原因、当前缺项、质检与真实输出引用。

产品Seedream首帧应锁定当前企业产品的外观、包装、Logo及必要文字；真人首帧、视频和声音沿用当前账号已授权的身份。不能把爆款原人物的脸或声音直接当作本企业已授权人物。

## 十一、统一执行架构与跨入口周额度契约

本节来自侧会话中的产品技术架构讨论；用户已要求写入本MD并同步主会话继续实施。**本节是后续实现约束，不是代码完成声明。** 第九节仍保留的每日发布口径、费用范围、回收截止等细节，不因本次补充而自动变成已确认；第十节的素材、人物与真实付费能力边界继续有效。

### 11.1 技术选型：沿用LangGraph，不推倒现有执行体系

当前项目已引入 `@langchain/core`、`@langchain/langgraph` 与检查点依赖，并已有 [LangGraph执行图](../../server/contentExecution/langgraphEngine.ts)、[检查点存储](../../server/contentExecution/langgraphCheckpoint.ts)和[生产桥接](../../server/contentExecution/productionGraphBridge.ts)。不再把“安装LangChain/LangGraph”当作主要工程成果，也不为同一生产流程新增第二个编排引擎。

| 层级 | 职责与最终依据 | 不应承担的职责 |
| --- | --- | --- |
| 周计划/业务服务 | 周目标、内容身份、名额账本、成本账本、依赖、权限、审核及发布许可；服务端持久化业务记录是最终依据 | 不由LLM文本、前端卡片或图恢复参数生成授权与交付 |
| LangGraph生产图 | 在既定业务边界内编排素材、生成、渲染、质检、审核等待与交付；保留可恢复检查点 | 不自行增加周额度、重置预算、批准发布，或取代业务状态机 |
| 持久队列与Worker | 原子领取、租约、并发、后台唤醒、退避及恢复，驱动图继续执行 | 不将扫描条数当生产并发，不把入队等同完成 |
| 供应商/渠道适配器 | Seedream、Seedance、Heygen、渲染、平台发布和消息接口；记录原请求与实际回执 | 不因网络超时擅自再次提交付费或对外动作 |
| 日历、工作台、灵小枢 | 提交有类型的业务命令，展示同源任务、缺项、费用和操作入口 | 不各自维护一套生产状态、计数或对外权限 |

LangChain可按需用于模型、工具和检索封装；现有明确可靠的供应商SDK或HTTP适配器无需为了统一名词全部重写。暂不同时引入另一套多Agent或长流程引擎。经营、编导、内容、客服是业务角色，不意味着需要四个可自由扩权的自治Agent。

模型负责提出选题、脚本、分镜及素材建议；确定性代码负责额度、成本、授权、依赖和执行准入。图节点输出必须通过结构化校验，并关联真实产物或回执后，才能投影为业务交付。

### 11.2 三个入口，共用一份内容订单和同一条生产管线

```text
周任务包 ──┐
内容工作台 ─┼→ 内容订单/原内容身份 → 周名额与费用准入 → 持久队列
灵小枢 ────┘                                      ↓
                                          单内容LangGraph生产图
                                                  ↓
                                          真实成片与验收凭据
                                                  ↓
                                     4个平台独立分发、预检和回执
```

“内容订单”是统一业务契约，可由现有内容任务记录及关联表承接，不要求重建所有表。三个入口必须调用同一套服务端创建/启动服务，不复制三套业务逻辑。复用现有 [内容任务服务](../../server/starter198/socialContentTasks.ts)及其幂等能力，补齐入口来源、周包归属、额度、费用和生产身份绑定。

每条独立新视频至少关联：`tenantId`、`programId`、`contentId`、入口来源、生产修订、归属周/周包版本、槽位与额度记录、生产任务/运行/图身份、原费用账本、产物版本与审核凭据。分发另关联平台、账号、发布目标及平台回执。字段名称可适配现有契约，但这些身份关系不能省略或靠标题推断。

相同业务请求重试必须复用原订单；内容修订可产生新的图执行身份，但不能自动获得新的周名额或一份新的15元预算。`publicationTaskId` 是分发身份，不能继续作为“同一原创在不同平台分别新建全量生产”的默认依据。

### 11.3 周度创作额度：入口无关，服务端统一预占

默认5条是本周新视频的计划/执行额度，不是已经确定的商业收费套餐。追加名额通过用户明确的目标修订处理，不自动扣款、不隐含开通付费套餐。

| 操作 | 周名额规则 | 费用与交付规则 |
| --- | --- | --- |
| 填需求、对话收集、保存草稿 | 不占执行名额 | 不因此启动付费生产；若另有实际收费预分析，必须单独明确并记账 |
| 确认启动一条独立新视频 | 服务端原子预占一个本周槽位 | 通过必要输入、报价、授权与费用准入后才提交实际生产 |
| 同一视频修改、失败重试、重新渲染 | 不重复占名额 | 费用累计归属原内容，保留修订及运行历史 |
| 同一成片向4个平台分发 | 仍只占一个新视频名额 | 创建独立发布项，必要派生文件不自动变成新原创 |
| 分发已有合规库存 | 不占本周新视频名额 | 保留库存来源、权利及本次发布许可；如涉及重新制作，不能冒充纯分发 |
| 创建另一条独立新视频 | 需要另一个可用槽位 | 明确关联新内容，而非借“重试”绕过数量或费用控制 |

周包提前建立的5个内容槽位不等于5次生产已经全部预占；需区分“计划占位”和“执行预占”。工作台或灵小枢临时启动内容时，优先承接本周尚未开始的自动内容槽位，并明确告知用户“使用本周一个名额，相应减少一个未开始的自动创作计划”，不能同时保留两条待启动订单争用同一槽位。

自动派单和手动启动竞争同一槽位时，由服务端事务/原子条件更新裁决，不能靠按钮禁用或进程内锁防重。保留原计划、替换关系和任务取消/被替代记录；不得删除历史。已持有执行租约、已提交供应商、已产生费用或外部结果未知的任务，不能当作“未开始”静默替换。

5个名额已被预占或使用后，提供“替换确实尚未开始的计划（如存在）”或“明确追加本周创作目标”的操作；没有可替换对象时不能显示可用。追加不得取消其他已启动任务，预算规则仍按新增内容的有效约定执行。

### 11.4 释放、取消、跨周和审计规则

- 名额状态建议区分计划、已预占、执行中、已交付、已释放/被替代；失败、暂停和等待资料不是自动释放理由。
- 预占后但尚未发生付费或不可撤回动作的任务，可按明确取消规则释放；必须确认无租约、无在途请求、无未知回执，释放命令幂等。
- 已付费失败或取消的内容，费用永久保留；如需释放周名额，必须通过明确的取消/范围修订规则。继续同一内容仍沿用原成本，不能换ID逃避上限。
- 同一条成片的验收、交付和名额消耗只结算一次；重复回调和恢复执行不能重复计数。无数据、模拟和取消不得计作真实成片交付。
- 归属周采用北京时间自然周并在预占时记录。跨周延续保留原内容、原费用和原额度来源；新周日历可显示“上周续做”，但不能既算旧周交付又消耗一份新的原创名额而无解释。
- 追加目标、释放、替换、跨周承接均记录操作者/自动策略、时间、原因、原/新对象和命令幂等键；技术恢复不能伪造用户确认。
- 业务范围修订可改变周包版本，不代表原名额失效。通过稳定的周额度池及修订映射继承已占用/消耗记录；不能每创建一个新版本就重新得到5个空名额。

额度账、费用账、成片交付账和发布账必须分开：释放名额不退回已花费用，生成成片不等于已发布，发布4次也不等于新作4条。

### 11.5 图、队列与业务状态的一致性

- 现有图已实现 `assets → render → quality → review → delivery`，属于生产子流程；不应直接宣称它已覆盖全部周计划、采集、编导、发布和客服流程。优先复用现有桥接及各阶段执行器，按需要扩展，不重复实现已有底层步骤。
- 周计划只编排与派单，每条内容独立运行生产图；每个平台独立分发，客服按消息事件运行。不把整个周包包进一张会被一个缺项整体挂起的巨图，也不为每个平台复制完整生产图。
- 图检查点保存执行位置与中间结果；额度、成本、授权和交付记录以业务服务的持久账本为准。恢复图时重新校验身份、版本、授权和原请求，不能信任恢复参数里的“已批准”。
- 名额预占、内容绑定和待执行命令应采用同一业务事务，或使用可对账的事务性Outbox等机制衔接。图检查点、消息投递和外部供应商不是一个数据库事务，必须承认并处理部分成功。
- 不要求所有层各维护一套可随意修改的完成状态。业务状态以验证过的运行事件/结果引用投影，提供图、队列、费用和产物不一致时的对账入口。
- 付费生成、渲染、上传、消息发送和发布均保存稳定操作ID、输入哈希、供应商请求号及结果；未知结果先查询原请求，不直接重复提交。框架恢复能力不等于外部动作天然只执行一次。
- 并发3条由统一生产准入和队列控制；资源池、账号发布限流及消息频控各自独立。不得把每个Agent都设为并发3而把整条链放大成多倍并发。
- 本地Mock使用独立身份与模拟证据；真实账本/发布准入不采纳模拟成功。后续接入真实WhatsApp不继承Mock权限或模拟交付。
