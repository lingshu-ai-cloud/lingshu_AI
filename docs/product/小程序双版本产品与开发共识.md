> 状态：持续讨论稿  
> 建立日期：2026-10-12  
> 适用范围：灵枢微信小程序运营版、管理版，以及与网页端共享的领域层和移动 BFF  
> 维护方式：每轮产品讨论后更新“已确认决策”“待确认问题”和“变更记录”  
> 上位视觉规范：`docs/product/PRD-灵枢AI全系统UI设计规范-v2-2026-10-09.md`

## 1. 文档目的

本文档记录灵枢小程序的产品定位、前端视觉方向、信息架构、技术路线、代码边界和阶段决策。它既是后续设计讨论的共识底稿，也是开发、评审和验收的依据。

小程序不是网页版的缩小版本。网页端适合复杂配置、批量操作和深度工作台；小程序承担随时查看、快速判断、现场执行和即时处理。两端共享账号、租户、权限、业务对象、状态规则和后端服务，但使用各自适合的界面结构。

## 2. 当前已确认的产品定位

灵枢小程序采用一个产品、两个工作版本：

### 2.1 运营版

服务一线运营、客服和内容执行人员，核心问题是：**我现在应该做什么，怎样尽快完成？**

首页和主要流程使用动词驱动：

- 去拍摄
- 去处理
- 联系客户
- 确认内容
- 查看执行结果

运营版强调任务、截止时间、下一步动作、现场拍摄、客户跟进和执行回执，减少经营图表、复杂排期和批量管理。

### 2.2 管理版

服务管理员和经营负责人，核心问题是：**当前经营是否正常，哪里需要我判断或干预？**

首页和主要流程使用数据及异常驱动：

- 待处理事项数量
- 核心经营指标及变化
- 待审批事项
- Agent 运行状态
- 风险与异常
- 任务进度和团队表现

管理版允许比运营版更高的信息密度，但首屏仍应优先展示结论和需要干预的事项，详细趋势和列表通过下钻查看。

### 2.3 两版关系

- 共用一个小程序 AppID、品牌、账号、组织、消息、个人中心和基础组件。
- 主包承载登录、组织身份、版本识别、版本切换和公共能力。
- 运营版和管理版分别使用分包。
- 管理员可以切换版本，普通角色直接进入有权限的版本。
- 版本切换只改变导航和默认工作视图，不构成安全边界。
- 数据和操作权限必须由服务端 capability 校验。

## 3. 工作区与分支策略

### 3.1 唯一开发工作区

- 工作区：`mobile-dual-edition-20261012`
- 分支：`codex/mobile-dual-edition-20261012`
- 基线提交：`5fb285d36b8cbf50ec74db2ba71ab441d3ef4164`
- 基线来源：`xixi数字员工联调v0`

旧的 `local-integrated-flow` 同时包含网页、小程序、后端及运行产物的未提交改动，只作为差异来源，不再作为双版本小程序开发区。不得在旧工作区执行批量提交、清理、重置或整体复制。

### 3.2 代码保护边界

| 路径 | 本项目处理方式 |
| --- | --- |
| `apps/shooting-miniapp/**` | 小程序主要开发范围 |
| `shared/**` | 仅增加跨端纯领域逻辑、契约和设计变量 |
| `server/**` | 仅增加或向后兼容扩展移动 BFF |
| `scripts/**` | 仅维护跨端代码生成和一致性检查 |
| `src/**` | 网页端保护区，小程序开发默认禁止修改 |

每次合并前执行网页路径门禁：

```bash
git diff --name-only 5fb285d...HEAD | rg '^src/'
```

正常结果应为空。确实需要网页适配时，必须拆到独立分支和独立提交，并单独完成网页回归。

### 3.3 推荐提交边界

1. 小程序双版本壳和导航。
2. 小程序共享移动组件。
3. 现有待办、助手和拍摄流程迁移。
4. 运营版首页移动投影接口。
5. 管理版首页移动投影接口。
6. 跨端 capabilities 和数据契约。

不同类别不混在同一提交中，以便独立评审、合并和回退。

## 4. 技术架构

采用 **单仓库、独立小程序 worktree、共享领域层、移动 BFF、双版本分包**。

### 4.1 小程序建议结构

```text
apps/shooting-miniapp/
├── pages/
│   ├── login/
│   ├── profile/
│   └── edition-switch/
├── packages/
│   ├── operator/
│   │   ├── home/
│   │   ├── todos/
│   │   ├── assistant/
│   │   ├── shooting/
│   │   └── customers/
│   └── management/
│       ├── home/
│       ├── approvals/
│       ├── agents/
│       ├── analytics/
│       └── risks/
├── components/
├── services/
├── lib/
└── styles/
```

现阶段保留 `shooting-miniapp` 目录名，等产品命名和迁移完成后再统一重命名，避免无意义的大范围路径变更。

### 4.2 可直接复用的代码基础

以下内容继续作为网页和小程序的唯一事实来源：

- `shared/design/tokens.json`：颜色、字号、间距、圆角、触控尺寸和动效。
- `shared/mobile-domain.mjs`：任务状态、角色、排期、紧急度和下一步文案。
- `shared/request-policy.cjs`：错误、版本冲突、请求锁、回执终态和幂等规则。
- `shared/action-form.cjs`：表单规范化、校验和 payload 构建。
- `shared/weekly-work-status.mjs`：工作状态。
- `shared/materialTaxonomy.ts`：素材分类。
- `shared/shootingWorkflow.ts`：拍摄流程。
- `shared/contracts/**`：跨端数据契约。
- `scripts/sync-mobile-shared.mjs`：生成及一致性门禁。

网页 React 组件、Ant Design 组件、Zustand、DOM/Portal、Recharts、Framer Motion 和桌面 CSS 不直接进入原生小程序。可以复用它们的信息结构、业务状态和交互语义，再以 WXML、WXSS 和微信小程序能力实现。

### 4.3 移动 BFF

在现有 `/api/overseas/mobile-workbench/**` 基础上扩展移动投影，不让小程序自行拼接大量网页接口：

```text
GET  /api/overseas/mobile/operator-home
GET  /api/overseas/mobile/management-home
GET  /api/overseas/mobile/todos
GET  /api/overseas/mobile/agents
GET  /api/overseas/mobile/approvals
POST /api/overseas/mobile/actions
GET  /api/overseas/mobile/actions/:receiptId
```

约束：

- 服务端从 token 确定用户和租户，客户端不提交租户作用域。
- 首页接口直接返回移动端需要的聚合结构。
- 写操作统一使用 `expectedVersion` 和 `idempotencyKey`。
- 长任务返回 `receiptId`，移动端展示真实节点和最终回执。
- 页面入口由服务端返回的 capabilities 控制，避免前端散落硬编码角色。
- 新接口以聚合和投影为主，复用现有底层业务服务。

## 5. 抖音来客参考图拆解

本次参考包括两张抖音来客截图：一张偏一线执行的运营界面，一张偏经营判断的管理界面。参考图用于分析成熟移动经营产品的信息组织和视觉手法，不作为逐像素仿制目标。

### 5.1 值得借鉴的总体层级

参考图从上到下形成稳定的六层结构：

1. **环境层**：浅色品牌背景，提供气质但不承载重要信息。
2. **身份层**：组织名称和版本切换，让用户明确当前组织及工作模式。
3. **核心工作层**：运营版展示高频动作，管理版展示关键数据和常用服务。
4. **任务层**：待办、预约、核销、售后、风险等可执行对象。
5. **成长与内容层**：活动、学习、指南等低优先级内容置于页面下部。
6. **全局导航层**：固定底栏保留稳定工作域。

灵枢应复用这种“身份—状态—行动—次要内容”的优先级，不复用来客具体业务文案和电商活动结构。

### 5.2 商务感的来源

参考图显得成熟和商务，主要来自秩序，而不是装饰：

- 所有卡片使用一致的左右边距和对齐线。
- 一个卡片区块只承担一种任务。
- 标题、内容、数字和动作位置保持稳定。
- 高频动作使用较大触控面积，低频能力收进列表或“全部”。
- 页面背景保持低对比，白色业务卡片承担主要内容。
- 图标、状态色和按钮帮助识别，不抢夺业务文字的层级。
- 底栏承担长期稳定的工作域，首页承担今天的优先级。

### 5.3 色彩策略

可取的色彩逻辑是“浅中性页面底 + 白色业务表面 + 品牌主色 + 语义状态色”：

- 蓝色表达可信、系统操作和当前导航。
- 绿色表达成功、安全或完成。
- 橙色表达经营增长和需要行动的提醒。
- 红色只表达紧急数量、风险和阻断。

灵枢不复制来客色值，继续使用现有 Token：黑灰正文、白色表面、蓝紫主操作、固定成功/等待/异常色。页面可引入非常浅的蓝灰分区底色，但不可形成另一套视觉体系。

渐变只用于：

- 极少量品牌区；
- 页面唯一主操作；
- 发出的消息气泡；
- 真实进度。

普通卡片保持白色。避免把每个指标、入口和模块做成重彩渐变卡。

### 5.4 卡片体系

第一阶段先建立六类标准移动组件，禁止每个功能自行设计卡片：

| 组件 | 用途 | 核心内容 |
| --- | --- | --- |
| 核心指标带 | 管理首页摘要 | 标签、数值、变化或时间口径、整体下钻 |
| 主行动卡 | 运营首页高频执行 | 图标、短动词、数量或状态、单一主操作 |
| 快捷服务宫格 | 次高频固定入口 | 统一图标、短标题，首屏最多 6–8 个 |
| 待办任务卡 | 运营与管理待处理 | 标题、状态、影响/价值、截止时间、一个主操作 |
| 风险/建议卡 | 管理干预 | 问题、影响、建议和明确处理入口 |
| 内容媒体卡 | 学习、素材和结果 | 稳定缩略图、标题、类型、时长或来源 |

建议移动尺寸基线：

- 页面水平边距：16px。
- 模块间距：12–16px。
- 卡片内边距：16px。
- 卡片圆角：遵循现有 `radius.panel`，不为参考图另加大圆角体系。
- 可点击列表行：至少 52px，触控目标不得低于 44px。
- 页面一级标题：20px；卡片标题：16px；正文：14px；辅助信息：12px。
- 普通卡片默认无阴影，以背景、分隔线和留白建立层级。

### 5.5 运营版视觉结构

运营版更接近行动工作台，信息要少而直接。推荐首屏顺序：

1. 组织名称、当前版本、消息入口。
2. 保留周日期切换，用于查看不同日期的工作安排。
3. 三项执行数字：待处理、待拍摄、待确认。
4. 两个横向排列的大型业务入口：“我的待拍”和“我的询盘”。
5. 今日卡点任务列表：列出所选日期在 Agent 排期日历中遇到卡点、需要人工介入的任务。

运营首页不设置“下一项任务”大型主卡，也不设置通用功能宫格。“我的待拍”和“我的询盘”是两个明确的核心业务入口，不扩展成多入口九宫格。任务优先级通过三项执行数字和今日卡点任务列表表达；稳定的一级功能由底部 Tab 承担。

当前工作页已有的六项指标、完整 Agent 排期和相关代码暂不删除，作为管理版首页候选能力保留；运营版首页不直接展示完整 Agent 排期。

今日卡点任务列表与完整 Agent 排期使用同一数据来源，但只投影运营人员需要介入的对象。每项至少展示：

- 任务名称和责任 Agent；
- 卡点类型和卡住的工作节点；
- 卡住时间或截止时间；
- 需要运营人员完成的下一步动作；
- 进入任务详情或执行页的入口。

列表不展示正常运行、无需人工处理的 Agent 日程。没有卡点时显示明确的正常状态，不用空白列表代替。

推荐底栏：

- 工作
- 待处理
- 灵小枢
- 消息
- 我的

“工作、待处理、灵小枢、消息、我的”均为独立一级页面。其中灵小枢是专门的对话页面，不是首页弹窗、浮动助手或快捷功能宫格入口。

运营首页不同时放入经营图表、完整 Agent 排期、大量快捷入口和学习内容。用户应在几秒内找到下一件事。

#### 5.5.1 待处理交互

- 保留卡片和列表双视图。
- 首页点击“待处理”数字后默认进入卡片视图。
- 卡片视图用于逐件处理；列表视图用于浏览、筛选和查找任务。
- 待拍任务保留右滑进入相机。
- 普通事项取消右滑直接执行，改为点击卡片主按钮或进入详情后处理。
- 左滑稍后处理保留，并提供短时撤销。
- 卡片直接展示任务类型、截止时间、当前状态和下一步动作。

#### 5.5.2 拍摄执行范围

运营版承担拍摄执行，不承担拍摄任务管理：

- 保留待拍任务、打开相机、从相册选择、上传进度、上传结果和关联失败后的重新关联。
- 运营人员不能在小程序中创建正式拍摄任务。
- 创建任务、复杂编辑和全部任务后台继续留在网页端或后续管理能力中。
- 已上传素材放在对应拍摄任务详情中查看，不设置“已上传”独立一级页面或一级底栏。
- 已完成任务允许追加素材，避免把追加误解为覆盖原素材。

#### 5.5.3 我的待拍

- 从运营首页“我的待拍”大按钮进入。
- 页面从上到下按日期排列待拍素材卡片，可使用日期分组或日期吸顶标题。
- 卡片展示拍摄任务、素材/镜头信息、截止时间、要求和完成状态。
- 用户逐个点击卡片进入任务详情并完成拍摄、选择素材和上传。
- 完成后返回列表，原卡片保留在原日期位置并显示明确勾选和“已完成”状态。
- 默认视图仍以未完成任务为行动重点，但完成态不能立即消失，避免用户无法确认刚才的操作结果。

#### 5.5.4 我的询盘

- 从运营首页“我的询盘”大按钮进入。
- 顶部使用“待确认”和“待跟进”两个分段 Tab，各自展示对应的用户会话列表。
- 会话列表复用网页版的客户数据模型、筛选字段、排序语义、搜索规则、未读状态和后端会话接口。
- 筛选能力继续支持来源渠道、国家/地区、语言、客户阶段、处理方式、客户标签、只看未读和高意向等现有条件；移动端使用底部 Sheet 承载筛选表单。
- 点击会话后进入单独的全屏客服对话页，不在手机上并排显示会话列表、聊天窗口和客户资料三栏。

移动客服对话页采用以下结构：

1. 顶部栏显示返回、客户名称、渠道和当前处理状态。
2. 中间是唯一的消息滚动区。
3. 底部固定输入区；点击文本区域唤起系统键盘输入。
4. 输入框左侧设置“＋”按钮。
5. 点击“＋”打开快捷能力面板，承接网页版右侧客户资料栏和其他辅助动作。
6. 快捷面板中的能力按小型 Tab/分段页组织，点击后进入内嵌内容页，不离开当前会话上下文。

第一批可迁移到“＋”面板的网页版能力包括：

- 客户资料：来源、产品、阶段、预计价值和下一步；
- 客户与销售工作台：意向处理、人工接管、生成回复、报价能力；
- 会话内搜索；
- 文件、媒体和链接；
- 分享客户摘要；
- 会话通知；
- 隐私设置与支持。

这些能力应按移动使用频率分批放入面板，不能一次平铺所有网页版右栏内容。首屏优先客户资料、生成回复/报价、媒体文件和会话搜索。

技术复用边界：

- 直接复用后端接口、鉴权、客户与会话数据模型、筛选规则、排序、发送状态、幂等与回执逻辑。
- 可将网页端纯函数和无浏览器依赖的状态规则抽到 `shared/**`，由两端共同使用。
- React、Ant Design、Popover、Collapse、DOM/localStorage 实现不直接装入原生小程序；移动端使用 WXML/WXSS、`wx.request`、小程序存储、底部 Sheet 和原生键盘重新实现呈现层。
- 网页端已有的 `list/chat/profile` 响应式切换只作为业务能力参考；小程序按“列表页 → 全屏对话 → ＋快捷面板”重新组织。

### 5.6 管理版视觉结构

管理版是轻量经营驾驶舱。推荐首屏顺序：

1. 组织名称、当前版本、消息入口。
2. 3–4 个核心指标组成连续指标带。
3. 最需要干预的事项。
4. 待审批和风险异常。
5. Agent 运行摘要。
6. 趋势、排行和经营建议的简化入口。

推荐底栏：

- 总览
- Agent
- 审批
- 消息
- 我的

指标只展示真实口径和时间范围。图表先给结论和趋势，详细数据进入下钻页面。管理首页不能演变成无限模块的信息门户。

### 5.7 助手的呈现

参考图中的悬浮卡通助手容易遮挡内容，也会削弱企业工具的专业感。灵小枢应采用以下方式：

- 作为运营版底栏的稳定入口。
- 在管理版作为消息或决策入口进入。
- 在具体任务中提供与当前上下文关联的建议和轻操作。
- 首次进入优先展示真正需要确认或审批的事项。
- 不使用持续悬浮、遮挡卡片的卡通形象。
- 普通回答使用轻量文本气泡；任务摘要、决策、确认和回执使用结构化卡片。

### 5.8 不照搬的部分

- 不复制管理版过长的首页和过多营销模块。
- 不使用大量橙色活动卡削弱专业感。
- 不把所有功能塞进九宫格。
- 不重复使用卡通智能助手遮挡业务内容。
- 不让每个列表项都出现同等级的“去处理”。
- 不复制电商核销和促销文案。
- 不把运营版和管理版简单做成同一页面换数据。

## 6. 当前小程序视觉问题与重构原则

当前页面虽然已有工作台、待办、助手、拍摄和操作详情，但整体更像功能原型：模块层级、页面节奏和组件类型不够稳定，同一屏中容易同时出现多个竞争焦点。局部功能修改无法从根本上解决视觉问题。

已识别的具体问题：

- `workbench` 同时承载首页、待办、助手、通知和多种弹层，模板和状态过度集中，还没有真正的业务组件目录。
- 页面大面积使用纯白底、白卡和灰色边框，卡片、指标、输入和弹层缺乏表面层级，视觉接近工程表单。
- 页面样式重复覆盖共享 Token，圆角、内边距、标题字号和状态色不统一。
- 多处使用 Unicode 字符充当图标，线重、基线和视觉风格不一致。
- 工作首页同时展示周切换、六项指标、同步信息和完整 Agent 时间线，首屏没有唯一重点。
- 操作详情把证据、费用、失败分镜、素材、连接和方案连续堆叠，缺少“问题—判断—操作”的阅读节奏。
- 拍摄页把筛选条件做成一级底栏，页面导航和内容筛选语义混淆。
- 待办、拍摄和助手已经具备业务能力，但缺少缩略图、任务视觉锚点、稳定的结构化卡片和明确的操作层级。

本轮保留现有 Token、共享领域逻辑、待办滑卡、拍摄上传、权限、执行确认、回执和错误处理；重做页面壳、信息架构和组件呈现，不重复建设已经可靠的业务能力。

重构遵循以下原则：

1. 先确定页面目标和首屏信息，再写页面壳。
2. 每个页面只有一个主要任务和一个最高优先级操作。
3. 使用连续指标带，避免碎片化 KPI 卡墙。
4. 使用少量标准卡片类型，避免页面各自发明视觉样式。
5. 状态必须有文字，颜色只辅助识别。
6. 普通业务卡片保持克制，真实媒体、数字和业务状态成为主视觉。
7. 拍摄、待办、审批等执行流程优先使用任务卡、底部 Sheet 和全屏步骤页。
8. 动效只表达空间关系和状态变化，不使用无意义浮起、发光、呼吸或纸屑效果。

## 7. 骨架开发前置确认

双版本骨架不是先创建目录和底栏。开始页面开发前，必须先确认三张核心页面蓝图：

1. **运营版首页**：首屏模块顺序、主要动作数量、最高优先任务的呈现。
2. **管理版首页**：指标数量、待干预事项、Agent 和风险摘要的先后顺序。
3. **共用处理流程**：待处理卡片、灵小枢建议、执行确认和回执如何衔接。

每张蓝图至少确认：

- 页面目标；
- 第一眼看到的信息；
- 首屏唯一主操作；
- 模块顺序；
- 使用的标准组件类型；
- 点击后的页面或 Sheet；
- 空状态、加载、异常和无权限状态；
- 运营版与管理版的可见权限。

确认以上蓝图后再实现主包、分包、导航和组件骨架，使技术结构服务于已确认的产品结构。

## 8. 建议开发阶段

### 阶段 0：视觉和信息架构确认

- 完成三张核心页面低保真构图。
- 明确两版底栏和版本切换方式。
- 确认六类标准移动组件。
- 确认设计 Token 是否需要增加移动页面背景和功能图标色。

### 阶段 1：双版本骨架

- 登录态和组织身份复用。
- 版本识别与切换。
- 运营版、管理版分包。
- 两套底部导航。
- 公共组件、状态页和权限不可用页。

### 阶段 2：运营版闭环

- 运营首页。
- 待处理事项。
- 右滑进入拍摄。
- 拍摄上传。
- 灵小枢。
- 操作确认和执行回执。

目标是形成“看到任务—执行—获得回执”的完整链路。

### 阶段 3：管理版闭环

- 管理首页指标。
- 待审批事项。
- Agent 排期和运行状态。
- 风险异常。
- 详情下钻。
- 管理动作和执行回执。

### 阶段 4：移动 BFF 固化

页面信息结构稳定后固化聚合接口，减少后端围绕频繁变化的 UI 重复返工。

### 阶段 5：回归和交付

- 小程序单元测试。
- `check:mobile-shared`。
- 移动 BFF 测试。
- 网页构建和关键流程回归。
- 真机安全区、键盘、弱网、长文字和权限状态验收。

## 9. 验收原则

- 网页保护区 `src/**` 默认零改动。
- 运营版用户进入首页后能在数秒内找到下一件事。
- 管理版用户进入首页后能判断经营状态和最需干预事项。
- 两版共享基础视觉语言，但信息密度和任务结构明显不同。
- 所有数字有口径，所有状态有文字，所有动作有结果回执。
- 不以假数据、假趋势或定时器伪造业务进度。
- 微信键盘、底部安全区、长文本、无数据、接口失败和无权限场景可用。
