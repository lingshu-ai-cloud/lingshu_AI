# 灵小枢回答质量与上下文管理方案

日期：2026-10-10  
状态：首版已开发并完成代码与隔离接口验证；本地预览联调和发布门禁记录见第 13 节。按用户要求暂不上线。  
范围：灵小枢作为经营主 Agent 的定位、回答质量要求、SaaS 上下文调研、长期记忆和验收方案。

## 1. 核心结论

建议以经营 Agent 为基础，让灵小枢成为统一对话与经营统筹入口；编导、内容、发布、客服等专业执行能力继续在后台分工。身份合并本身不会自动提升回答质量，关键是让主 Agent 能按需读取跨领域的真实状态和历史决策。

长期保存的业务数据可以持续增长，但每次送给模型的上下文必须按问题重新组装、控制规模。灵小枢应该掌握经营全貌的读取能力，而不是在每一轮记住全部经营细节。

长上下文不必然导致幻觉，短上下文也不能保证正确。风险主要来自无关信息干扰、旧新事实冲突、证据缺失、摘要失真以及模型把自己的建议当成已经发生的事实。工程上应同时解决“塞得太多”和“忘得太快”。

## 2. 当前项目的观察与边界

本节记录开发前基于本地 `local-preview-v2` 的静态核查，不代表线上部署。已实施情况见第 12 节；改动已合入当前本地预览使用的 `local-integrated-flow`。

- `src/components/GlobalAssistant.tsx` 将经营 Agent 映射到 `strategy`，请求路径为 `/api/overseas/strategy/chat`。
- `send()` 附加当前页面、当前模块、北京时间、企业中心摘要和实时接入事实。
- `apiHistory()` 仅保留最近 8 条消息，助手消息和用户消息分别按 1200、800 的长度参数压缩；这是文本长度控制，不是完整的 token 预算，也不是业务记忆。
- `loadLiveIntegrationFacts()` 汇总社媒账号、YouTube 账号、采集视频与客户档案等信息，并明确客户档案不等于询盘。
- 目前查看的前端路径尚不能证明每次回答都读取了跨 Agent 任务、审批、发布回执、销售结果和历史决策；后端是否补充这些内容，需要进一步审计。
- 当前提示中要求不要以“缺少数据”等句式开头。建议改为“先回答能够确认的部分，但证据不足时允许直接说明”，避免对表达流畅的追求掩盖真实缺口。

因此，现状不能简单描述为“所有历史无限堆积”。前端已有裁剪；更值得检查的是关键约束是否被持久化、实时状态是否齐全，以及后端实际组装了什么上下文。

### 2.1 后端补充核查：已有分类保存，缺口在回答接入

后续静态核查确认：企业事实已在独立企业资料中保存并有事实版本；业务流程已有部分决策与审批记录；周任务、执行状态和工作流事件已有持久化；发布、报价和产物相关证据也已有领域保存机制。因此，不应将方案解读为“目前完全没有分别保存”。

当前 `server/routes/strategy.ts` 的 `/chat` 明确加载企业资料，再把前端提供的消息交给模型。在这条处理路径中未看到统一读取周任务、业务决策和执行证据的逻辑。普通聊天中的决定是否成为独立长期记忆，也不能由已有业务审批记录推断出来。

实施重点：复用现有领域数据建立受权限控制的回答读取层；补齐用户明确保存的对话决策记忆，防止建议被当成授权；保持来源、阶段、版本、范围和查询失败状态。此核查针对本地代码，未验证生产部署和数据库实际记录。

## 3. 市面上类似产品怎么处理上下文

以下为官方公开资料可确认的机制。公开说明不能揭示厂商全部内部架构，也不能据此比较实际幻觉率。产品能力随版本与配置变化。

| 产品 | 官方公开机制 | 对灵小枢的启示 |
| --- | --- | --- |
| Salesforce Agentforce | 使用 CRM 等结构化数据，以及文档等非结构化数据进行 grounding；RAG 检索相关知识作为回答依据 | 当前任务与客户状态查业务系统，知识说明查文档；不要全部当聊天文本处理 |
| Intercom Fin | 先理解问题，再检索相关内容、动态数据与动作，生成后检查回答准确性和依据 | 上下文选择和回答验证都需要建设，不能只优化提示词 |
| Notion Enterprise Search | 搜索工作区及连接应用，支持限定搜索范围；基于内部来源回答时提供引用，并遵循访问权限 | 检索范围、引用和权限属于上下文管理本身 |
| Microsoft Copilot Studio | 将知识源用于生成回答；可配置源与字段过滤，不同连接方式具有不同索引或实时读取行为 | 文档索引和实时业务查询应分别设计，并显式管理同步延迟 |

来源：[Salesforce grounding](https://trailhead.salesforce.com/content/learn/modules/grounding-an-agent-with-data/learn-the-basics-of-grounding)、[Intercom Fin AI Engine](https://www.intercom.com/help/en/articles/9929230-the-fin-ai-engine)、[Notion Enterprise Search](https://www.notion.com/help/enterprise-search)、[Notion 权限说明](https://www.notion.com/help/enterprise-search-security-and-privacy-practices)、[Copilot Studio 知识源](https://learn.microsoft.com/en-us/microsoft-copilot-studio/knowledge-improve)、[Copilot Studio 数据过滤](https://learn.microsoft.com/en-us/microsoft-copilot-studio/use-your-own-prompt-data)、[连接器模式比较](https://learn.microsoft.com/en-au/microsoft-copilot-studio/knowledge-graph-vs-power-platform-connectors)。

从这些公开机制可以归纳出一个适合本项目的模式：外部保存知识与业务事实，按问题检索或实时查询，将少量相关证据交给模型，再校验关键结论。这是本方案的归纳，不是上述产品完全相同的内部实现。

## 4. 时间推进后，会不会越来越长并导致幻觉

### 4.1 区分三种增长

1. **业务记录增长**：客户、视频、任务、审批、指标越来越多，是正常的数据积累，应由数据库、对象存储和索引承载。
2. **会话记录增长**：完整聊天可以保存用于回溯，但无需每轮全量发送。
3. **推理上下文增长**：只有这一部分直接占用模型本轮窗口，应通过选择、检索、裁剪与摘要控制。

上下文窗口是模型单次处理信息的容量；数据库保存量不是上下文窗口。窗口变大也不意味着模型对每一条信息都同样可靠。

### 4.2 研究能说明什么

《Lost in the Middle》在多文档问答和键值检索中发现，相关信息的位置影响表现，位于长输入中部的信息更容易被遗漏。它支持“能容纳不等于能可靠利用”的判断，但研究中的模型与任务不能直接推算本项目当前模型的幻觉率，也不能推出上下文长度与幻觉率必然单调相关。[论文](https://arxiv.org/abs/2307.03172)

Anthropic 的工程说明建议按需加载信息，并通过会话压缩、结构化笔记和任务分工管理长时间工作；同时提醒过度压缩可能丢失关键细节。[官方工程说明](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### 4.3 灵小枢的具体失败方式

| 失败方式 | 示例 | 对策 |
| --- | --- | --- |
| 旧事实覆盖新事实 | 已改主推产品，仍按旧产品安排内容 | 字段版本、有效期与替代关系 |
| 建议被当成事实 | “建议发 10 条”后来被记成“已发 10 条” | 区分建议、授权、执行、回执 |
| 概念混淆 | 客户档案数量被说成询盘数 | 指标定义和事件证据 |
| 摘要漏掉条件 | 忘记“只做英语、暂不自动发布” | 关键约束独立存储 |
| 摘要反复改写 | 多轮压缩后把原因、时间和数字写错 | 从原始记录重建，保留来源 |
| 检索找到旧文档 | 检索到旧报价和过期政策 | 元数据过滤、时效与版本排序 |
| 查询失败被当成零 | 接口超时后回答本周没有询盘 | 区分零值、未知、失败和部分结果 |
| 多 Agent 报告冲突 | 制作完成但发布失败，却称全流程完成 | 分阶段状态与权威证据 |

RAG 是降低无依据回答风险的手段，不是消除幻觉的保证。检索遗漏、数据过期、错误引用和模型误读仍然需要检查。

## 5. 灵小枢应达到的回答质量

### 5.1 对外身份与职责

灵小枢承接用户意图、解释经营现状、统筹任务、提出建议并记录决策。后台专业 Agent 接收范围明确的任务，返回结构化结果和证据。用户无需为了同一经营问题分别切换多个对话人格。

对外统一身份不等于后台共享全部聊天；专业 Agent 只读取完成任务所需的数据，主 Agent 接收结果摘要及来源引用。

### 5.2 每次回答的要求

- 承接用户已确认的目标、约束和近期决定，不重复询问已保存的信息。
- 数字带时间范围、口径和来源；增长率、总额等由查询或确定性计算产生。
- 明确区分已确认事实、分析判断、建议和待核验项。
- 查询进展时先查最新状态，不仅凭聊天记忆作答。
- 缺少证据时不编造完成情况、成交、价格、交期或平台结果。
- 提供可执行下一步；涉及实际动作时沿用已有权限与审批流程。
- 用户纠正后形成可追溯的变更，后续回答使用新版本。
- 无需展示内部提示和技术流程，但应允许用户查看关键业务证据。

默认回答顺序：直接结论 → 关键依据 → 下一步。证据不足会影响结论时，应在结论附近说明，不藏到结尾。

## 6. 推荐上下文架构

### 6.1 分层存储，按问题组装

| 层 | 保存内容 | 本轮如何读取 |
| --- | --- | --- |
| 行为规则 | 身份、权限、事实要求、工具规则 | 受控版本，稳定载入 |
| 企业事实 | 产品、市场、语言、品牌、已确认限制 | 读取当前有效字段与相关详情 |
| 经营状态 | 当前目标、任务、待决策、预算、阻塞 | 根据问题实时查询 |
| 决策记忆 | 用户确认的选择、原因、范围、失效条件 | 按项目、对象与时间检索 |
| 文档知识 | 企业材料、知识库、方案、政策 | 检索相关片段及原文引用 |
| 会话记忆 | 最近交流、尚未解决事项、指代对象 | 最近完整轮次加结构化摘要 |
| 执行证据 | 产物、审批版本、发布回执、询盘事件 | 携带引用，必要时读取细节 |

业务状态以领域数据库为准；文档用于知识依据；聊天用于理解意图。向量检索适合查相关描述，不应单独承担精确任务计数、金额计算或审批状态判断。

### 6.2 建议的回答流程

1. 确定问题涉及的对象、时间范围和业务领域，理解“这个”“上次”等指代。
2. 在服务端检查租户、用户、对象权限；前端页面文本不能成为权限或事实的唯一依据。
3. 查询相关经营状态，检索企业资料与决策记录；缺少跨域证据时补查，而不是让模型填空。
4. 去重并处理版本冲突，组装本轮上下文，保留来源、查询时间和数据覆盖情况。
5. 生成回答；关键数字、任务状态、外部动作结果必须能映射到证据。
6. 校验不通过时补查、修正或明确限定结论。模型自检可辅助，但不能替代确定性规则。
7. 记录使用的数据版本和引用，支持排查；仅将适合长期保存的信息写入记忆。

若生成前后发生状态变更，提交实际动作前应再核验对应版本，避免根据已过期的回答执行。

### 6.3 事实与记忆记录

建议记录包含：`tenantId`、对象 ID、来源类型与 ID、版本、有效起止时间、核验时间、状态、权限范围和替代关系。业务发生时间与系统写入时间分别保存，以支持历史回溯。

事实状态至少区分：已核验、用户明确提供、待核验、已过期、存在冲突。来源不同不代表统一高低排序：用户可以改变目标与偏好，但“已经发布”需要发布回执；第三方指标也必须记录采集时间与口径。

模型输出默认属于建议或分析。只有经过明确业务流程确认，才能成为已确认决策；只有实际执行证据才能成为完成事实。不能通过反复摘要把猜测升级为事实。

## 7. 如何防止长期上下文膨胀

### 7.1 输入预算

首版可以把普通问答的输入目标设为约 8k–16k tokens，复杂经营复盘按需提高，并为输出与后续工具调用预留空间。这是试运行参数，不是行业标准或最佳值，应按实际模型、费用、延迟和正确率调整。

稳定规则、有效约束和关键证据优先保留；冗余工具结果、重复解释和无关历史优先移出。超过预算后应明确选择补查、分步分析或缩小范围，不能默默截掉决定结论的证据。

### 7.2 会话摘要与长期记忆

- 摘要按 token 压力触发，保留目标、用户约束、已确认决策、未解决问题、当前对象和来源引用。
- 最近对话尽量按完整轮次保留，避免简单截断造成指代丢失；有关联的工具调用与结果应成组处理。
- 长期记忆按对象独立保存，支持更正、撤销和删除；不能仅存在一段不断变长的总摘要中。
- 变化频繁的状态在回答时查新值，摘要只保存其引用或历史含义。
- 周期复盘从事件与原始记录生成，不无限依赖上一轮摘要；必要时追溯原文。
- 用户要求“为什么上个月这样安排”时读取历史有效版本，不能用今天的目标解释过去。

### 7.3 更新和失效

任务、审批、发布回执和关键业务字段变更后，更新相关投影并使对应缓存失效。外部指标记录同步延迟；失败查询不得覆盖最后已核验值，也不得冒充最新值。删除和权限撤销应传播到索引、缓存和记忆。

缓存和大窗口可以优化性能或容量，但不会自动解决来源错误、版本冲突和摘要失真。

## 8. 跨 Agent 如何回流

建议统一返回：任务 ID、Agent 角色、阶段状态、输入事实版本、产物引用、证据引用、阻塞原因、待决策项、更新时间和后续建议。

主 Agent 根据领域权威状态回答，不根据“Agent 说完成了”直接宣布结果。尤其应分别表示：方案完成、制作完成、审批通过、发布提交、平台发布成功、指标采集成功和销售成交。前一阶段完成不能自动推出后一阶段完成。

示例：内容 Agent 已交付 3 条视频，发布服务仅确认 2 条成功，则灵小枢应回答“已制作 3 条，其中 2 条已发布成功，1 条仍待处理”，并提供阻塞原因；不能回答“3 条都已上线”。

## 9. 分期落地

### P0：回答先有统一事实依据

统一灵小枢主对话身份；服务端组装企业事实、当前目标、任务、待决策、发布与销售证据；补齐时间范围和指标定义；将零值、未知、失败、部分数据明确区分；建立证据引用和关键结论检查。

### P1：让长对话保持一致

建立独立决策记忆、完整轮次裁剪、带来源的结构化摘要和 token 预算；支持更正与失效；跨 Agent 采用结构化交接并同步业务投影；保留历史版本。

### P2：持续改善

按问题类型调整检索与预算，建设跨周期复盘；分析错误发生在意图理解、查询、检索、组装还是生成环节。先验证收益，再引入更复杂的记忆基础设施。

本方案的后续开发已启动，实际完成范围、验证结果与剩余限制见第 12 节。生产环境尚未变更。

## 10. 验收与长期退化测试

建议首批整理至少 50 个代表性问题，每个包含标准事实、必需证据、允许结论和禁止结论；数据明确标识为测试夹具。以下数量和门槛都是本项目建议，需通过首轮基线校准。

| 场景 | 必须验证 |
| --- | --- |
| 企业从 A 产品改成 B 产品 | 新回答使用 B，历史回溯仍正确解释 A |
| 只允许英语输出，跨越多次摘要 | 约束仍生效 |
| 建议发布但未批准 | 不宣称已授权或已发布 |
| 客户档案 20 条，无询盘事件证据 | 不把档案数当询盘数 |
| 发布服务返回失败或部分成功 | 精确说明阶段和缺口 |
| 接口超时 | 不回答为零，不假装查到数据 |
| 历史摘要与当前业务记录冲突 | 使用对应时点的权威证据并说明冲突 |
| 改变证据位置并加入无关历史 | 比较回答质量是否退化 |
| 100、300 轮对话及多轮压缩 | 关键决策、实体指代和证据保持正确 |
| 另一租户的同名客户或文件 | 不进入检索结果或回答 |
| 删除记忆或撤销权限 | 后续回答不继续泄露被移除信息 |

监测：关键事实正确率、无依据断言率、引用支持率、最新状态使用率、关键约束保留率、检索证据召回率、数据缺口表达正确率，以及 p95 延迟和每问成本。

上线前，跨租户泄露、捏造成交或发布成功、建议被当成授权等关键错误，在验收集中必须为零；这不等于保证生产环境永远零错误。其他质量指标以基线和目标共同评估，长会话版本应与短会话版本对比。

## 11. 最终设计原则

灵小枢的长期能力来自可查询、可更正、可追溯的经营记录。每次回答只携带足够支持当前问题的有效信息。通过这种设计，使用时间变长可以增加可用经验和证据，而不必持续增加单次输入长度。

“有依据地回答、持续承接决策、读取真实进展”比“上下文最长”更适合作为灵小枢的质量目标。

## 12. 首版实施记录（2026-10-10）

### 12.1 已完成的功能

- 默认助手入口进入“灵小枢 · 经营统筹”；保留编导、内容和客服的专业入口与既有工作流。
- 服务端按问题类别选择进度、效果、目标或综合来源，复用 14 类现有经营数据，包括目标、工作流、审批、规则决策、周包、内容任务、发布回执、指标、复盘、订单与报价询盘。
- 每类读取至多 4 条记录，经营证据文本限制为 10,000 字符；企业资料与近期记忆分别限制为 12,000、6,000 字符附近。采用字符预算控制输入规模，尚非模型级精确 token 计量。
- 读取保留来源、业务时间、状态和截断说明，失败与空结果分别标识；局部样本不能计算全量营业额或本周总成果。
- 企业资料只读取当前租户的持久化记录，缺失时不注入全局演示资料；关闭 AI 访问或资料读取失败时不继续加载其他经营事实。
- 全局经营任务与证据仅对严格验证的 admin/super_admin 角色加载；普通角色不自动获得租户全局数据。
- 用户可对自己的原话明确点击保存、查看近期记忆与撤销；修改和撤销采用不可变版本及版本冲突校验。记忆按租户和用户隔离，不能代替执行审批或授权。
- 最近聊天按完整轮次保留，默认最多 6 轮、12,000 字符；较早约束最多保留 3,000 字符原文，明确标记为历史请求且新输入优先。
- 账号或支持会话切换时清理助手状态并丢弃旧会话的异步响应，防止旧资料混入新账号。
- 经营聊天不再接收前端企业摘要和接入统计作为权威事实，页面信息仅用于导航与问题理解。
- 删除强制隐藏数据不足的提示及预设行业示例，避免旧示例和语种推断污染回答。

### 12.2 接口与迁移

新增经营记忆接口位于 `/api/overseas/strategy/decisions`：GET 读取近期有效记忆，POST 明确保存，PATCH 按版本修改，DELETE 按版本撤销。身份来自服务端认证，客户端不能指定租户或用户。支持会话仍禁止写入。

新增 PocketBase 迁移：`1791586800_create_assistant_decision_memories.js`。新集合仅由服务端访问，包含用户、租户、逻辑记忆 ID、版本、内容、来源引用、确认时间、失效时间与状态；唯一索引阻止同一记忆版本被并发覆盖。PostgreSQL 的通用记录存储沿用现有 collection/id 唯一约束，不新增专属 SQL 表。

来源引用 `user-confirmed-text:<hash>` 表示用户明确确认的文本，不能伪称为已经核验的服务端聊天事件 ID。

新增 `test:assistant-quality` 并接入既有 `quality` 门禁。迁移测试使用隔离临时数据库，验证首次应用、重复应用、唯一约束、回滚和重放，不访问现有业务库。

### 12.3 当前限制与后续验收

- 经营读模型提供限量近期记录，不提供全周期指标聚合；遇到全量统计问题应限定结论并提示核验范围。
- 记忆查询最多扫描近期 100 个版本，解析至多 20 条逻辑记忆，再受单次上下文预算限制；不承诺任意久远的决定必然进入每次回答。完整历史检索与跨周期记忆整理属于后续迭代。
- 本地独立订单文件尚未进入该读模型；`tenant_orders` 的空结果不能推断本地台账没有订单。
- 长对话回归覆盖 300 轮历史、输入规模及关键约束保留；真实模型对回答的事实使用正确率仍需基于验收问题集评估。隔离假模型的 HTTP 流式测试只证明传输与上下文组装，不证明语言模型无幻觉。
- 当前请求尚未使用结构化模型判定来识别全部意图；类别关键词可能漏检，需要根据实际问题继续优化。
- 本机浏览器自动化因管理策略校验不可用而未能打开验证页，未绕过该限制。自动化代码、HTTP、权限与迁移验证不能替代最终视觉验收。
