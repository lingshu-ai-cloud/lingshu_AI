# 图片生产与灵小枢共享接口说明

> 日期：2026-10-24
>
> 适用范围：自由创作模式下的单条图片生产
>
> 图片实现分支：`codex/image-generation-content-task-20261024`
>
> 对接对象：后续合并的首页灵小枢对话分支
>
> 边界：本文只定义任务绑定、状态读取和用户决定接口；不包含真实付费生成、自动发布和数字员工周任务改造。

## 1. 对接结论

灵小枢不应自己拼装图片工作流，也不能根据等待时间猜进度。它只做四件事：

1. 先创建或取得唯一的 `ContentTask`；
2. 用该任务创建／恢复一个图片子运行；
3. 按服务端快照和追加事件更新同一张对话任务卡；
4. 将用户的采用／拒绝操作连同精确候选版本交给图片服务。

图片服务是图片节点、候选版本、质检结果、返工谱系和批准成品的事实源；`ContentTask` 是业务目标、产品、平台、语言和任务身份的事实源；聊天消息不是生产状态源。

## 2. 身份关系

```text
conversation/thread
  └─ ContentTask（唯一业务任务）
       └─ SocialImageProductionRun（图片子运行）
            ├─ 16 个版本化节点
            ├─ 候选图片与质量结果
            ├─ 显式用户验收凭证
            └─ DeliveryPackage（仅交付，不代表发布）
```

同一租户、同一 `contentTaskId`、同一 `deliverableKey` 只对应一个确定性的图片子运行。重复点击、请求重试和刷新应恢复它，不得再建一条任务或重复扣费。

## 3. 灵小枢调用接口

### 3.1 创建或恢复图片子运行

```http
POST /api/overseas/social-images/content-tasks/:contentTaskId/runs
Idempotency-Key: <一次用户业务动作的稳定键>
Content-Type: application/json

{
  "expectedContentTaskVersion": "7",
  "deliverableKey": "primary-image",
  "entrySource": "assistant",
  "imageType": "product_poster"
}
```

响应：

```text
task       图片子运行完整数据
resumed    true 表示恢复已有运行，false 表示首次建立
snapshot   面向前端的权威状态投影
```

约束：

- `ContentTask` 必须存在于当前租户，且版本完全一致；
- `Idempotency-Key` 不少于 8 个字符，重试必须复用；
- `entrySource=assistant` 用于首页对话；`workspace` 供兼容工作台使用；
- 同一交付物若更换图片类型会返回范围冲突，不能覆盖原运行；
- 旧的 `POST /tasks` 与 `POST /tasks/from-reference` 不再允许创建无 `ContentTask` 根节点的图片任务。

### 3.2 读取状态并断线恢复

```http
GET /api/overseas/social-images/tasks/:runId/production?afterSequence=18
```

响应：

```text
snapshot   当前权威快照
events     sequence > afterSequence 的增量事件，单次最多 100 条
```

`snapshot.previews[]` 提供当前未过期候选的 `candidateId / candidateVersion / contentHash / state / mediaUrl / materialId`；事件的 `artifactRefs[]` 提供事件发生时的候选版本与实际字节哈希。首页不得从 URL 或消息顺序推断候选版本。

灵小枢 BFF 可将该结果接入首页统一事件流；本图片分支提供可轮询快照和游标事件，不单独创建第二套聊天 SSE。

恢复规则：

1. 首次打开或断线重连先读快照；
2. 再从最后确认的 `sequence` 补事件；
3. 按 `eventId` 去重；
4. 本地消息、计时器和动画不得覆盖服务端状态；
5. `progress.kind=indeterminate` 时只能显示节点状态，不能显示虚构百分比。

### 3.3 ContentTask 已更新

```http
POST /api/overseas/social-images/tasks/:runId/refresh-content-task

{
  "expectedVersion": 12,
  "expectedContentTaskVersion": "8"
}
```

该操作会重新绑定最新业务输入，并将所有受影响的下游节点追加为 `stale`。旧证据保留用于审计，但不得混入新版本继续生产。

### 3.4 准备素材与参考图证据

```http
POST /api/overseas/social-images/tasks/:runId/evidence/prepare

{
  "expectedVersion": 12
}
```

服务端只读取当前租户的企业知识库图片和素材库图片。它在付费生成前完成：

- 强制企业资产实际字节解码、SHA-256、尺寸与 OCR 观察；
- 爆款参考图实际字节冻结；
- 九宫格归一化区域、区域裁切哈希、亮度、对比度、边缘、显著性顺序与 OCR 区域；
- 写入正式的 `asset_manifest / reference_snapshot / element_inventory` 节点结果。

必需资产或爆款参考图不可读取时返回 422 并保留阻断节点，不能删除 `productIds` 后继续。外部参考 URL 必须先物化为当前租户可读取的企业资产或素材记录；服务端不会从任意外部 URL 抓取图片。

### 3.5 独立编导复核

```http
POST /api/overseas/social-images/tasks/:runId/director-review

{
  "expectedVersion": 21,
  "candidateId": "candidate-a",
  "candidateVersion": 2
}
```

浏览器只能选择候选，不能提交 `accept` 或 `repair` 结论。服务端依据已持久化的硬检查和参考结构证据生成决定；任何硬检查缺失、失败或不确定都会失败关闭。

### 3.6 用户验收候选

```http
POST /api/overseas/social-images/tasks/:runId/decision

{
  "expectedVersion": 22,
  "candidateId": "candidate-a",
  "candidateVersion": 2,
  "expectedContentHash": "<候选实际字节的 sha256>",
  "decision": "approved | rejected",
  "note": "可选的修改意见"
}
```

批准必须同时满足：

- 候选 ID、版本和实际文件字节哈希完全一致；
- 所有硬质量门已通过；
- 独立编导复核为 `accept_for_user_review`；
- 任务没有待确认事实，且不是模拟事实；
- 当前工作流确实停在 `user_approval / needs_review`；
- 操作者通过本接口作出显式决定。

自动预检、生成 Agent、前端通用 PATCH 和聊天文案都不能代替用户批准。用户拒绝可直接形成返工要求，不必先把不合格候选伪装成质检通过。

### 3.7 创建交付包

```http
POST /api/overseas/social-images/tasks/:runId/delivery-packages

{
  "expectedVersion": 23
}
```

它只把已冻结的批准图片、平台、比例、语言和文案形成幂等交付包，不调用社媒平台、不写发布成功、不代表发布授权。

## 4. 前端只依赖的快照字段

| 字段 | 含义 | 展示规则 |
| --- | --- | --- |
| `businessStage` | `clarify / plan / produce / accept` | 转为“核对信息／形成方案／制作中／等待验收” |
| `currentNode` | 当前真实节点 | 用业务中文映射，不能直接展示枚举 |
| `currentStatus` | 当前节点状态 | 决定旋转、等待用户、失败或完成样式 |
| `progress` | 真实进度 | 仅 `known` 时显示分子／分母 |
| `activityKey` | 稳定文案键 | 由前端本地化为一句业务说明 |
| `waitingFor` | `system / user / provider_reconciliation / null` | 决定是否显示操作和“请勿重复提交” |
| `canApprove` | 是否允许进入采用操作 | 仍须由服务端重新验证，不是权限证明 |
| `blockingReasons` | 结构化阻断原因 | 映射成缺产品、缺授权、需核对结果等文案 |
| `previews` | 当前候选 ID、版本、实际字节哈希和媒体引用 | 只展示未过期候选；决定操作必须原样回传版本和哈希 |
| `latestEventSequence` | 事件续传游标 | 保存于任务卡运行态，不作为生产事实 |

## 5. 16 个节点与灵小枢文案映射

| 节点 | 默认用户文案 | 可能等待谁 |
| --- | --- | --- |
| `task_binding` | 正在建立图片任务 | 系统 |
| `business_context` | 正在核对产品与制作目标 | 用户／系统 |
| `asset_manifest` | 正在检查企业素材与授权 | 用户／系统 |
| `reference_snapshot` | 正在冻结参考图证据 | 系统 |
| `element_inventory` | 正在拆解参考图构图和元素 | 系统 |
| `hook_factors` | 正在筛选最关键的 4–5 个爆点 | 系统 |
| `adaptation` | 正在确定保留、替换与创新点 | 系统 |
| `director_brief` | 正在形成图片编导方案 | 系统 |
| `execution_plan` | 正在选择制作路线 | 用户／系统 |
| `render_spec` | 正在冻结画布、图层和文字规格 | 系统 |
| `candidate_generation` | 正在生成候选图片 | 系统／外部结果核对 |
| `quality_check` | 正在检查事实、版式和品牌一致性 | 系统 |
| `director_review` | 编导正在独立复核候选 | 系统 |
| `repair` | 正在定点修复未通过区域 | 用户／系统 |
| `user_approval` | 图片已准备，请验收 | 用户 |
| `delivery` | 正在整理可下载成品 | 系统 |

`stale` 必须显示“上游信息已更新，正在按新版本重新核对”；`outcome_unknown` 必须显示“结果正在核对，请勿重复提交”；不得把二者都写成普通“生成中”。

## 6. 双方职责

### 灵小枢／首页分支

- 原子地保存用户参考消息并创建／取得 `ContentTask`；
- 将 `contentTaskId`、版本、稳定幂等键传给图片服务；
- 在同一任务卡渲染快照、事件、候选和决定；
- 实现事件流转发或轮询，不猜状态；
- 用户点击“采用”或“修改”时调用专用决定接口；
- 不直接修改图片节点、批准凭证和交付包。

### 图片功能分支

- 验证租户、任务版本和交付物范围；
- 保存 16 节点状态、版本化输出、事件和候选谱系；
- 执行 4–5 个爆点、创新点、硬质量门、独立复核和局部返工约束；
- 在服务端校验实际候选字节后冻结批准成品；
- 提供可恢复快照、增量事件和幂等交付包；
- 不发送聊天消息、不自动发布、不把内部推理暴露给前端。

## 7. 合并注意事项

灵小枢分支应先合并，随后合并图片分支。若出现冲突，应保留：

- `src/lib/socialImageApi.ts` 中新增的 ContentTask 子运行、状态、刷新、决定和交付接口；
- `SocialImageWorkbench` 对 `contentTaskId` 与 `entrySource` 的接收及统一任务绑定；
- 灵小枢分支对首页消息、任务卡和事件流的最新实现；
- 不恢复无 ContentTask 的旧图片创建入口。

任何冲突解决都不能把“聊天消息状态”重新变成生产事实源，也不能让前端通用 PATCH 写入批准状态。
