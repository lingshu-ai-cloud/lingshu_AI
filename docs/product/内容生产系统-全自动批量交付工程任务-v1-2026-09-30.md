# 内容生产系统：全自动化与正式批量交付工程任务 v1

- 日期：2026-09-30
- 文档状态：工程排期基线，不代表功能已经实现或生产环境已经验收
- 代码基线：`f811edd0719a70e59a4daa566ea294660e8b98d5`
- 目标：把当前“能生成部分内容”的能力，升级为“正常任务无人值守、异常可恢复、成本可控制、质量可证明、可持续批量交付”的内容生产系统
- 适用角色：产品经理、编导/内容算法、前端、后端、媒体工程、平台/SRE、QA、安全与交付运营

## 1. 结论先行

当前系统不能仅靠“再接几个生成模型”进入正式批量交付。代码已经具备部分内容分析、素材匹配、数字人、Seedance、渲染、质量检查、任务租约、就绪检查和交付投影，但正式批量交付仍被以下五类问题共同阻塞：

1. **编导结果还没有成为稳定、可执行的逐镜合同。** 精确逐句时间、镜头动作、产品/人物身份锁、素材权利、供应商输入和验收点没有在同一不可变版本里闭环。
2. **逐镜执行没有统一的持久任务模型。** 部分任务有幂等、租约和回执，但还没有覆盖全部供应商、渲染、质检与返工的统一状态机。
3. **当前生产形态不能安全横向扩容。** 发布编排仍是单 `app` 容器加 PocketBase；HTTP、调度和大量后台工作默认同进程运行，代码也明确在持久队列完成前禁止 Web/Worker 拆分。
4. **媒体、API 和供应商管理不统一。** 生产对象存储代码要求 COS，但部分部署示例、发布代码和备份文档仍使用 R2 命名；供应商能力、密钥、额度、限流、熔断、成本和账单也没有形成统一管理面。
5. **没有批量交付所需的生产证据。** 现有容量工具只覆盖公开健康/就绪 GET，不能证明已登录业务流、上传、队列、AI 供应商、渲染、SSE、故障恢复和长稳运行。

因此，正式批量交付前的正确顺序是：

`冻结交付规模与质量标准 → 固化编导/内容合同 → 建立逐镜路由和预检 → 建持久队列与统一供应商任务 → 统一媒体存储 → 自动质检与局部返工 → 做真实供应商 E2E → 做容量、故障和恢复验收 → 小批量灰度 → 正式放量`

只升级单台服务器规格不能替代这条路径。现有实际服务器是否“够用”，也不能从代码仓库直接得出；必须先做只读资源盘点和内容负载压测。

| 冲突 | 本版统一口径 |

## 3. “全自动化”的产品定义

### 3.1 正常路径

用户选择企业、账号、产品、平台、语言和内容目标后，系统自动完成：

1. 读取已确认的企业事实、产品档案、品牌规则、人物和素材授权。
2. 生成或导入编导方案，形成冻结的逐句脚本与逐镜合同。
3. 按 14 类场景识别每个镜头，检查能力、素材、预算、额度和供应商状态。
4. 为每镜选择主路线和降级路线，计算预估成本与完成时间。
5. 创建持久任务，自动调度素材处理、TTS、数字人/视频生成、动态图文和本地渲染。
6. 自动执行技术、语义、身份、事实、权利和平台质量检查。
7. 失败时只返工受影响镜头；供应商故障时按规则重试、换供应商或降级，不重复付费。
8. 合成平台版本，生成交付包、成本单、质量回执和全链路血缘。
9. 达到自动放行条件时交付；高风险或低置信结果进入异常队列。

### 3.2 全自动不等于无边界

以下事项不能由模型自行猜测：

- 真人肖像、声音和素材授权；
- 客户案例、证书、工厂、功效、价格和真实结果；
- 超出预算、跨境传输或敏感数据外发；
- 不可逆的平台发布动作；
- 质量模型低置信但可能损害品牌的候选。

系统必须在任务启动前把这些边界转化为已配置政策。正常任务无需人工逐步点击；只有政策没有配置或出现异常时才进入人工队列。

### 3.3 统一业务状态

内容批次、单条内容和单个镜头分别持有状态，禁止用一个“处理中”覆盖所有阶段：

`draft → preflighting → blocked_input / queued → executing → quality_checking → repairing → assembling → ready_to_release → delivered`

任意阶段还可进入 `retry_scheduled`、`human_attention`、`failed_terminal` 或 `canceled`。页面刷新、进程重启、Worker 崩溃后必须从服务端事实恢复，不能依赖浏览器内存。

## 4. 14 类生成场景的自动路由矩阵

每种场景都要注册“首选执行器、必要输入、禁止事项、自动降级、质量门和成本档位”。场景注册表由服务端版本化，前端只展示结果和待办。

| ID | 场景 | 首选自动路线 | 必要前提 | 自动降级/阻断 | 关键验收 |
| --- | --- | --- | --- | --- | --- |
| SC01 | 纯人物口播 | 已授权账号人物 + HeyGen/可替换数字人 + MiniMax/Qwen TTS | 人物与声音授权、脚本、字/音素时间、语言口音策略 | 数字人不可用时转授权真人口播或动态图文+配音；无授权则阻断 | 人物一致、口型、语音自然度、字幕同步、手势不过度、无包装畸变 |
| SC02 | 泛行业人物/UGC | 同账号授权真人素材优先；受控人物模型补齐 | 素材商用范围、人物连续性 ID、账号人物版本 | 找不到同一人物时不能随机换脸；转无人物 B-roll 或待拍 | 同账号人物一致、肖像权、动作与文案匹配 |
| SC03 | 纯产品静态展示 | 产品原图抠图 + 确定性版式/局部运镜 | 产品身份锁、透明图/多角度图、Logo/文字保护区 | 无合格原图时阻断并生成采集任务 | 轮廓、颜色、数量、Logo、包装文字、比例不变 |
| SC04 | 开盖/旋转/挤压/质地 | 企业实拍优先；多角度产品锁 + 受控视频生成 | 动作起止、接触位置、材质、参考角度齐备 | 无法保证产品和物理动作时转静态分解图或待拍，不伪造结果 | 产品身份、接触关系、物理连续性、质地真实性 |
| SC05 | 产品 + 生成环境 | 锁定产品前景 + 生成背景/灯光 + 合成 | 产品蒙版、阴影/反射规则、场景拓扑 | 生成污染产品时退回确定性合成 | 产品像素保护、光影一致、边缘无穿帮、空间合理 |
| SC06 | 人拿产品 | 授权真人/UGC 实拍优先；受控人物生成补齐 | 手部、产品比例、抓握位置、人物版本 | 手/包装无法稳定时转产品特写或待拍 | 手指完整、抓握真实、产品不变形、人物一致 |
| SC07 | 人使用产品 | 授权真人或专业 UGC；高控制模型仅在能力门通过后使用 | 完整使用步骤、接触关系、安全边界、人物/产品授权 | 当前能力不达标时自动转待拍或步骤信息卡，禁止假装真实使用 | 动作因果、接触位置、产品状态和安全提示正确 |
| SC08 | 产品上脸/展示功效 | 实拍或授权创作者 | 人物授权、使用方法、功效证据、前后对比条件 | 不允许生成虚假功效；无证据时改为使用方法/卖点卡 | 不夸大、不伪造前后对比，肤色/面部无异常 |
| SC09 | 人物 + 工厂设备 | 企业授权素材或明确商用素材 | 来源、工厂归属、设备和人物授权 | 通用素材必须标为示意；不能冒充客户现场 | 来源可追溯、无错误品牌、人与设备关系真实 |
| SC10 | 工厂/质检/生产流程 | 企业真实素材 + 短片段剪辑 | 流程步骤、素材时间段、事实确认 | 缺真实素材时转流程图或待拍，不生成“客户工厂实景” | 流程顺序、设备名称、事实与画面一致 |
| SC11 | 参数/卖点/流程/对比 | 模板化动态图文、信息卡、必要时 3D 解释 | 已确认事实、单位、来源、免责声明 | 未确认数据不进入成片 | 数值、单位、语言、排版、可读时长正确 |
| SC12 | 客户案例/效果/证书/展会 | 授权素材 + 信息可视化 | 证据文件、有效期、授权和可用范围 | 无证据则删除主张或改为一般能力说明 | 证据可追溯、不过期、不误导、不泄露客户信息 |
| SC13 | 转场/氛围/环境 B-roll | 已授权素材；非证明性场景可用 Seedance/Veo | 场景语义、画幅、时长、禁止元素 | 供应商故障时转素材库或模板转场 | 不承担事实证明、风格连续、无品牌污染 |
| SC14 | CTA/品牌结尾 | 模板化动态图形 + 真实 Logo/产品/联系方式 | 品牌规范、CTA、链接/二维码和安全区 | 缺 CTA 配置时阻断最终交付 | Logo 不变形、信息可读、平台安全区、链接正确 |

首批正式交付不要求所有高级生成路线都成熟，但要求 14 类场景全部有**可执行首选路线或明确自动降级路线**；不能出现任务提交后才发现“此类镜头系统根本不会做”。

## 5. 目标系统与关键联调合同

### 5.1 目标流水线

```text
内容订单
  → 企业/产品/授权快照
  → 编导交接物 DirectorHandoffV3
  → 逐镜图 ShotGraph
  → 能力/预算/素材/权利预检
  → 持久工作流与优先级队列
  → 素材、TTS、人物、产品、图文、渲染 Worker
  → 候选对象与供应商回执
  → 自动质量门与局部返工
  → 多平台合成与交付包
  → 发布/下载回执、成本对账和效果回流
```

横向公共能力包括：PostgreSQL 事实库、Redis/持久队列、COS 对象存储、供应商网关、密钥管理、日志/指标/追踪、审计、配额和告警。

### 5.2 `DirectorHandoffV3`

编导 Agent 不再只传一段自然语言分析，必须为每个镜头提供：

- `handoffId`、`schemaVersion`、租户/项目/内容版本、输入哈希；
- 企业事实、产品档案、人物、品牌与授权快照版本；
- 稳定 `lineId`、逐句原文、语言、精确起止时间、目标时长；
- `sceneType`、镜头功能、观察事实、推断意图、风险和置信度；
- 主体、环境、动作起止、接触关系、构图、景别、运镜、灯光和声音；
- 产品/人物身份锁、允许改变与禁止改变的部分；
- 事实/证据引用、素材权利要求、允许的外部处理范围；
- 可接受的执行路线、禁止路线、自动降级顺序；
- 可机器判断的验收条件、预算档和截止时间。

编导交接物一旦进入生产即不可原地覆盖；修改必须生成新版本，并使受影响镜头的旧候选失效。

### 5.3 `RouteDecisionV1`

内容 Agent 对每个镜头保存：

- 选中的策略、适配器、供应商、模型/模板版本和选择理由；
- 能力、配置、租户授权、素材、预算、额度、地域和权利检查结果；
- 输入资产版本及哈希、预估成本/时长/成功率；
- 降级链、最大尝试次数、超时、退避和是否允许换供应商；
- 全局幂等键、请求哈希、预算预留 ID 和追踪 ID。

### 5.4 `ProviderJobV1` 与 `CandidateAssetV1`

所有外部供应商和本地媒体任务使用同一任务外壳，至少记录：

- 本地任务 ID、远端任务 ID、状态、attempt、lease owner/fencing token；
- 提交请求哈希、供应商回执、轮询游标、Webhook 事件 ID；
- 预留成本、实际用量、实际成本、退款/失败状态和账单来源；
- 输出对象键、内容哈希、时长、编码、宽高、帧率和派生关系；
- 语义、身份、事实、权利、技术和平台质量结果；
- 是否可自动放行、阻断原因、返工范围和最终交付引用。

禁止把密钥、原始敏感素材、长 Prompt 或大文件放进队列载荷；队列只放稳定 ID 和最小快照引用。

## 6. 详细工程任务总表

### 6.1 排序和估算规则

- 排序主键：`P0 → P1 → P2`；同一优先级按 `S → M → L → XL` 展示。
- `P0`：不完成就不能对外正式批量交付。
- `P1`：可在小批量灰度后完成，但必须在规模放大前关闭。
- `P2`：质量、成本和运营效率优化。
- 工程量为跨角色的初始人日：`S=1–3`、`M=4–8`、`L=9–15`、`XL=16–30+`。真实排期需在接口和数据迁移 Spike 后重估。
- 表格顺序不是串行开发顺序；第 9 节给出依赖驱动的执行波次。

### 6.2 P0：正式批量交付阻断项

## 7. 服务器、容量和成本专项

### 7.1 当前能否判断服务器够用

不能。仓库只说明部署结构和代码上限，没有实际主机的连续 CPU、内存、磁盘 IO、网络、容器、数据库和任务峰值数据。当前单 `app + PocketBase + Caddy` 形态即使短期跑通，也不应作为正式批量交付架构：媒体转码会与 API/调度争抢资源，进程退出会同时影响前台与后台，且不能安全增加 API 副本。

### 7.2 首轮工程估算负载档案

若业务暂未给出交付量，工程可先用以下 **估算档，不是商务承诺**：

- 100 个客户，每客户每天 3 条内容，共 300 条/日；
- 单条 30–90 秒，平均 8–15 个镜头，10% 镜头发生一次返工；
- 峰值 30 条流水线同时运行、10 个并发上传、8 个外部生成提交；
- 已登录 UI 延续架构目标做 1,200 会话混合负载；
- 4 小时常规 soak，季度执行 24 小时长稳；
- 原始素材 30 天热存、交付件按合同保留，临时中间件 1–7 天自动删除。

产品必须在 P0-S-01 中确认或修改这些值，之后再采购和承诺容量。

### 7.3 容量计算必须分开

- API 容量：活跃会话、读写比例、SSE 连接、上传签名和查询 p95/p99。
- 编排容量：每分钟新任务、队列等待、租户公平、重试风暴和 DLQ 增长。
- 外部供应商容量：`到达率 × 供应商 p95 时长 × 重试系数`，受账号并发/QPS/日额度约束。
- 媒体 Worker：每条视频的 FFmpeg CPU 分钟、内存峰值、临时盘峰值和并行数。
- 存储：`每日输入+中间件+输出 GB × 保留天数 × 版本/重试系数 × 1.2 余量`。
- 数据库：任务/事件写入速率、连接数、索引大小、归档和备份窗口。
- 网络：素材入站、供应商出入站和交付下载分开计量。

### 7.4 用于压测的起始拓扑

以下只用于建立测试环境，不是未经压测的采购结论：

| 层 | 起始配置建议 | 说明 |
| --- | --- | --- |
| Web/API | 2 个实例，每个 2–4 vCPU、4–8 GB | 仅处理短请求、签名和查询，不做转码/长轮询 |
| 编排 Worker | 2 个实例，每个 2–4 vCPU、4–8 GB | 负责 DAG、供应商提交/轮询、回执和状态推进 |
| 媒体 Worker | 2 个实例，每个 8–16 vCPU、16–32 GB、独立临时 NVMe | 实际并发由 FFmpeg 基准决定；避免与 API 共置 |
| PostgreSQL | 托管 HA 或等价，4–8 vCPU、16–32 GB 起测 | 开启 PITR、连接池、慢查询和容量告警 |
| Redis/队列 | HA，2–4 GB 起测 | 持久化、内存上限、故障切换和 DLQ 监控 |
| 媒体存储 | COS 私有桶 + CDN/签名下载 | 原始/派生/交付/质检证据分前缀和生命周期 |
| GPU | 默认不配置 | HeyGen/Seedance/Runway/Veo 为外部能力；只有自建模型时单独建池 |

最终规格以 P0-XL-04 的资源曲线、30% 以上余量和成本报告为准。

## 8. API 与系统管理必须补齐的细节

### 8.1 供应商 API 管理

- 密钥按环境、供应商和用途隔离；禁止写入仓库、日志、队列、前端或错误正文。
- 每次请求有全局幂等键；供应商不支持幂等时由本地任务账本阻止重复提交。
- Webhook 必须验签、校验时间窗和事件去重；轮询与 Webhook 可同时存在但只能推进一次状态。
- 对 429、5xx、超时、内容拒绝、余额不足、账户冻结、模型下线分别处理，不能统一“重试三次”。
- 配额同时覆盖供应商账号、模型、租户、批次和单镜；预算必须先预留、完成后对账、失败后释放。
- Readiness 要区分“配置存在”“供应商可访问”“账户有余额/额度”“该模型可用”；不能只检查环境变量。
- 模型版本升级必须跑固定评测集，支持按租户灰度和一键回滚。
- 供应商成本、币种、税费、退款和账单延迟有明确口径。

### 8.2 内部 API 管理

- 所有写接口要求鉴权、租户隔离、权限、幂等、请求大小、超时和审计。
- `X-Request-Id` 必须进入日志和下游调用，不能只作为响应头返回。
- 长任务 API 只负责创建/查询/控制任务，不保持 15 分钟 HTTP 请求等待供应商。
- 大文件使用对象存储直传，服务端只签发短时上传凭据并验证完成对象。
- 关键 API 版本化；破坏性变更先双读/双写或适配，不能静默改变前端含义。
- 分布式限流按边缘 IP、租户、用户、API key 和高成本资源组合执行；当前进程内 IP 限流只保留为单实例保护。

### 8.3 监控和告警

最少建立以下看板与告警：

- 业务：提交量、完成量、交付 SLA、异常队列、取消、人工介入、自动放行率；
- 队列：等待时长、执行时长、lease 过期、重试、DLQ、租户公平；
- 供应商：提交/完成成功率、429/5xx/超时、p95、余额、配额、成本偏差；
- 质量：按场景和供应商的身份、口型、语义、产品、事实、技术失败率及返工率；
- 媒体：上传、下载、转码、临时盘、对象存储失败、丢失对象和签名 URL；
- 基础设施：CPU、内存、GC、事件循环、磁盘/IO、网络、数据库连接/慢查询、Redis 内存和复制；
- 安全：异常鉴权、越租户访问、密钥读取/轮换、Webhook 验签失败和敏感日志扫描。

告警必须带租户、工作流、镜头、供应商任务和运行手册链接，但不得包含密钥和客户敏感正文。

### 8.4 备份与灾难恢复

建议首批批量交付目标为 `RPO ≤ 15 分钟、RTO ≤ 2 小时`，由业务确认。数据库备份不能替代对象存储清单；恢复时必须同时验证数据库引用、对象哈希、供应商未知任务、预算账本和未完成工作流。至少覆盖：

- 数据库误删、实例故障和迁移失败；
- Redis/队列丢失或切换；
- Worker 在供应商已经受理后崩溃；
- 对象存储暂时不可用或对象缺失；
- 供应商回执延迟、重复或永不到达；
- 应用回滚后继续读取新版本事实。

## 10. 正式批量交付放行门禁

以下门禁全部满足才可标记“正式批量交付就绪”：

1. **场景覆盖：** SC01–SC14 都有可执行主路线或经产品批准的自动降级路线。
2. **合同完整：** 交付任务 100% 使用版本化编导交接物、路由决策和输入哈希。
3. **幂等与恢复：** 重复提交、页面刷新、API 重启、Worker 崩溃和重复 Webhook 不产生重复付费或重复成片。
4. **质量：** 每个交付件都有机器可读质检回执；高风险证明性内容没有自动伪造；抽检误放率达到业务阈值。
5. **成本：** 提交前可见预算，供应商完成后有实际用量，月度账单差异可解释。
6. **存储：** 交付资产和质检证据在对象存储；本地盘只作为有上限、可清理的临时空间。
7. **容量：** 通过确认后的内容负载档案、1,200 已登录混合会话、4 小时 soak 和故障注入，关键资源保留至少 30% 余量。
8. **可观测：** 任何失败能在 10 分钟内定位到租户、任务、镜头、供应商尝试和具体错误分类。
9. **恢复：** 隔离环境完成数据库与对象恢复，达到确认的 RPO/RTO；恢复后未完成任务能继续或安全终止。
10. **安全与权利：** 密钥、租户隔离、素材授权、数据外发、保留/删除和审计通过检查。
11. **交付运营：** 值班、告警、停机公告、供应商升级、成本异常和客户补偿都有 owner 与运行手册。
12. **真实 E2E：** 至少一轮真实供应商、真实存储、真实渲染、真实下载的证据通过，不用 Mock、测试旁路或手工补数据替代。

## 11. 产品经理与开发必须在动工前回答的问题

### 产品/交付

- 首批客户、每天每客户交付几条、最长视频和允许交付时长是多少？
- “全自动交付”是否包含自动发布，还是只到成片/交付包？
- 哪些场景允许自动降级，哪些必须阻断？
- 哪些客户或品类必须保持最终人工审核？
- 自动放行的误放率、返工率和质量底线是多少？
- 供应商成本超预算时，是等待、降级、换供应商还是停止？

### 内容/编导算法

- 每一类场景的最小输入和机器验收标准是什么？
- 编导结论中哪些是观察事实、哪些是推断、哪些允许内容 Agent 改写？
- 同一人物、产品和品牌跨镜/跨片的一致性以哪个版本为真值？
- 参考爆款的哪些部分只可分析，哪些可保留结构，哪些绝不能进入生产？

### 后端/平台

- 所有外部副作用是否都能关联本地幂等账本、远端任务和成本回执？
- 供应商受理成功但本地保存失败时如何对账，而不是盲目重提？
- Web、编排、媒体三类负载是否真正隔离？
- 数据库、队列和对象存储任一不可用时，系统进入什么状态、谁收到告警、如何恢复？
- 当前生产密钥、配额、余额和模型下线由谁负责？

### QA/SRE

- 哪套固定素材和金标用于供应商升级回归？
- 如何验证口型、产品身份、人物连续性、字幕和事实，而不只检查文件能播放？
- 如何证明没有重复扣费、丢任务、跨租户和对象丢失？
- 压测是否覆盖真实上传、转码、队列和回执，而不是只打健康检查？

- 当前进程角色已有 `all/web/worker` 缝隙，但持久队列完成前主动禁止拆分；对应 P0-XL-01。
