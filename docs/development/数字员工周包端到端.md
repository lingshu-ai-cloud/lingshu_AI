# 数字员工周包端到端

> 状态：实施中  
> 建立日期：2026-10-20  
> 适用范围：数字员工周任务包、周执行图、内容生产、异常干预、验收、发布与效果回流  
> 当前实施分支：`codex/colleague-handoff-20261019`

## 1. 开发原则

本规划以两条规则作为开发、联调和发布的硬门槛：

1. 每项能力必须接入现有产品入口、领域服务、持久队列和真实执行器。只有端到端贯通才算完成；局部函数、局部节点或局部测试通过不能代表功能完成。
2. 开发目标是改善用户完成周任务的体验。成片只是任务流中的产物和诊断样本，不以单条 MVP 成片效果代替产品任务流、异常处理和经营闭环建设。

## 2. 目标链路

```text
用户进入数字员工
→ 系统依据企业资料形成周任务建议
→ 产品展示预计费用和执行范围
→ 用户一次接受周任务
→ 冻结周包、方案、预算和关键资产版本
→ 周执行器创建正式领域任务
→ 持久队列领取任务
→ LangGraph 调用现有生产执行器
→ 运行中仅在真实例外发生时请求用户干预
→ 用户在原任务详情处理同一版本化决策
→ 系统从原断点恢复
→ 用户验收最终成片
→ 用户主动发布
→ 真实效果回流下一周计划
```

## 3. 产品边界

- 采集开始前不假定具体样片政策、同品素材或素材授权已经可知。
- 产品侧提前估算周包费用；用户接受周包后，在冻结预算内自动执行。
- 人物、声音、产品资产不可用，权利状态变化或预算内不存在合格方案时，才创建异常决策。
- 异常通知、助手决策中心和任务详情必须消费同一决策对象、版本和任务身份。
- 单条内容失败只暂停该条，不能阻塞整周。
- 不新增平行制作台、平行任务、平行素材库、平行预算账本、第二张异常卡或第二套执行器。
- 周包授权不等于成片验收或发布授权；成片必须由用户最终验收，发布必须由用户主动触发。

## 4. 唯一 Golden Journey

```text
数字员工首页
→ 接受本周推荐任务
→ 冻结周任务版本
→ 创建周执行图
→ 创建正式内容任务
→ 订单与预算原子准入
→ content_execution_jobs
→ worker 领取及续租
→ LangGraph checkpoint
→ 现有素材、人物、声音和视频生产执行器
→ 供应商回执与成本证据
→ 多维 QA
→ 异常干预或成片验收
→ delivery package
→ 用户主动发布
→ 平台回执、指标与下周输入
```

每次阶段验收必须从正式产品或领域入口启动，不得直接调用中间图节点来代替整链验证。

## 5. 第一阶段：恢复可信的端到端技术底座

### 5.0 实施进度（2026-10-20）

第一阶段代码已完成，正在按完整质量门禁收口：

- 已修复 PostgreSQL Store 与 cutover store 的原子 CAS 能力声明和严格转发。
- 已修复 LangGraph 完整媒体 E2E，并恢复真实本地 MP4、QA、人工审核、恢复和交付验证。
- 已新增隔离技术 canary，验证同一构建的 Web→worker 领取及 checkpoint 写读回验。
- 已新增内容 worker 心跳、内容订单原子存储等 fail-closed readiness 检查。
- 已把进程角色、BullMQ 队列和完整媒体 E2E 归入统一生产运行时质量门禁。
- 已新增前向 migration `1792195221_create_weekly_production_runtime_probes.js`，未修改历史 migration。

沿途发现并解决的问题：

1. PostgreSQL 底层具备原生 CAS，但此前底层和 cutover 层都未暴露能力声明。
2. 完整媒体测试 Store 同样缺少能力声明，导致订单准入 fail-closed。
3. 完整媒体夹具缺少唯一 `social_program`，无法冻结订单预算归属。
4. 隔离子进程无法从临时目录解析 `tsx`。
5. 四段测试素材实际完全相同，被真实逐镜 QA 正确识别为重复镜头；夹具已改为四段可测且不同的画面，没有放宽 QA。
6. 旧审核版本篡改断言落后于当前更早的审核对象变化门禁。
7. 普通 Redis 连通、历史 checkpoint 和通用 heartbeat 都不能证明当前构建的 Web→worker 实际领取，因此新增不进入业务队列、不会调用供应商的独立技术 canary。
8. 技术 canary 自身异常只阻断 readiness，不允许反向拖垮正常业务 worker。

非阻断观察：本地媒体 OCR 会把异常的 `65024 DPI` 回退到 `70 DPI`；Vite 仍提示部分 chunk 大于 500 kB。

### 5.1 工作项

1. 修复 PostgreSQL selected store 的原子能力声明和转发：
   - `supportsAtomicCompareAndSwap` 必须来自真实后端能力；
   - `compareAndSwap` 和能力声明必须同时存在；
   - 不支持原子 CAS 的后端继续 fail-closed。
2. 修复 LangGraph 完整媒体专项测试：
   - 测试 Store 使用同一原子能力合同；
   - 覆盖任务创建、渲染、真实本地 MP4、QA、人工验收、恢复和交付；
   - 不跳过测试，不使用固定 `passed` 替代检测。
3. 扩充环境与运行时 readiness：
   - `content_order_atomic_store`；
   - `langgraph_checkpoint_store`；
   - `content_worker_heartbeat`；
   - `web_to_worker_job_claim`；
   - Redis/BullMQ 和数据库兜底扫描；
   - 执行器绑定及审批恢复。
4. 把完整媒体专项测试纳入正式质量门禁。
5. 为 Web 与 worker 分进程链路补充实际领取和恢复测试。

### 5.2 验收条件

- `pnpm run test:langgraph` 通过。
- `pnpm run test:langgraph:local-production` 通过。
- selected store 原子能力合同测试通过。
- readiness 在缺少任一可信证据时 fail-closed。
- Web 入队后 worker 能领取同一持久任务。
- worker 强退后从原 checkpoint 恢复，已完成付费阶段不重复调用。
- `pnpm run quality`、`pnpm test`、`git diff --check` 全部通过。

## 6. 第二阶段：贯通正式周任务 Golden Journey

### 6.1 工作项

- 从数字员工正式入口创建和接受周任务。
- 复用周任务包、周执行图、Starter198 内容任务和 `content_execution_jobs`。
- 冻结产品、人物、声音、预算、方案及输入哈希。
- 让周执行器调用现有 LangGraph 和生产执行器，不在页面或测试中绕过业务准入。
- 将供应商 request ID、费用和产物血缘回写同一任务。
- 从原任务详情处理异常并从断点恢复。

### 6.2 禁止事项

- 新建第二套任务或状态机。
- 页面直接调用供应商。
- 用临时 JSON 代替正式领域记录。
- 为单节点新增平行 worker。
- 在 LangGraph 内重写供应商重试机制。
- 用普通素材替代指定的产品、人物或声音资产。

### 6.3 验收证据

每次 Golden Journey 必须记录产品动作、周包版本、任务 ID、预算范围、job ID、图 thread ID、checkpoint、供应商回执、成本、产物哈希、QA、用户决策和交付包 ID。

## 7. 第三阶段：产品任务流与动态异常

产品向用户统一呈现以下领域节点：

1. 本周目标；
2. 事实、素材与授权准备；
3. 推荐方案与预计费用；
4. 周任务已授权；
5. 内容生产；
6. 系统质量检查；
7. 需要用户处理的例外；
8. 最终成片验收；
9. 待用户主动发布；
10. 效果回收。

动态异常遵循：先执行可确定部分，真实缺口发生后暂停受影响单条任务，创建版本化决策，通知用户进入原任务详情，处理后校验原对象及版本并从断点继续。

用户在任务详情必须能看到当前进度、暂停原因、已完成工作、已发生费用、系统已尝试的恢复、需要采取的动作、恢复位置及是否会再次收费。

## 8. 第四阶段：产品级质量与恢复

质量必须分别表达：

- 技术质量；
- 事实质量；
- 权利质量；
- 表达质量；
- 业务可交付质量。

统一恢复顺序：首次生产 → QA → 同一管线定向修复一次 → 再次 QA → 原预算内受控降级修订 → 无合格方案时请求用户干预。已通过镜头不得重做，重试与降级共享原预算。

## 9. 第五阶段：受约束引入 DeepAgent

DeepAgent 不替代 LangGraph，也不直接控制业务真相。首批仅用于只读资料分析、缺口发现、候选方案生成、脚本/分镜语义评审和方案取舍解释。

首版禁止 DeepAgent 直接修改业务事实、调用付费供应商、提高预算、确认授权、批准成片、执行发布或无限创建子 Agent。其输出必须是包含输入版本、证据、不确定项、费用估计、风险和工具轨迹的结构化候选，由领域服务校验后再交给 LangGraph 推进。

## 10. 第六阶段：真实基础设施联调与灰度

使用 PostgreSQL、Redis/BullMQ、独立 Web/worker、对象存储、一个已授权真实供应商账号和内部测试租户完成联调。主动注入 Web/worker 重启、Redis 不可用、供应商超时、接受后本地写入失败、checkpoint 失败、上游事实变化、资产撤销、预算耗尽和重复命令。

灰度顺序：内部租户 → 单产品/人物/声音 → 单供应商 → 只生产不自动发布 → 完整周周期 → 少量客户 → 多供应商和更高自治。

## 11. 统一完成定义

任何功能只有同时满足以下条件才算完成：

- 有正式产品入口；
- 使用正式领域对象；
- 接入既有执行器；
- 有持久状态、上游调用者和下游消费者；
- 有失败、幂等和恢复路径；
- 有用户可理解的状态；
- 有费用与供应商回执；
- 有端到端测试并通过 Golden Journey；
- 能说明改善了哪个产品指标。

函数完成、节点测试通过或生成一条样片，都不能单独作为完成依据。

## 12. 产品与工程指标

- 周任务启动成功率；
- 产品入口到执行器的贯通率；
- 无意义人工确认次数；
- 异常定位和处理成功率；
- 断点恢复成功率；
- 重复付费次数（必须为零）；
- 预算预估与实际费用偏差；
- 单条失败隔离率；
- 最终成片验收率；
- 发布和经营效果回流率。
