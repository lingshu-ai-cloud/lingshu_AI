# 数字员工周包端到端

> 状态：实施中
> 建立日期：2026-10-20
> 适用范围：数字员工周任务包、周执行图、内容生产、异常干预、验收、发布与效果回流
> 当前实施分支：`codex/colleague-handoff-20261019`

## 1. 开发原则

本规划以两条规则作为开发、联调和发布的硬门槛：

1. 每项能力必须接入现有产品入口、领域服务、持久队列和真实执行器。只有端到端贯通才算完成；局部函数、局部节点或局部测试通过不能代表功能完成。
2. 开发目标是改善用户完成周任务的体验。成片只是任务流中的产物和诊断样本，不以单条 MVP 成片效果代替产品任务流、异常处理和经营闭环建设。

## 2. 目标链路

```text
用户进入数字员工
→ 系统依据企业资料形成周任务建议
→ 产品展示预计费用和执行范围
→ 用户一次接受周任务
→ 冻结周包、方案、预算和关键资产版本
→ 周执行器创建正式领域任务
→ 持久队列领取任务
→ LangGraph 调用现有生产执行器
→ 运行中仅在真实例外发生时请求用户干预
→ 用户在原任务详情处理同一版本化决策
→ 系统从原断点恢复
→ 用户验收最终成片
→ 用户主动发布
→ 真实效果回流下一周计划
```

## 3. 产品边界

- 采集开始前不假定具体样片政策、同品素材或素材授权已经可知。
- 产品侧提前估算周包费用；用户接受周包后，在冻结预算内自动执行。
- 人物、声音、产品资产不可用，权利状态变化或预算内不存在合格方案时，才创建异常决策。
- 异常通知、助手决策中心和任务详情必须消费同一决策对象、版本和任务身份。
- 单条内容失败只暂停该条，不能阻塞整周。
- 不新增平行制作台、平行任务、平行素材库、平行预算账本、第二张异常卡或第二套执行器。
- 周包授权不等于成片验收或发布授权；成片必须由用户最终验收，发布必须由用户主动触发。

## 4. 唯一 Golden Journey

```text
数字员工首页
→ 接受本周推荐任务
→ 冻结周任务版本
→ 创建周执行图
→ 创建正式内容任务
→ 订单与预算原子准入
→ content_execution_jobs
→ worker 领取及续租
→ LangGraph checkpoint
→ 现有素材、人物、声音和视频生产执行器
→ 供应商回执与成本证据
→ 多维 QA
→ 异常干预或成片验收
→ delivery package
→ 用户主动发布
→ 平台回执、指标与下周输入
```

每次阶段验收必须从正式产品或领域入口启动，不得直接调用中间图节点来代替整链验证。

- 已修复 LangGraph 完整媒体 E2E，并恢复真实本地 MP4、QA、人工审核、恢复和交付验证。

- 已新增前向 migration `1792195221_create_weekly_production_runtime_probes.js`，未修改历史 migration。

沿途发现并解决的问题：

1. PostgreSQL 底层具备原生 CAS，但此前底层和 cutover 层都未暴露能力声明。
2. 完整媒体测试 Store 同样缺少能力声明，导致订单准入 fail-closed。
3. 完整媒体夹具缺少唯一 `social_program`，无法冻结订单预算归属。
4. 隔离子进程无法从临时目录解析 `tsx`。
5. 四段测试素材实际完全相同，被真实逐镜 QA 正确识别为重复镜头；夹具已改为四段可测且不同的画面，没有放宽 QA。
6. 旧审核版本篡改断言落后于当前更早的审核对象变化门禁。
7. 普通 Redis 连通、历史 checkpoint 和通用 heartbeat 都不能证明当前构建的 Web→worker 实际领取，因此新增不进入业务队列、不会调用供应商的独立技术 canary。
8. 技术 canary 自身异常只阻断 readiness，不允许反向拖垮正常业务 worker。

非阻断观察：本地媒体 OCR 会把异常的 `65024 DPI` 回退到 `70 DPI`；Vite 仍提示部分 chunk 大于 500 kB。

## 6. 第二阶段：贯通正式周任务 Golden Journey

### 6.0 实施进度（2026-10-20）

第二阶段第一批正式链路已经接入现有系统，没有新增平行任务、状态机、预算账本或执行器：

- 周执行任务真实阻塞后，从既有 durable notification outbox 产生幂等提醒，并精确导航到原 program/package/version/executionTask 任务详情。
- 通知写入失败不会回滚已经持久化的阻塞状态；后续 Worker 扫描可恢复投递。仅提醒具有自身卡点的根任务，避免继承阻塞造成整张 DAG 通知风暴。
- 原任务 workspace 新增只读运行投影：暂停原因、已完成上游、真实已结算费用、原 job/Checkpoint、恢复与对账证据、下一动作以及再次收费可能性。
- 费用投影只认同租户、同 content task/run 的 settled ledger；未知费用保持 unknown，不显示为零或估算值。
- 从历史超长 `DigitalEmployeePage.tsx` 抽出纯展示的周计划确认组件；确认仍回到原版本化入口，文件预算由 5449 同步下调到 5441。
- 产品费用口径统一为“产品预估并在周计划确认时冻结费用边界；采集、语义分析、生产和返工分别经过既有颗粒化额度及费用证据”；不新增总授权卡。
- 新增正式 `test:weekly-golden-journey` 门禁，连续验证 pipeline、周 Worker、异常恢复、任务详情、交付导航和真实本地媒体 LangGraph/Checkpoint。

沿途发现并解决的问题：

1. 在 Worker 阻塞分支即时写通知不可恢复；改为从持久化 blocked 根任务做确定性 outbox 投影。
2. 给所有继承阻塞的下游任务发通知会制造提醒风暴；只通知带自身阻塞原因和 lastError 的根任务。
3. 任务详情原来只有身份和 blocking code，用户看不到已发生费用、恢复位置及是否可能再次收费。
4. 费用不能从预算上限或报价推断；只累计真实 terminal + settled + known 的 ledger 回执，扫描不完整时 fail-closed。
5. 周计划确认组件首次拆分后，尚未点击确认时缺项徽标会误显示为可确认；交叉审查时已修复，并保持提交后才展开具体错误列表。
6. 前端曾出现“采集不另设金额上限”的冲突文案，与后端费用证据门禁不一致，现已纠正。

第二阶段第二批已完成：

- 统一 workspace 运行投影已接入 Agent 任务日历的原“任务详情” Drawer，不再叠加第二套生产现场弹层。日历、通知和运行投影必须匹配同一 `executionTaskId`，身份不一致时 fail-closed。
- 新增版本化整周交付验收回执，汇总既有交付卡、执行任务、QA、逐条用户验收和已结算费用，并冻结版本、证据哈希与记录哈希。回执不授权发布，历史回执可读但非当前 active/head 版本不得新签。
- Golden Journey 门禁扩展到用户处理缺失素材、原任务从同一 job/run/checkpoint 恢复、已完成阶段不重复扣费，以及最终整周交付验收冻结。

本批次沿途发现的真实链路问题及处理：

1. 用户在正式素材请求中补交并审核视频后，Director 候选投影仍只看到企业产品身份图；修复为仅投影同租户、已审核、权利完整且哈希匹配的周素材。
2. 用户显式选择本地素材剪辑后，历史参考生产路由会重新开启 AIGC；改为保留参考分析供 QA 审计，但不覆盖用户已选的精确本地资产。
3. 普通任务更新可能丢失服务端私有的周权限快照；现在保留服务端下发的下划线字段，并在生产方案或素材状态变化时失效旧 Director plan，防止沿用过期决策。
4. 测试中注入自定义供应器会被正式付费边界正确拒绝；本次没有放宽边界，而是改用正式素材请求、审核、绑定和本地执行路由。
5. 周生产适配器丢失 `materialPorts`，导致已审核本地视频误走云端获取；现已把正式素材端口透传到原执行器。
6. 用户选择 `material_cut` 后，历史单参考策略仍在 LangGraph checkpoint 中被推断为 `single_source_fidelity`；现通过运行前的前向 revision 改为 `multi_source_hybrid`，将不可复用因子记录为 `functionally_replaced`，保留参考仅用于结构与 QA 审计。
7. 参考来源未透传 `cachedReferenceRecordId`，导致原片字节、连续帧和音频指纹无法正式核验；现复用 `addSocialTaskSource` 冻结真实记录和哈希，未伪造 proof。
8. 初始场景缓存对“同一已核验视频供多个镜头复用”误判为冲突；现仅在 id/path/hash/source/type 完全相同时允许，任何漂移仍 fail-closed。
9. 默认周口播缺少实测对齐证据；现用本地受控声音和 ffmpeg 实测时长生成对齐回执，不调用真实付费供应商。
10. 生产曾绕过 LangGraph 直接执行；现改为同一 job/run/checkpoint 下的 `executeSocialProductionGraph`，并在 `social.graph_review` 耐久暂停后恢复，已完成的声音阶段不重复计费。
11. quality/rework 的已成片快速返回分支遗漏 `quality_receipt`，且 Worker 结果验证器不识别该类型；现仅接受精确一个 artifact 与一个同任务、同版本 G5 receipt 的组合。
12. 用户 approval 会把同一成片从 vN 前向升级到 vN+1，旧验收服务却要求 QA/approval/card 版本完全相同；现要求直接前向版本、canonical content hash、production lineage 和 owned media bytes 全部一致，跳版或字节漂移仍拒绝。
13. Messenger 承接和 TikTok 发布在无真实授权时正确阻断；本阶段把“整周验收冻结”与“对外发布”解耦，验收回执固定 `authorizesPublishing=false`，测试断言无 publication attempt、无客服消息、无外网请求。

完整 M1 已验证：用户处理素材卡点后，原任务在同一 package version、execution task、content task、run 与 checkpoint 上恢复，通过 LangGraph quality、G4/G5/G6、逐条用户 approval 和 settled known 本地费用，最终冻结版本化整周验收回执。本测试不部署、不发布、不调用真实付费供应商。

## 7. 第三阶段：产品任务流与动态异常

产品向用户统一呈现以下领域节点：

1. 本周目标；
2. 事实、素材与授权准备；
3. 推荐方案与预计费用；
4. 周任务已授权；
5. 内容生产；
6. 系统质量检查；
7. 需要用户处理的例外；
8. 最终成片验收；
9. 待用户主动发布；
10. 效果回收。

动态异常遵循：先执行可确定部分，真实缺口发生后暂停受影响单条任务，创建版本化决策，通知用户进入原任务详情，处理后校验原对象及版本并从断点继续。

用户在任务详情必须能看到当前进度、暂停原因、已完成工作、已发生费用、系统已尝试的恢复、需要采取的动作、恢复位置及是否会再次收费。

## 8. 第四阶段：产品级质量与恢复

质量必须分别表达：

- 技术质量；
- 事实质量；
- 权利质量；
- 表达质量；
- 业务可交付质量。

统一恢复顺序：首次生产 → QA → 同一管线定向修复一次 → 再次 QA → 原预算内受控降级修订 → 无合格方案时请求用户干预。已通过镜头不得重做，重试与降级共享原预算。

## 9. 第五阶段：受约束引入 DeepAgent

DeepAgent 不替代 LangGraph，也不直接控制业务真相。首批仅用于只读资料分析、缺口发现、候选方案生成、脚本/分镜语义评审和方案取舍解释。

首版禁止 DeepAgent 直接修改业务事实、调用付费供应商、提高预算、确认授权、批准成片、执行发布或无限创建子 Agent。其输出必须是包含输入版本、证据、不确定项、费用估计、风险和工具轨迹的结构化候选，由领域服务校验后再交给 LangGraph 推进。

## 10. 第六阶段：真实基础设施联调与灰度

使用 PostgreSQL、Redis/BullMQ、独立 Web/worker、对象存储、一个已授权真实供应商账号和内部测试租户完成联调。主动注入 Web/worker 重启、Redis 不可用、供应商超时、接受后本地写入失败、checkpoint 失败、上游事实变化、资产撤销、预算耗尽和重复命令。

灰度顺序：内部租户 → 单产品/人物/声音 → 单供应商 → 只生产不自动发布 → 完整周周期 → 少量客户 → 多供应商和更高自治。

## 11. 统一完成定义

任何功能只有同时满足以下条件才算完成：

- 有正式产品入口；
- 使用正式领域对象；
- 接入既有执行器；
- 有持久状态、上游调用者和下游消费者；
- 有失败、幂等和恢复路径；
- 有用户可理解的状态；
- 有费用与供应商回执；

- 能说明改善了哪个产品指标。

函数完成、节点测试通过或生成一条样片，都不能单独作为完成依据。
